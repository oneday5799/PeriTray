## ⛔ `verify-wheel-volume.py` 曾长期 0/6（2026-09-28 已修，10/10）

这个坑值得留着，因为它**伪装成功能坏了**，消耗过一整轮排查：

- **根因：脚本盲选第 0 项注入。** 快照按 `it.battery.is_none() && !it.has_audio` 排序
  ⇒ **有电量的设备排在前面** ⇒ `#0` 常常是键鼠这类「有电量、无音频端点」的设备。
  在它上面滚滚轮**本来就该没反应**（键鼠也有 tooltip，但不是音量设备），而日志一行不出。
  ✅ 现在按触发区日志里的 `有音频 / 无音频` 标记挑项，并把「触发区里存在有音频的项」
  升为一条判据（没有就直接失败并说明，而不是静默打空）。
- **第二个坑：音量基线走 `cdp-eval.mjs → invoke("get_audio_devices")`，popup 隐藏时
  `invoke` 会挂死**（同机时灵时不灵，20~60s 超时）⇒ 旧版在这里 `raise`，整轮在
  **读基线**那步就崩，够不到滚轮。✅ 现在降级为可选：读不到就跳过依赖基线的两条判据，
  **日志判据照跑**（`滚轮音量 id=… 前 -> 后` 是应用自己的记录，不需要 IPC）。
- ⚠️ 排查期还发现**产品侧一个真缺陷**：命中判定之后的五个早退（快照为空 / 索引越界 /
  **无音频端点** / 无端点 id / 拿不到写线程）**一行日志都不打** ⇒ 用户报「滚轮没反应」
  时现场零线索。✅ 已全部补上 `滚轮未受理: idx=N 原因=…`（详细级）；
  纪律含义：**命中之后不许有静默 return**。
