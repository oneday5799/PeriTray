# PeriTray 迁移 Slint 1.18 评估报告

> 评估日期：2026-09-17　｜　分支：code-review-remediation（`32ea860`）　｜　版本 v1.3.6
> 性质：仅评估，未改动任何代码。

---

## 0. 一句话结论

**不建议为迁移而迁移。** 本项目真正要重写的是约 2,800 行「窗口/UI 胶水」+ 7,840 行前端，
而约 9,900 行业务逻辑（蓝牙、音频、2.4G、WMI、配置）基本不用动。
收益集中在「冷启动快、内存低、不再依赖 WebView2」这三点，代价是**样式重写 + 中文/IME 实测 + 4 个插件自研 + 打包链重做**。
若确有痛点（弹窗打开慢 / 内存占用高 / 用户缺 WebView2 Runtime），应按 §6 的「先 spike 后决策」走，不要一次性大爆炸重写。

## 2. Slint 1.18 到底给了什么（先澄清两处误解）

**误解一：「托盘图标是 1.18 的新功能」——不是。**
`SystemTrayIcon` 是 **1.17（2026-06-24）** 引入的，1.18 博客里没提托盘。
它的能力（据官方文档）：

- 顶层组件，`inherits SystemTrayIcon`，Windows 走 `Shell_NotifyIcon`；
- 属性 `icon` / `tooltip` / `visible` / `title`（Windows 下 `title` 无可见效果）；
- `clicked()` 回调：Windows 左键触发、右键开菜单；
- 子 `Menu` **响应式**——MenuItem 的 `title`/`enabled`/`checked` 变化时自动重建平台菜单；
- **限制**：托盘菜单上的 `shortcut` 绑定被忽略（未挂焦点窗口，无处触发）；
  `SystemTrayIcon` 根的组件**拿不到 window、也跑不了事件循环**，需与 Window 实例并存。

**误解二：「Slint 必须付费」——不是。**
两档 $0：

- **GPLv3**：本项目已是 GPL-3.0，直接可用，无额外义务。
- **Royalty-free License 2.0**（桌面/移动/Web，不含嵌入式）：免费用，**但有署名义务**——
  (a) 在「关于」页展示 `AboutSlint` 组件，**或** (b) 在可下载二进制的公开页面展示 Slint 徽章。
  → 本项目已有「设置 → 关于」页，走 (a) 几乎零成本。

### 1.18 真正的增量（2026-09-16 发布，评估时**仅 1 天**）

| 特性 | 对本项目的价值 |
|---|---|
| FlexboxLayout | 中：设备卡片列表/自适应布局比旧布局省事，但仍不如现在的 CSS 灵活 |
| 运行时改 z-order | 中：弹窗内浮层/右键菜单叠放次序可用 |
| 弹簧动画 spring() | 中高：现有 popup 用牛顿迭代手写 cubic-bezier(0.62,0,0.32,1)，可换成声明式 |
| 路径动画 | 低 |
| 模型 push/remove/insert | **高**：设备列表、音频会话列表是高频增删，1.18 前要靠整体重建模型 |
| 结构体字段默认值 | 中：44 个 command 的返回结构转 Slint struct 时省样板 |
| WindowMoveArea | 中：无边框设置页拖动（若自绘标题栏） |
| 实验性 Vello 渲染器 | 低：实验性，生产不碰 |
| 读屏可读 TextInput | 中：无障碍补课；**注意 HTML 方案原本天然有基础读屏支持，这是补齐而非超越** |

## 3. 收益（按确定性分级）

### A. 确定性高

1. **去掉 WebView2 依赖。** 不再要求用户装 WebView2 Runtime；`webview.rs` 整个模块（384 行）作废——
   恒透明背景、Suspend/Resume 内存档位、Controller2 QI 这些**纯为绕 WebView2 而存在**的代码全部消失。
2. **消除本机的 dev 启动绕行。** 现在必须带 `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS="--disable-gpu-sandbox"`
   （火绒拦 WebView2 GPU 沙箱，否则卡死在 `popup::create` 的 `builder.build()`）。迁 Slint 后此绕行不再需要。
3. **类型安全取代字符串 IPC。** 44 个 command + 90 处 invoke 的 stringly-typed 边界消失，
   改为 Rust 直调 + 编译期检查；前后端字段漂移类 bug 由编译器兜住。
4. **消除 P0-4 那一类死锁的土壤。** 现有「持锁区调 Tauri 菜单/窗口 API → `run_item_main_thread!` 无超时
   `rx.recv()` 等主线程 → 主线程又要这把锁」的 AB/BA 死锁，根子在 Tauri 的同步主线程派发。
   Slint 的模型是「状态在 Rust、菜单声明式响应式」，菜单更新不再需要跨线程同步等待。
   （**诚实补充**：不等于从此不会卡死。Slint 仍要求 UI 更新走 `invoke_from_event_loop`，
   在事件循环里做阻塞工作照样冻结，是无超时等待这一类具体机制消失。）
5. **体积与常驻内存。** 每个 webview 常驻约 50–100 MB，Slint 为几十 MB 量级；不再随窗口数线性增长。

### B. 中等（需实测才能确认）

6. **弹窗冷启动/打开延迟。** WebView2 首次建实例有明显初始化成本，托盘弹窗类应用对此最敏感。
   预期从数百毫秒降到数十毫秒，**但必须用真机计时验证，不要采信推断**。
7. **CSS 动画转声明式。** 现有 8 组 `@keyframes` + 11 处 `animation` + 20 处 `transition`，
   改为 Slint 声明式后由框架统一驱动，行为更可控。

### C. 基本拿不到（别算进收益）

8. **跨平台**：本项目是深度 Windows 绑定（wmi / hidapi / DWM / MSIX），Slint 的跨平台优势用不上。
9. **杀软导致的日志慢（约 21ms/行）**：属磁盘 I/O，与 UI 框架无关，迁移不改善。

## 4. 代价与风险（按严重度分级）

### 严重 —— 可能直接否决

**R1. 中文与 IME 是头号未知项。**
本项目是**纯中文界面**，含 22 个 `<input>` + 1 个 `<textarea>`（设备重命名）+ **快捷键录制**（需捕获按键序列）。
Slint 官方字体文档只说明「字体从系统自动拾取、可 import 自定义 ttf/otf」，
**没有对 Windows 上 CJK 字形回退与 IME 候选框行为给出保证**。
1.18 只提到「读屏软件可读输入框内容」，未提 IME。
→ **必须真机实测**：中文显示有无豆腐块、微软拼音候选框是否跟随光标、快捷键录制能否拿到裸按键。
这一项不过，整个迁移免谈。

**R2. 毛玻璃没有原生对应。**
现有 CSS 用 **8 处 `backdrop-filter`**。Slint 没有等价元素；可行替代是靠 DWM 的
Mica/Acrylic 打底（`window_material.rs` 逻辑可复用，`WindowHandle` 实现了 `HasWindowHandle`，
**能拿到 HWND，这条路是通的**），但**窗内局部毛玻璃需自己画**，视觉上有落差。

**R3. 1.18 才发布 1 天。** 生产项目追首发不合理；建议观察 1.18.x 若干周。

### 中等 —— 增加工时

**R4. 样式全部重写。** 2,372 行 CSS（含 10 处 `box-shadow`、`linear-gradient`、自定义滚动条）
要在 Slint 里重建；`std-widgets` 要出当前观感需写自定义 style。
**R5. 4 个 Tauri 插件要自研替代**：autostart（注册表/启动目录）、global-shortcut（`RegisterHotKey` 或
`global-hotkey` crate）、single-instance（命名互斥量）、window-state（自存位置尺寸）。单个不难，合计约半周到一周。
**R6. 打包链重做。** MSIX 已有自制脚本可复用；**NSIS 目前靠 Tauri bundler，需另找方案**。
**R7. 复杂控件要重建**：settings.html 82 个 id 的表单、5 个页签、5 处右键菜单（Slint 有 `ContextMenuArea`）、
1 处 `MutationObserver`、滚动位置保持（9 处 `scrollTop`）。
**R8. 知识栈切换**：从 HTML/CSS/JS 换到 `.slint` DSL + Rust 回调绑定。

### 轻

**R9.** 若未来想转专有许可，Royalty-free 档仍需履行署名义务。

## 5. 三种路径对比

| | 路径 A：维持现状 | 路径 B：大爆炸全量迁移 | 路径 C（推荐）：先 spike，再决定 |
|---|---|---|---|
| 改动 | 0 | 前端 7,840 + 胶水 2,800 行重写 | 先 1–2 天原型，零改动主仓 |
| 工期 | — | **约 5–8 周**（单人估算） | 1–2 天，之后才有数据决策 |
| 风险 | 无新增 | 高：R1/R2 任一不过即返工 | 低 |
| 中断现有功能 | 无 | 有，且窗口期长 | 无 |
| 适用 | 当前无明确痛点 | 已确证痛点且愿承担重写 | **绝大多数情况** |

**路径 C 的 spike 该做什么**（一个独立 Slint 原型，不碰主仓）：

1. 无边框窗口 + `SystemTrayIcon` + 左键弹窗；
2. 用 `WindowHandle` 取 HWND，把 `window_material.rs` 的 Mica/Acrylic 代码原样套上，确认材质生效；
3. 托盘旁精准定位（复用 `popup.rs` 的 `compute_position` 数学）；
4. **中文渲染 + 微软拼音 IME 候选框 + 快捷键录制按键捕获**；
5. 弹簧动画复刻 popup 的 cubic-bezier(0.62,0,0.32,1) 手感。

第 4 项不过就停。四项全过，再谈迁移范围。

**关于「渐进迁移（Slint 只做 popup，Tauri 继续做 settings）」**：
理论上可把 Slint 窗口放在独立线程跑自己的消息循环，但 Tauri 的事件循环（tao/wry）与 Slint（winit）
在同进程共存**没有查到成熟方案，属未验证项**。若真要走渐进路线，务必先用 20 行代码做共存 spike，
不要写进计划当既定事实。

## 7. 建议

1. **先别动主仓**。当前分支上 P0-4 死锁修复刚落地（`6d37bd4`）、看门狗误报刚修（`32ea860`），
   稳定性正在收敛，此时叠加框架级重写风险叠加。
2. **先回答一个业务问题**：现有用户是否真的被「弹窗慢 / 内存高 / 缺 WebView2」困扰？
   若无实测投诉，路径 A 就是最优解。
3. 若确有痛点，走路径 C，把 §5 的五项 spike 跑完再决策。
4. 若最终决定迁移，**优先重写 popup**（收益最明显、孤立性最好），settings 页（82 个 id 的表单）
   放到第二阶段——它是工时大头，且迁移收益最低。
