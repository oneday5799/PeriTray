## 3. 计划内剩余 · 第三批（8 条）

### P1-7　配置解析失败时整份配置静默重置（**唯一不可逆项**）

- **位置**：`src-tauri/src/config.rs:274`（`init_config`，解析失败分支在 `:281-292`）
- **根因**：解析失败 → 用户全部个性化配置一次性丢失且 UI 无提示；更隐蔽的是**下一次任意写入
  会用默认值覆盖磁盘原文**，原始配置永久不可恢复。
- **改法**：10 个字段**逐字段**补 `#[serde(default)]` / `#[serde(default = "…")]`。
  ⚠️ **绝不可写「其余同理」**——逐字段比对 `Config::default()`（`config.rs:164-176`）后有 **2 个字段
  的默认值不相等**：

  | 字段 | `Config::default()` 实际值 | 裸 `#[serde(default)]` 会得到 | 后果 |
  |---|---|---|---|
  | `hidden_groups` | `vec!["Battery", "Monitor"]` | `vec![]` | 升级后 Battery / Monitor 两组突然出现 |
  | `dedup_devices` | `true` | `false` | 设备去重被静默关闭 |

  这两个字段必须用**具名 helper**。另：解析失败时生成 `.bak` 备份并让前端提示。
- **验证**：① 手工删除 `hidden_groups` / `dedup_devices` 两行 → 重启 → Battery/Monitor 仍隐藏、
  去重仍开启；② 故意写坏 `config.toml` → 生成 `.bak` + 前端有提示；③ 配置往返单测。
- **依赖/风险**：自包含，无依赖；风险**中**。建议排第三批首位。

### P1-8　`ANIMATING` 全局标志无 RAII 保护

- **位置**：`src-tauri/src/popup.rs:102-208`。**两个置位点**：`:145`（`close`）、`:190`（`show`）；
  对应复位 `:157`、`:206`；动画体 `animate_close` / `animate_open`。
- **根因**：动画线程 panic → `ANIMATING` 永久 `true` → 弹窗**再也打不开或关不掉**，只能重启应用。
  报告与主方案原稿的修复块**只给了 `close` 一处**，照此实施后 `animate_open` 的 panic 仍会永久卡死。
- **改法**：复用 `state.rs` 的 `SingleFlightGuard`（CAS），**不新建 `AnimatingGuard`**；
  占用点固定在函数顶部；`spawn_animation(guard, f)` 的守卫是**必需参数**（漏传即编译错误）。
  ⚠️ `Cargo.toml:84` 的 `[profile.release] panic = "abort"` ⇒ **靠 Drop 复位的收益在 release 为空**，
  必须补一条与 profile 无关的兜底：建议**超时自愈**（`ANIMATION_STARTED: AtomicU64`，
  把「永久卡死」改成「最多卡 2 秒」）。
- **验证**：① `grep -c "ANIMATING.store" src-tauri/src/popup.rs` = **0**；
  ② **两条路径各插一次 `panic!()`**（`animate_close`、`animate_open`）确认弹窗仍能再次打开（验证后移除）。
- **依赖**：P3-13 已完成 ✅（守卫已上移 `state.rs`）。风险：低。

### P1-11　`update_config` 全量覆盖导致丢失更新

- **位置**：`src-tauri/src/commands.rs:84-103`、`src-tauri/dist/scripts/settings.js:26-32`
- **根因**：典型 lost update——弹窗重命名设备的**同时**设置页切换开关并 `saveConfig()`，
  若设置页持有的 `config` 快照早于重命名，则**重命名被覆盖丢失**。
- **改法**：三条路线按成本递增（补丁式字段合并 / 乐观锁 revision / 先上线观测打点）。
  ⚠️ **必须复用 P1-3 已落地的机制**：`config.rs` 现有 `persist_if_changed` / `claim_revision` /
  `revision_is_latest` / `PERSIST_LOCK` / `CONFIG_REVISION`——**不要另起一套版本号**。
  同时注意：**P1-3 的版本号只防「后发先至」，不防「两个内容不同但都需要保留」**，后者才是本条的职责，
  两者不可互相替代。
- **验证**：`merge_config` / `check_revision` **纯函数单测** + 双窗口 20 次手测
  （`cargo check` 是类型检查，证明不了并发正确性）。
- **依赖**：P1-3（已完成）。风险：路线 1 需前后端同步改。

### P1-6　`showToast` 与调用方 `<br>` 约定不一致

- **位置**：`src-tauri/dist/scripts/common.js:709-729`（实现）、`:736-745`（调用方）

### B12　panic hook 用**模态 MessageBox** 阻塞 panic 线程（P1-8 验证中实测发现）

- **位置**：`main.rs:39-60` `install_panic_hook` —— 全局 panic hook 里调用
  `show_error_box(&full)`（`MessageBoxW`，**模态**），随后才 `default_hook(info)`。
- **证据（实测，非推断）**：P1-8 的注入验证中，在 `animate_close` 顶部插 `panic!()` 后：
  - 日志出现 `[panic] … @ src\popup.rs:375:5`（hook 自己写的行），
    但**子进程 stderr 为 0 字节**——说明 `default_hook`（会向 stderr 打印
    `thread panicked at …`）**从未执行**，即 hook 卡在 `show_error_box` 上；
  - 该动画线程因此**永不完成栈展开**，`SingleFlightGuard` 的 Drop 不执行，
    `ANIMATING` 一直是 `true`：随后 1.5s 的那次 toggle 直接静默失效
    （日志里只有 `[P1-8TEST] toggle #1`，没有 `[popup] toggle`），
    直到 3.0s 后**超时自愈**把它救回来
    （`[popup] ANIMATING 超时自愈：动画线程疑似已死（已过 3002ms，上限 2000ms），强制放行`）。
- **影响面**：这不是弹窗独有问题——**任何后台线程 panic 都会弹出一个模态框**，
  并让该线程永久挂住（开发/调试构建），或（release 下 `panic = "abort"`）
  弹框后直接终止进程。而 `show_error_box` 的标题写的是
  「外设监控 - 启动失败」，它本意只服务于**启动期失败**，却挂在了全局 hook 上。
- **建议改法（按成本递增，择一）**：
  1. **只对主线程 panic 弹框**：hook 内比对 `std::thread::current().id()` 与
     记录的主线程 id，非主线程只写日志（`standard_log!` + `eprintln!`）不弹框；
  2. 保持弹框但**放到独立线程**且设置 `MB_SERVICE_NOTIFICATION` / 超时自动关闭
     （Win32 原生 MessageBox 无超时参数，需自绘或用 `MessageBoxTimeoutW`）；
  3. 最简：非主线程 panic 直接 `eprintln!` + 日志，不弹框。
- **验证**：在后台线程插 `panic!()`，断言该线程能正常结束（栈展开完成）、
  应用不弹模态框、`ANIMATING`（或任意 RAII 标志）被正确释放。
- **风险**：低（仅影响异常路径）；但**收益明确**——它决定了「后台线程 panic」
  到底是「死一个线程」还是「卡死一个线程 / 整个进程」。
- **✅ 已实施 `c11869e`**：采用方案 1（按线程区分，`PanicSite::of/shows_dialog`），
  并把「弹框动作」抽成可注入参数（`make_panic_hook` + `handle_panic`），
  使单测能用记录器替代 `show_error_box` —— 否则模态框会把测试挂死。
  新增 11 个用例（88→99），含「真装 hook 的后台线程 panic」集成用例。
  可证伪性：判据写反 ⇒ 3 条转红。真实二进制：stderr 由修复前 **0 字节** 变为
  327 字节且含默认 hook 的 `thread '<unnamed>' panicked at`（栈展开确实发生），
  panic 后 5s 进程仍存活。
- **⚠️ 知情副作用**：release 下后台线程 panic 现在会**真的**走到 `abort()`，
  即整个进程终止（此前是「弹框 + 线程僵死 + 进程存活」）。这是
  `panic = "abort"` 的既定语义，也是「快速失败优于带病运行」的选择。

### B14　前端 `config-changed` 整份覆盖本页未落盘的改动（P1-11 实施中新发现）

- **位置**：`dist/scripts/settings.js` 的 `config-changed` 监听

- **现象**：该处理器会**整份替换**设置页的工作副本 `config`。若用户在「刚点了一下开关、

  同一思路：把 payload 当**新基线**、把本地未落盘改动当**补丁**重放一次
  （即 `config = mergeLocal(configBase, config, payload)`）。
- **为什么当时不做**：它改的是**渲染时机**（原来一次整份替换，改后变成「先合并再渲染」），
  与 P1-11 的后端合并语义不是同一个可证伪单元，混在一起提交会让两边的验收互相干扰。
- **风险**：中（前端状态机）；收益：消除一类「点了没反应」的哑故障。

**过程中的四个关键发现**（都会影响后续同类验收，务必先读）

1. **WebView2 的 `TrySuspend` 会让 IPC 静默失效，而 CDP 求值不受影响。**
   popup 窗口隐藏时渲染进程被挂起（日志 `[webview] TrySuspend completed: success=true`）：
   `Runtime.evaluate` 的**同步表达式照常执行**，但**返回 Promise 的表达式永不 resolve**
   ——因为 Tauri IPC 的回包依赖渲染进程的消息循环。**故凡涉及 `invoke` 的 CDP 求值，
   必须先让目标窗口可见**。本次解法：`PM_DEV_OPEN_SETTINGS=1`（应用自带的自动化开关，
   `main.rs::spawn_dev_open_settings`）打开设置窗；popup 则用**第二实例的单实例回调**
   （`popup::open_popup`）唤醒——后者同时就是「用户双击图标」的真实路径。
   ⚠️ 初版探针没意识到这点，把「Promise 不 resolve」误判成「命令挂住」，
   白白多花了一轮排查。

2. **探针自身会制造假阳性，而且形态很隐蔽。**
   首次在 popup 页注册事件收集器时求值超时，我误以为失败；实际**同步部分已执行**，
   监听器**已经注册**。随后重载页面重新注册，于是 popup 页有了**两份**监听器，

   重载页面清空后重测，实得**恰好 1 次**。
   **教训**：`Runtime.evaluate` 超时 ≠ 代码没执行；注册类探针必须先清理旧监听器
   （或重载页面）再测量，否则会把「自己的重复注册」读成「产品的重复投递」。

`retention = once` 时，**第二个实例会删掉主实例正在写的日志**。
- **机制**：`process.rs::should_delete_log` 对 `Once` **无条件返回 true**；
  而「跳过当前正在写的日志文件」的保护只比对**当前进程自己的** `current_name`
  （`log_path()` 按本进程 pid 算），**覆盖不到「同一应用的其他实例」**。
- **触发路径是最高频的用户操作**：双击图标 → 单实例回调 → 新进程启动 →
  `init_config` 阶段 `clean_old_logs()` 把主进程的 `debug_once_{主pid}.log` 删掉。
- **后果**：主进程后续日志写入一个「已从目录删除」的句柄 ⇒ 磁盘有数据但**目录里看不见**，
  用户与排查者都会以为「没有日志」。
- **为什么不在本批修**：⑧-e 的定位是**验收轮**，混入修复会破坏「验收 vs 修复」的边界；
  且修法需先定夺（提前单实例检测 / `Once` 模式跳过非本进程文件 / 删前试锁），
  属独立决策项。**已登记，建议下一轮单独评估。**
- **本次绕行**：把 `log_retention` 临时改为 `one_day`（日期命名 ⇒ 当天文件不会被删），
  验收后已还原为 `once`（`diff` 确认仅此一行与备份不同）。

**修复记录（⑧-f，`cd97845`，独立提交）**

三种候选修法中选了**「删除前做活动性探测」**（而非「提前单实例检测」或
「`Once` 跳过非本进程文件」）：它对 `once` 与按天命名**两种模式都成立**，
且不需要把 `clean_old_logs()` 挪到单实例插件注册之后；另两种各只覆盖一半场景。

- **原理**：Rust 的 `File` 在 Windows 上默认以
  `FILE_SHARE_READ | FILE_SHARE_WRITE | FILE_SHARE_DELETE` 打开 ⇒ 用
  `share_mode(0)`（不共享）打开同一路径，只要已有持有者就必然失败并返回
  `ERROR_SHARING_VIOLATION (32)`。**该前提先独立实测**：本进程持有 / 跨进程持有
  均 raw=32；对照「同样默认共享模式打开」成功 ⇒ 失败确实源于共享位而非权限。
  ⚠️ `kind()` 返回的是 `Uncategorized` 而非 `PermissionDenied`，判据不能只看 `kind()`。
- **实现**：新增 `is_file_in_use`；把清理循环抽成
  `clean_log_dir(dir, retention, current_name, today_days) -> CleanOutcome`
  （抽函数是为了**可测**：`clean_old_logs` 固定作用于 `logs_dir()`，单测无法在不污染
  真实日志目录的前提下验证「删除判据 + 活动性探测」这条接线）；删除前探测为真则
  跳过并记 `[process] 跳过被占用的日志: {name}`。
- **容错方向**：只有 `NotFound` 判「未占用」，其余错误（权限不足、杀软锁、路径异常）
  一律判「被占用」——删除不可逆，误判成被占用只是少清一个文件（下次启动会重试）。
  `once` 语义不变：崩溃进程留下的陈旧文件无人持有，照删。
- **验收（可证伪）**：单测 +5（169 → 174 passed）。两轮注入：① 探测恒 false →
  3 个用例转红，失败信息直指「被另一写入者持有的日志不得被删除」；② 文件名判据改为
  永不匹配 → **恰好 1 个**用例转红、其余全绿 ⇒ 两条防线各自独立可测。
  **真实双实例 E2E**（同一 shell 内保证两实例同时存活）：修复版下 A(pid 31256) 的
  日志幸存且 50416 → 50596 字节**增长**、B 留有跳过记录；注入版重建后 A 的日志
  **被删除** ⇒ 修复是承重的。E2E 顺带把两条原本只靠读码的假设变成观测：主实例
  `LogSink` 确实长期持有句柄；第二实例的 `clean_old_logs()` 确实**先于**单实例插件
  执行（B 随即退出，但仍完成了清理尝试）。
- ⚠️ **E2E 的坑（值得记住）**：第一次把两个实例放在**两次工具调用**里启动，第一个
  进程在调用结束被回收 ⇒ 第二实例删掉的是**无人持有的陈旧文件**——这恰是 `once` 的
  正确语义，却被误读为「修复无效」。**双实例必须保证同时存活**，否则测的是另一条路径。

### 决策 1：P1-7 是否提前 → **提前**

- **可行性**：高。改动自包含在 `config.rs`（10 个 serde 属性 + 2 个具名 helper）+ 前端一处提示；
  无跨模块依赖、无新依赖。
- **对比**：
  - 提前做：消除**唯一不可逆**的用户数据丢失面；代价只是打乱主方案的批次编号（文档里记一句即可）。
  - 不提前：继续暴露在「升级后首次写入即用默认值覆盖磁盘原文」的风险下——**这是全部剩余条目里唯一

- **结论**：提前，排在全部剩余工作之前（已同步修订 §2 的执行顺序）。

### 决策 2：P2-8 是否补 `tauri` test feature + dev-dependencies → **不补**

- **现状**（`commands.rs:251-273`）：`with_config` 读（`:253-262`）与 `with_config_mut` 写（`:264-267`）
  是**两次独立加锁** ⇒ TOCTOU 成立。
- **方案 A（推荐）**：抽
  `fn try_toggle_tray_device(c: &mut Config, name: &str) -> Result<(), String>`，
  把「查重 + 上限判定 + 写入」全放进去；命令侧只留
  `run_blocking(move || config::with_config_mut(|c| try_toggle_tray_device(c, &name)))`。
  - 可行性：**高**。原子性从「靠约定」变成**结构性保证**——函数只拿到 `&mut Config`，
    **物理上无法跨两次加锁**。
  - 可测性：单测直接 `Config::default()` 构造后调用，**不需要 `AppHandle`**。
  - 单测清单：未达上限可加入 / 达上限拒绝且不写入 / 已存在则移除。
- **方案 B（补依赖）**：dev-dependencies 加 `tauri = { version = "2", features = ["test"] }` +
  `mock_app()`。tauri 2.11.5 确有 `pub mod test`（`lib.rs:1098`，`cfg(any(test, feature = "test"))`）。
  - 可行性：中。代价：① 首次给仓库引入 dev-dependencies；② `cargo test` 会以 `test` feature
    编译 tauri（feature 统一），编译时间与行为面变大；③ mock runtime 下窗口/`emit` 行为与真实环境
    不同，对「锁作用域」这条**没有额外价值**；④ 仍然测不到真实并发。
- **结论**：A。B 只在将来需要「窗口/命令级集成测试」时再考虑。

### 决策 3：P3-9 是否改 Rust 枚举 → **分两步，先做集中校验**

- **关键风险（实测）**：现有 `LogRetention` 的 `Deserialize` 对**未知值直接 `Err`**
  （`config.rs:36-39`），而该字段标了 `#[serde(default)]`——`serde` 的 `default`
  **只在字段缺失时生效，字段值解析出错仍会导致整份 `Config` 反序列化失败**。
  也就是说：**把更多字段改成枚举 = 把「整份配置重置」的触发面放大**，
  正是 P1-7 要消灭的那个不可逆故障。
- **方案 A（改枚举）**：可行性中。每个枚举都必须实现「未知值**降级为默认** + 告警日志」，
  否则不能上线；且 `LogRetention` 现有实现**本身就是反例**，要一并修正。
- **方案 B（推荐先做）**：保持 `String`，新增 `fn normalize_config(&mut Config)`
  （在 `init_config` 解析成功后调用），把非法值收敛为默认并记日志；每字段一个非法值的单测。
  - 可行性：高、零风险、可立即单测；**与 P1-7 正交**（一个治「字段缺失」，一个治「值非法」）。
- **结论**：先 B；A 待 P1-7 落地 + 各枚举兜底策略确定后再评估。

### 决策 4：B5 日志改造范围 → **独立写线程 + 有界通道**

- **先澄清一个安全点**：`log_path()` 只读原子量（`LOG_LEVEL` / `LOG_ONCE`，`config.rs:223-224`），
  **不取 CONFIG 锁** ⇒ 在 `with_config` 内打日志**不会**自锁，改造无额外耦合。
- **方案 A（BufWriter）**：可行性高、改动最小（~10 行）；但**锁结构与每行 syscall 不变**，
  锁排队问题不解决，主线程仍可能被其他线程的日志洪峰顶住。
- **方案 B（独立写线程 + `sync_channel`）**：可行性中（~60 行，局限 `process.rs`）。
  - 收益：日志锁从业务路径彻底消失；**探针不再被日志锁污染**（本轮已被坑过一次，见 B10-4）。
  - 代价/风险：① 崩溃时可能丢最后几行 → 必须在 `watchdog_self_restart` 与退出路径**显式 flush**
    （注意 `std::process::exit` **不执行 Drop**，`main.rs:113` 正是这种调用）；
    ② 跨天文件切换与 `log_once` 切换逻辑移到写线程；
    ③ 通道满时策略要明确：**丢弃 + 计数，绝不阻塞**。
- **结论**：B。若想更保守可先 A 再 B，但 A 单独做收益有限。

### 决策 5：B7 watchdog 探活 → **做方案 A**，可选叠加 B

- 要点见 B7 节：**检测本身有效**，问题在**探针线程泄漏**（`getter!` 内层 `rx.recv()` 无超时）
  与恢复慢（≥40s）。
- **A**：探活闭包体内只做 `EVENT_LOOP_TICK.fetch_add(1, …)`，判据仍是「5s 内能否被主线程取走」。
  改动 ~10 行，消除泄漏，可把节奏收紧到 `sleep(3s) + recv_timeout(2s)`；**风险低**（判据语义不变）。
- **B**（缓存 hwnd + `SendMessageTimeoutW`）：~40 行，多一条**不依赖 tauri proxy** 的通道，
  可与 A 叠加。注意：hwnd 必须在主线程启动时缓存（`window.hwnd()` 同样是无超时 `getter!`），
  且弹窗重建后需刷新缓存。
- **C（前端心跳）**：**排除**——弹窗隐藏时 `TrySuspend` 会暂停 JS 定时器 ⇒ 必然误报。
- **结论**：先 A；B 视「是否需要区分事件队列拥塞与主线程僵死」再定。

### 决策 6：B8 防复发断言 → **落地（debug-only）**

- **方案 A（推荐）**：`config.rs` 加 `static CONFIG_LOCK_DEPTH: AtomicUsize`
  （`with_config` / `with_config_mut` 进出 ±1）；`tray.rs` 把菜单/托盘 API 调用收口到 3~4 个薄包装
