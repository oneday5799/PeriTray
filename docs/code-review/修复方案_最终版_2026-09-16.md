### 1.3 每批的通用回归闸门

每批完成后必须全部通过，缺一不可：

```bash
cd src-tauri && cargo fmt --check          # 格式
cd src-tauri && cargo check                # 必须零 warning（pre-commit 强制）
cd src-tauri && cargo test                 # 当前基线 59 passed / 0 failed
node tools/check.mjs                       # 前端 6 类校验
```

> 之所以强调「零 warning」：`AGENTS.md:31/:101/:167` 要求 `cargo check` 零警告并由 pre-commit 钩子强制拦截。**P0-1 之所以能进仓库，正是「用下划线消掉告警」绕过了这道闸门**——第零批先修 P3-14，就是为了**让这道闸门重新有效**。`【第二十六轮复核修正】`⚠️ **但要说清楚「重新有效」到什么程度**：P3-14 恢复的是「**命名正确时** `cargo check` 会告警」这条通道，**不是**一条能自动发现「守卫未被持有」的检查——后者属**报告 P3-8 明列的「已知无法覆盖」**。也就是说，闸门是否真的拦住，**取决于下一个人是否遵守命名约定**；而「是否遵守」没有任何机械检查。**不要把「约定已写入文档」当成「闸门已闭合」。**

> `【第二十一轮复核修正】`⚠️ **本节原称「验收闸门」，用词有误，已改为「回归闸门」。这个区别很要紧。**
>
> **这四道闸门全部是「编译 / 格式 / 结构」级的，没有一道能证明「缺陷已消除」。** 已实测其中最容易误解的一道——`cargo test`：
>
> | 事实 | 数值 | 依据 |
> |---|---|---|
> | 全仓测试总数 | **59** | 与第六轮实测的「59 passed」一致 |
> | 其中位于 `wireless_24g/drivers/**` 的 | **36** | 而报告第八章**明确声明该目录不在审查范围内**（「`wireless_24g/drivers/` 协议实现……未扩展覆盖」） |
> | 位于受审模块的 | **23** | 全部是**纯函数测试**：`persist.rs` 的序列化往返/坏 JSON/过期淘汰、`mod.rs` 与 `bluetooth.rs` 的 `apply_*_` 合并逻辑、`xinput.rs` 的电平映射、`device_data.rs` 的键合并、`audio_spatial.rs` 的 GUID 解析 |
> | **位于「含 40 条发现」的 15 个文件中的** | **0** | 逐个核查 `tray.rs` / `commands.rs` / `config.rs` / `main.rs` / `update.rs` / `popup.rs` / `shortcut.rs` / `process.rs` / `windows.rs` / `app_icon.rs` / `battery_notify.rs` / `audio_notify.rs` / `audio.rs` / `webview.rs` / `state.rs` —— **全部 0 个 `#[test]`** |
>
> **即：`cargo test` 与 40 条发现零交集。** 它在**修复之前就已经全绿**（第六轮实测 59 passed），因此**它在修复之后也必然全绿**——**这是一条恒真的验收标准，它不可能失败，也就不可能证明任何事。** 同理：`cargo fmt --check` 只在格式错时失败，`cargo check` 只在编译错时失败，`node tools/check.mjs` 只在动了前端且引用/语法出错时失败。
>
> **结论与正确用法**：
> - 这四道闸门的作用是 **「确认没改坏」**（回归），**不是「确认改对了」**（验收）。方案原先把它们称作「验收闸门」，会让实施者产生「通过 = 这批修好了」的错觉——**而实际上通过只意味着「编译过、格式对、没碰坏前端」**。

### 1.5 统一技术约定（全方案唯一权威声明）

**为什么单列这一节**：本方案曾在两节里对同一个东西给出**互斥处方**（§4.6 禁止新建守卫类型，§5.3 却自建一个 `AnimatingGuard`）。**为避免重演，全方案涉及以下六项的表述一律以本节为准，其余各处只引用、不重述。**

**① 单飞守卫：复用 `SingleFlightGuard`，不新建类型。**
- 唯一的守卫类型是 `crate::state::SingleFlightGuard<'a> { flag: &'a AtomicBool }`（**P3-13** 把它从 `bluetooth.rs:519-541` / `wireless_24g/mod.rs:44-71` 上移到 `state.rs`，并加 `pub(crate)`）。
- **禁止**再定义 `ForceGuard` / `AnimatingGuard` 等语义相同的类型（避坑清单第 2 条）。
- 目标 flag 需为 `pub static AtomicBool`（如 `state.rs:33` 的 `ANIMATING`、`bluetooth.rs` 的 `BT_BATTERY_REFRESHING`）。

**② 占用点固定在函数顶部。**
- 守卫必须在**函数顶部**取得：`let Some(guard) = SingleFlightGuard::new(&FLAG) else { return };`
- **不允许**把占用推迟到 `std::thread::spawn` 那一行——否则 `resume_webview` / `set_size` 等**窗口操作会在无守卫状态下执行**（§5.3 的「占用点对照表」）。
- 需要「唯一出口」时用 **`fn spawn_animation<F>(guard: SingleFlightGuard<'static>, f: F)`**：**守卫作必需参数**，漏传即 `error[E0061]`（**类型级拦截，不是 lint 提醒**）。

**③ 「必须被持有」无法用 lint 表达。**
- `#[must_use]`、命名约定、下划线规则**都拦不住** `let _ = f();`（**已实测**：`Option<#[must_use] T>` 作裸语句不告警；`let _ = f()` / `let _g = f()` 亦被抑制）。
- 可靠的只有**结构约束**：把守卫做成某个函数的**必需参数**。
- 因此 **P3-14 的命名约定只是「约定层」护栏，不是自动拦截**（详见 §二 的「P3-14 到底恢复了什么」对照表）。

**④ 失败路径回滚约定（原「专题 B 共用小工具」的最终裁定）。**
- **裁定：撤回「抽一个共用代码小工具」这一承诺。** 理由——三条的机制**并不同族**：

  | 条目 | 机制 | 结论 |
  |---|---|---|
  | **P0-2** | CAS 置位 + **RAII 守卫**（作用域退出即复位） | 复用 `SingleFlightGuard` 即已解决，**无需额外工具** |

  | **P2-12** | **无原子量**，只是「先判 `Result` 再 `insert`」的顺序调整 | 与前两者**不同族**，无法共用 |

  **强行共用会违反 ①「不新建类型」，或造出一个三条都不用的空壳**（这正是避坑清单第 29 条记录的坑）。
- **改为共用一个「规范条目 + 评审检查项」**——这是真正可共用、且**可直接执行**的部分：
  - **写入 `AGENTS.md`**：「**失败路径不得留下成功状态**——凡「先置位 / 先记录状态、后续步骤可能失败」的代码，必须在失败分支显式回滚，或用 RAII 守卫保证作用域退出即复位。」
  - **评审检查项**（列入 `AGENTS.md` 的 code review 清单）：「**这个置位有回滚吗？**」——对每处 `compare_exchange` / `store(true)` / `registered.insert` 都问一遍。
- **落地位置**：§3.2（P0-2）、§4.7（P3-12）、§5.7（P2-12）三条**各自独立执行、互不依赖**；本节只保证它们**遵守同一个原则**。
- （若日后确实需要代码化，**唯一合规形态是自由函数**，如 `fn rollback_on_fail(flag: &AtomicBool, ok: bool)`——**不得引入新类型**。）

### 3.1 P0-1　单飞守卫未随工作线程释放

**位置**
- `src-tauri/src/wireless_24g/mod.rs:198-214`（`snapshot`）
- `src-tauri/src/bluetooth.rs:653-670`（`enqueue_bt_refresh`）

**问题**：变量名为 `_guard` 且**在闭包体内从未被引用**，因此 `move` 闭包不会捕获它；未被使用的 `_guard` 在函数返回时立即 Drop，而不是在工作线程结束时——**单飞语义退化为无保护**。

**改法（方案 A-1，推荐）**

```rust
// 方案 A-1：把外层绑定改名（语义最清晰，且恢复编译器护栏）
let Some(guard) = SingleFlightGuard::new(&REFRESHING) else { /* 已有刷新在跑 */ return result; };
std::thread::spawn(move || {
    let _guard = guard;          // 显式引用 → 触发捕获，随线程结束 Drop
    refresh_worker(stale);
});
```

**备选（方案 A-2，可行但易读性差）**

```rust
let Some(_guard) = SingleFlightGuard::new(&REFRESHING) else { /* 已有刷新在跑 */ return result; };
std::thread::spawn(move || {
    let _guard = _guard;         // RHS 指外层绑定 → 触发捕获
    refresh_worker(stale);
});
```

> ❌ **不要照抄原稿的「方案 A」**：原稿写 `let _guard = guard;` 但外层绑定名是 `_guard`（无 `guard` 变量），`rustc 1.96.0` 报 `error[E0425]: cannot find value 'guard' in this scope`。**必须用上面的 A-1 或 A-2。**

**改法（方案 A-3，把护栏从「lint」升级为「类型错误」——比 A-1 更强，建议一并采纳）**

A-1/A-2 的护栏仍然是 **lint**：它依赖 `unused_variables` 恰好落在「外层绑定」上。若日后有人写成 `let _single_flight = SingleFlightGuard::new(..)`（具名但不引用），告警同样会消失——**P3-14 的坑会以另一种命名形式复发**。A-3 从根上堵住：**让守卫成为工作函数的参数**，于是「必须被持有」由类型系统保证。

```rust
// 工作函数签名多接一个守卫（仅承担 Drop，参数名带下划线是正确写法）
fn refresh_worker(stale: bool, _guard: SingleFlightGuard<'_>) { /* 原函数体不变 */ }

// 调用点：守卫随参数移入线程，线程结束才 Drop
let Some(guard) = SingleFlightGuard::new(&REFRESHING) else { return result; };
std::thread::spawn(move || {
    refresh_worker(stale, guard);
});
```

**已实测**（`rustc 1.96.0`）：该写法**零告警**通过；而一旦漏传守卫（`refresh_worker(stale)`）会直接得到硬错误——`error[E0061]: this function takes 2 arguments but 1 argument was supplied ... argument #2 of type 'SingleFlightGuard<'_>' is missing`。**即：忘记持有守卫不再是「少一条 lint」，而是编译不过。**

> 取舍：A-3 需改 `refresh_worker` 的签名（`wireless_24g/mod.rs:371` 与 `bluetooth.rs` 对应 worker 各一处），改动面比 A-1 略大。若只想最小改动，用 A-1；**若想让这类缺陷不再复发，用 A-3**。两者可叠加（A-3 之下 A-1 的改名仍建议保留，便于阅读）。

**为何首选 A-1**：它不仅修好缺陷，还**恢复了编译器的回归保护**——日后若有人再删掉闭包内对守卫的引用，`unused_variables` 会立刻报警。（若采纳 A-3，这一层保护由类型系统接管，更彻底。）

**已核实无副作用**：后台线程体 `refresh_worker`（`wireless_24g/mod.rs:371-393`）只调用 `query_and_cache` / `notify_battery_changed` / `persist::flush`，**不触碰 `REFRESHING`**，故修复后标志被正常持有至线程结束**不会造成自我阻塞**。

**两处都要改**：`wireless_24g/mod.rs:198-214` 与 `bluetooth.rs:653-670`。

**验证**
1. `cargo check` 零告警（若忘改闭包内引用，A-1 会立刻报 `unused variable`）。
2. 手动：连续快速触发多轮设备刷新，观察日志中**不出现**两个 `refresh_worker` 并发区间（修复前会出现）。

**回归风险**：低。唯一风险是「闭包内引用写错」——A-1 的编译器告警会直接拦住。

### 4.1 P0-3　手写 COM 回调对象引用计数错误

**位置**：`src-tauri/src/webview.rs:95-158`（`mod try_suspend_cb`）

**问题**：`add_ref` 恒返回 1 而不递增，`release` 无条件 `Box::from_raw`。**只有 Release 恰好被调用一次时才是正确的**，这依赖 WebView2 运行时对完成回调「AddRef 一次 / Release 一次」的配对方式。风险是**双重释放**（堆破坏 / use-after-free），且该路径**每次关闭弹窗都执行**（`popup.rs:349-357` 的 `animate_close` → `popup.rs:356` → `webview::suspend_webview`，定义于 `webview.rs:163`）。

**改法（推荐，本批实施）**：**保留手写对象，把它补成一个契约合规的 COM 对象**——① 真实引用计数；② 修 `qi` 的 `IID_IUnknown` 契约违反（见下）；③ 同步更新 `create()` 的初始化。三处必须一起改，只改引用计数会留下一个「计数正确但仍非合规 COM 对象」的半成品。

```rust
// ① Obj 增加引用计数成员
#[repr(C)]
pub struct Obj { vtable: *const Vtable, refs: AtomicU32 }

// ② add_ref / release 改为真实计数
unsafe extern "system" fn add_ref(this: *mut Obj) -> u32 {
    unsafe { (*this).refs.fetch_add(1, Ordering::Relaxed) + 1 }
}
unsafe extern "system" fn release(this: *mut Obj) -> u32 {
    let n = unsafe { (*this).refs.fetch_sub(1, Ordering::Release) } - 1;
    if n == 0 { unsafe { drop(Box::from_raw(this)) }; }
    n
}

// ③ qi 必须让 IID_IUnknown 成功（并 AddRef），否则不是合规 COM 对象
unsafe extern "system" fn qi(
    this: *mut Obj,
    iid: *const windows_sys::core::GUID,
    out: *mut *mut core::ffi::c_void,
) -> i32 {
    // IID_IUnknown = {00000000-0000-0000-C000-000000000046}
    const IID_IUNKNOWN: windows_sys::core::GUID =
        windows_sys::core::GUID::from_u128(0x0000_0000_0000_0000_C000_0000_0000_0046);
    unsafe {
        if !iid.is_null() && *iid == IID_IUNKNOWN {
            add_ref(this);                       // QI 成功必须 AddRef
            *out = this as *mut core::ffi::c_void;
            0                                    // S_OK
        } else {
            *out = core::ptr::null_mut();
            -2147467262                          // E_NOINTERFACE
        }
    }
}

// ④ create() 必须初始化 refs（原稿未给出，照抄会漏）
pub fn create() -> *mut core::ffi::c_void {
    let obj = Box::new(Obj { vtable: &VTABLE, refs: AtomicU32::new(1) });
    Box::into_raw(obj) as *mut core::ffi::c_void
}
```

并补一条注释说明**初始引用计数归属**（谁创建、谁释放），避免后续再次误改。

> ✅ **本改法已实测**：`rustc 1.96.0` 编译零告警；`create → add_ref(→2) → release(→1) → release(→0)` 运行通过（含 `Box::from_raw` 恰在计数归零时发生）。
>
> ⚠️ 若只改 `add_ref`/`release` 而**漏掉 `create()` 的 `refs` 初始化**，会得到 `refs = 0` 的未初始化计数——这是本改法最容易漏的一步。

**改法（备选，愿意增加一个依赖时）**：加入 `webview2-com = "0.38"`（**与现有 `webview2-com-sys = "0.38"` 同版本，已在本地 registry 缓存中，可离线构建**），删除整个 `try_suspend_cb` 模块，改用上游现成的完成回调封装：

```rust
use webview2_com::TrySuspendCompletedHandler;

let handler = TrySuspendCompletedHandler::create(Box::new(
    move |_result: windows_core_061::Result<()>, is_successful: bool| {
        standard_log!("[webview] TrySuspend completed: success={}", is_successful);
        Ok(())
    },
));
wv3.TrySuspend(&handler)?;
```

依据：`webview2-com-0.38.2/src/callback.rs:482` 的 `#[completed_callback] pub struct TrySuspendCompletedHandler(ICoreWebView2TrySuspendCompletedHandler, HRESULT, BOOL);` 会生成 `create(...) -> ICoreWebView2TrySuspendCompletedHandler`。**代价**：该 crate 依赖 `windows = "0.61"`（7 个 feature）与 `windows-core = "0.61"`，会给依赖图再添一份 `windows 0.61`；闭包签名里的 `Result` 属 windows-core 0.61（即仓内 `windows_core_061::Result`），**与仓内主用的 0.62 不是同一个类型**，需在注释中说明，否则后续易混。若团队接受这两个代价，这是**代码量最小、且由上游维护**的路线。

> ❌ **不要按原稿的「首选」改用 `implement!` 宏——经实测该路线在本仓不可行。** 原稿写「`webview2-com-sys` 与 `windows-core-0.61` 同基座，**可直接复用**」，这个「直接复用」正是做不到的地方。第十六轮复核用真实 crate 做了离线构建复现（依赖与仓内完全一致：`windows-core = "0.62"` + `windows-core-061` + `webview2-com-sys = "0.38"`）：
>
> ```
> error[E0277]: the trait bound `ICoreWebView2TrySuspendCompletedHandler:
>               windows_core::Interface` is not satisfied
> note: there are multiple different versions of crate `windows_core` in the dependency graph
>   --> windows-core-0.62.2/src/interface.rs:14:1  this is the expected trait
>   --> windows-core-0.61.2/src/interface.rs:14:1  this is the found trait
> ```
>
> 根因：`implement!` 宏**硬编码** `::windows_core::` 路径（`windows-implement-0.60.2/src/lib.rs:150` 的 `<#ident as ::windows_core::Interface>::Vtable`，全文共 15 个硬编码路径：`ComObject` / `ComObjectInterface` / `AsImpl` / `IUnknownImpl` / `IInspectable_Vtbl` / `GUID` / `HRESULT` / `imp` 等），且**宏不支持指定 crate 路径**（`ImplementAttributes` 仅解析接口名、`TrustLevel(..)`、`Agile(..)` 三类 token）。而本仓把 **0.62** 命名为 `windows_core`（`Cargo.toml:24`）、把 0.61 改名为 `windows_core_061`（`Cargo.toml:27`），因此宏生成的 `::windows_core::` 一律指向 **0.62**，与 `webview2-com-sys-0.38.2/src/bindings.rs:37212` 要求的 `windows_core::IUnknownImpl`（0.61）**不是同一个 trait**。**无论 `use windows_core::implement;` 还是 `use windows_core_061::implement;` 都一样失败**——两个版本的 windows-core 依赖的是**同一份** `windows-implement 0.60.2`（`windows-core-0.61.2/Cargo.toml:45` 与 `0.62.2/Cargo.toml:44`），宏体完全相同；本仓 `Cargo.lock:5341-5342` 亦只有**一条** `windows-implement 0.60.2`，而 `windows-core` 有 0.61.2 与 0.62.2 **两条**——与上述判断一致。
>
> 已实测：把依赖改成 `windows_core = { package = "windows-core", version = "0.61" }`（即让 `windows_core` 就是 0.61）后**编译通过**——这反证了「`::windows_core::` 必须等于 0.61」才是宏路线的前提。但该前提与本仓现状**直接冲突**：`audio_notify.rs:12` 的 `use windows_core::implement;` 服务的是 `windows 0.62` 的接口（`IAudioEndpointVolumeCallback` 等），一旦把 `windows_core` 改成 0.61，那三处 `#[implement(...)]` 会以同样方式失败。`Cargo.toml:24-26` 的注释已明确「**rename 共存，勿合并**」，故**不能**通过改名解决。
>
> 唯一能让 `implement!` 生效的结构性办法是**把 `try_suspend_cb` 挪进一个只依赖 windows-core 0.61 的私有子 crate**（在那里 `windows_core` 就是 0.61）——为一个 4 行回调引入新 crate 与 workspace 改造，性价比明显低于上面的「推荐」改法，故不采纳。

**验证**
1. `cargo check` + `cargo test`。
2. 反复开关弹窗（100+ 次）观察是否崩溃；建议在 Debug 下开 `pageheap`（`gflags /p /enable PeriTray.exe /full`）跑一轮，可显著提高双重释放的暴露率。
3. 走「推荐」改法时，确认 `TrySuspend` 的 `Err` 分支（`webview.rs:195-198` 的 `try_suspend_cb::destroy(cb_ptr)`）语义仍成立——改用真实计数后，`destroy` 与 runtime 的 `release` 可能**双重释放**，需二选一：要么保留 `destroy` 并让 `create` 的初始计数归属调用方，要么把 `destroy` 改为 `release`（并让 `create` 返回计数为 1、由调用方持有）。**这是本次改动中最容易出错的一处，必须与 `add_ref`/`release` 的计数约定一起想清楚。**

**回归风险**：中。这是全仓 149 处 `unsafe` 中风险最集中的一处，改动需配合实测。

> ⚠️ **本条的「双重释放是否真实可触发」仍未闭合**——静态审查无法定论，需运行应用走 `TrySuspend` 错误分支，或观察 WebView2 内部 AddRef/Release 配对。见 §八。**注意：该未闭合项不因改走哪条路线而消失**——「推荐」改法只是让计数与 QI 契约变正确，是否真有第二条 Release 路径仍需实测确认。

### 4.4 P1-3　`with_config_mut` 在持有配置锁期间执行同步磁盘 I/O

**位置**：`src-tauri/src/config.rs:329-366`

**问题**：`sync_all()` 强制落盘，机械盘/受控磁盘/杀软实时扫描场景下可达数十毫秒；期间所有 `with_config` 读取者（托盘 tooltip、设备查询、电量通知、快捷键分发、看门狗探活）全部阻塞在配置锁上。

**改法**：保留原子写入，把 I/O 移出锁。

```rust
pub fn with_config_mut<F, R>(f: F) -> R {
    let (result, snapshot) = {
        let mut guard = lock_unpoisoned(CONFIG.get().expect("Config not initialized"));
        let result = f(&mut guard);
        sync_log_cache(&guard);                       // 缓存同步留在锁内（纯内存，微秒级）
        (result, toml::to_string_pretty(&*guard).ok())
    };                                                // ← 锁在此释放
    if let Some(content) = snapshot { persist_if_changed(content); }   // 脏检查 + 落盘在锁外
    result
}
```

> ⚠️ **`persist_if_changed` 是方案新引入的辅助函数，当前并不存在**（`config.rs` 无任何 `persist*` / `write_config*` / `save_config*` 函数，现有落盘逻辑内联在 `with_config_mut` 中）。**照抄无法编译**，需一并实现该函数（含脏检查）。同理 `sync_log_cache` 的现状需核对。

> ⚠️ **必须重新审视脏检查缓存的并发语义**：`LAST_CONFIG_CONTENT` 当前是在锁内读写的；落盘移出锁后，建议改为 `Mutex<String>` 独立保护并**在锁外串行化落盘**，避免两次并发写入**交错覆盖**。

> `【第二十七轮复核修正】`**⚠️ 上面只说了「串行化」，而串行化并不解决「乱序」——必须补上版本号比对。** 落盘移出锁后会出现这个交错：调用 A 先取到内容、调用 B 后取到内容，但 B 的落盘先完成、A 的后完成 → **磁盘上留下 A 的旧内容**（A 的内容版本更早，却最后写）。**串行化只保证「不交错」，不保证「按版本顺序」**。因此本条的改法**必须**包含（这是 §八.1 第 3 条要求的「必须一并处理」，第二十七轮已把它落到本节）：
>
> ```rust
> // 落盘在锁外串行化（独立 Mutex），且用「内容版本号」拒绝过期写入
> static PERSIST_LOCK: Mutex<()> = Mutex::new(());
> static CONFIG_REVISION: AtomicU64 = AtomicU64::new(0);
>
> fn persist_if_changed(content: &str) {
>     let rev = CONFIG_REVISION.fetch_add(1, Ordering::SeqCst) + 1;
>     let _serial = lock_unpoisoned(&PERSIST_LOCK);   // 串行化：不交错
>     if rev != CONFIG_REVISION.load(Ordering::SeqCst) {
>         return;                                      // 已被更新的写入超越 → 丢弃本次（防乱序覆盖）
>     }
>     // …原有的脏检查 + File::create/write_all/sync_all/rename…
> }
> ```
>
> **⚠️ 上面是示意片段，`CONFIG_REVISION` 与 `persist_if_changed` 都是本条新引入的符号（当前不存在），照抄无法编译。** 落地时还需注意：`fetch_add` 取号必须**在取到内容之后、进入串行区之前**，否则版本号与内容不对应；且该判据只防「后发先至」，**不防「两个写入内容不同但都需要保留」**——后者属 P1-11（防覆盖）的职责，两条不可互相替代（这也正是 §1.2 把 P1-3/P1-11 归入同一专题的原因）。

**验证**
1. `cargo check` + `cargo test`。
2. 手动：连续快速切换多个设置开关，观察 UI 是否仍卡顿（修复前会有明显顿挫）。
3. **并发回归**：模拟两个来源同时写配置（设置页 + 弹窗重命名），确认最终磁盘内容包含两者——**这一步同时是 P1-11 的前置验证**。
4. `【第二十七轮复核修正】`**乱序专项（针对本节新增的版本号比对）**：把两次 `persist_if_changed` 的**串行区入口**人为错开——在第一次调用的串行区**之前**插入 `sleep(300ms)`，使「先取号者后落盘」必然发生；**修复前**（无版本号判据）磁盘上留下的是**较早取号的那份内容**（旧内容覆盖新内容），**修复后**该写入被 `rev != CONFIG_REVISION` 判据丢弃、磁盘保留**最新**内容。**这是一条能区分修复前后的注入式验证**（参照 §6.2 对时序类缺陷的一贯要求：不要指望手测命中竞态）。

**回归风险**：**中高**。这是本批中结构改动最大的一条；落盘移出锁后若串行化没做好，可能引入**落盘乱序**（后发起的先落盘、先发起的后落盘）。见 §八.1 第 3 行。`【第二十七轮复核修正】`**该风险现已在本节「改法」与「验证」中就地闭合**（版本号比对 + 第 4 条的注入式专项验证），**不再只是「指向 §八.1」**——原稿只把要求放在未闭合项表里，实施者按本节改法做出来的正是 §八.1 判为不足的东西。

### 4.5 P1-4 + P1-10　`open_url` 白名单 + CSP + 收窄 capabilities（同一批）

**位置**

**改法 1：`open_url` 加白名单（保留属性与签名）**


### 4.6 P1-5　`set_hotkey_config` 先注销旧键再校验新键

**位置**：`src-tauri/src/commands.rs:408-450`

**问题**：分支 3（新键无法解析）时旧键已注销、`config` 仍保留旧键 → **配置与实际注册状态不一致**，前端显示「已设置 XX 快捷键」但按键无反应，且 `config-changed` 不广播，用户无从察觉。

```rust
#[tauri::command]
pub fn set_hotkey_config(app: tauri::AppHandle, action: String, key: Option<String>) -> Result<(), String> {
    // ① 只做校验，不做任何副作用
    let new_sc = match &key {
        Some(k) => {
            let sc = parse_shortcut(k)?;                        // 解析失败：状态零变化
            if app.global_shortcut().is_registered(sc.clone()) {
                return Err("快捷键已被占用".to_string());         // 被占用：状态零变化
            }
            Some(sc)
        }
        None => None,
    };

    // ② 校验全部通过后，才执行「注销旧 → 注册新 → 落配置」
    let prev = config::with_config(|c| /* 取旧键 */);
    if let Some(pk) = prev { if let Ok(sc) = parse_shortcut(&pk) { let _ = app.global_shortcut().unregister(sc); } }
    if let Some(sc) = new_sc {
        app.global_shortcut().on_shortcut(sc, move |...| { ... }).map_err(|e| e.to_string())?;
    }
    set_config_key(&action, key);
    ...
}
```

**一并做**：把 `on_shortcut` 的错误从 `let _ =` 改为向上传播，让前端能提示「注册失败」。

> 需改的是 **`shortcut.rs:81-88` / `:104-111`** 两处（`commands.rs:437-444` 本已是 `.map_err(...)?` 向上传播，无需改）——见 P2-12。

**另注**：`commands.rs:434-436` 在**注册尝试之前**就打印 `"[hotkey] registered {} {}"`，若随后失败日志会与事实相反。**建议把该日志移到成功之后。**

### 5.3 P1-8　`ANIMATING` 全局标志无 RAII 保护

**位置**：`src-tauri/src/popup.rs:102-208`

**问题**：动画线程 panic → `ANIMATING` 永久为 `true` → 弹窗**再也无法打开或关闭**，只能重启应用。

`【第十七轮复核修正】`⚠️ **本条有「置位」两处，不是一处**——`ANIMATING.store(true, …)` 出现在 **两个**函数里，失败模式完全相同：

| 置位点 | 复位点 | 动画体 |
|---|---|---|
| `popup.rs:145`（`close`） | `:157` | `animate_close` |
| **`popup.rs:190`（`show`）** | **`:206`** | **`animate_open`** |

原稿（报告与本方案）的修复块**只给了 `close` 一处**——照此实施后，**`animate_open` 的 panic 仍会永久卡死弹窗**，正是本条要消除的那个症状。注意报告自己的「潜在影响」段写的是「**`animate_close` / `animate_open`** 内部调用 `window.set_position`…若其中任一环节 panic」，即**报告已知道有两条路径，但「改进建议」只覆盖了一条**（与 P0-3 遗漏 `qi` 属同一类跨节丢失）。

**改法（两处都要改）**

`【第二十四轮复核修正】`**不要新建 `AnimatingGuard`——复用 `SingleFlightGuard`。** 原稿在这里定义了 `struct AnimatingGuard` + `acquire()` + `Drop`，但：

- **它与 §4.6（P3-13）的处方直接冲突**——§4.6 与避坑清单第 2 条明写「**不要引入新类型 `ForceGuard`**……它新引入了**第三种守卫类型**，而**同文件已有语义完全相同的 `SingleFlightGuard`**；两个 Drop 守卫并存与 `AGENTS.md` 的「统一收口」倾向相悖」。
- **`AnimatingGuard` 是 `SingleFlightGuard` 的严格特例**：`SingleFlightGuard<'a> { flag: &'a AtomicBool }` 的 `new(flag)` 对**任意** `AtomicBool` 做同一套 CAS；`AnimatingGuard::acquire()` 只是把 flag 硬编码成 `ANIMATING`。**同一个方案里，§4.6 刚以「已有同语义类型」为由否掉一个新守卫，§5.3 又造了一个。**
- `ANIMATING` 本就是 **`pub static AtomicBool`**（`state.rs:33`），天然满足 `SingleFlightGuard::new` 的 `&'static AtomicBool` 参数。

**并且这一步会连带解决一处判据矛盾**：`AnimatingGuard` 的 `Drop` 定义在 `popup.rs` 内，所以 `grep -c "ANIMATING.store" src-tauri/src/popup.rs` 修复后**必然残留 1**（见下）；改用位于 `state.rs` 的 `SingleFlightGuard` 后，`popup.rs` 的 `ANIMATING.store` **归零**，本节与 §6.3 原本写的「应为 0」**重新成立**。

```rust
use crate::state::{ANIMATING, SingleFlightGuard};   // 复用 P3-13 上移后的项目级守卫

// ① close（popup.rs:145 的 store(true) 与 :157 的 store(false) 一并删除）
fn close(window: &tauri::WebviewWindow, target_x: f64, target_y: f64, start_y: f64) {
    let Some(guard) = SingleFlightGuard::new(&ANIMATING) else { return };  // 原子占用（函数顶部）
    // …place_below_taskbar 与位置计算保持不变…
    let win = window.clone();
    spawn_animation(guard, move || animate_close(&win, cx, cy, start_y));
}

// ② show（popup.rs:190 的 store(true) 与 :206 的 store(false) 一并删除）
fn show(window: &tauri::WebviewWindow, /* …原参数… */) {
    let Some(guard) = SingleFlightGuard::new(&ANIMATING) else { return };  // 同样在顶部
    // …resume_webview / set_memory_usage_target / set_size / set_position / show 保持不变…
    let win = window.clone();
    spawn_animation(guard, move || animate_open(&win, target_x, start_y, target_y));
}

/// 唯一出口：守卫是**必需参数**——漏传即 `error[E0061]`；闭包内显式持有，随线程结束释放
fn spawn_animation<F: FnOnce() + Send + 'static>(guard: SingleFlightGuard<'static>, f: F) {
    std::thread::spawn(move || {
        let _guard = guard;
        f();
    });
}
```

> `【第二十四轮复核修正】`**顺序依赖**：本改法要求 `SingleFlightGuard` 已是**项目级可导入**的符号，即 **P3-13 必须先完成**（把它从 `bluetooth.rs` 上移到 `state.rs` 并加 `pub(crate)`）。现排期中 P3-13 在**第一批**、P1-8 在**第三批**，**顺序已满足**；但请勿把 P1-8 提到第一批之前。
>
> **次序注意**：`SingleFlightGuard::new` 用 `SeqCst`，而现网代码在 `close`/`show` 里用的是 `Relaxed`（`popup.rs:145/157/190/206`）。改用守卫后**写侧统一为 `SeqCst`（更严）**；调用方 `toggle` / `open_popup` / `close_popup` 顶部的 `ANIMATING.load(Ordering::Relaxed)` 保持不变即可——它们现在退化为**提前返回的优化**，真正的互斥由 CAS 保证。

> **两处都必须显式 `let _guard = guard;`** 把守卫移入闭包——否则会重演 P0-1 的缺陷。**这里的下划线是正确的**（内层绑定，仅承担 Drop），不要按 P3-14 的规则误改。
>
> **落地后必须核对**：`grep -c "ANIMATING.store" src-tauri/src/popup.rs` 应为 **0**（两个置位点、两个复位点共 4 处全部被守卫取代）。若仍是 2，说明漏改了 `show`。
>
> `【第二十四轮复核修正】`**这条判据的期望值随上文的改法一起变，请注意**：① **采用本文的 `SingleFlightGuard` 改法 → 期望值 0**（守卫与 `Drop` 都在 `state.rs`，`popup.rs` 里不再有任何 `ANIMATING.store`），**「若仍是 2」这个诊断阈值也成立**（只改 `close` = 删 2 处 → 剩 2）。② 若你**坚持**原稿的 `AnimatingGuard` 写法（`Drop` 定义在 `popup.rs` 内），则期望值是 **1**、且「漏改 `show`」的签名是 **3**（删 2 加 1）——第二十二轮据此把 §6.3 的对应行改成了 1，**那个改动只在「保留 `AnimatingGuard`」的前提下成立**。本轮已按 ① 统一：**§5.3 与 §6.3 都写 0**。
>
> `【第二十四轮复核修正】`**一处此前只改了一半的地方（本轮补齐）**：第二十二轮发现「§6.3 要求该计数为 0、与修复代码块冲突」时，**只改了 §6.3 的派生副本，漏改了本节（源头）**——本节 `:775` 与 `:780` 当时仍写着「应为 0」「若仍是 2」，与 §6.3 的「应为 1」**互相矛盾**。**这正是第十七轮「P1-8 的修复只覆盖 `close`、遗漏 `show`」的失效模式，在「验证文本」上复发了一次**：同一个问题在两处出现，只改了一处。本轮通过「采纳 `SingleFlightGuard` 改法」使两处**同时回到 0**，矛盾自然消解；但教训是——**改判据时要沿引用链找到全部副本**。

**附带收益**：`toggle` 中「读 → 计算 → 写」的 check-then-act 竞态（P3-6）一并解决。

**验证**
1. `cargo check`；`grep -c "ANIMATING.store" src-tauri/src/popup.rs` = **0**（`【第二十四轮复核修正】`**期望值 0 与上文 `SingleFlightGuard` 改法配套**；若改用原稿的 `AnimatingGuard` 则为 1，见上）。
2. 手动：**两条路径各测一次**——① 在 `animate_close` 内临时插 `panic!()`，确认弹窗仍能再次打开；② **在 `animate_open` 内临时插 `panic!()`，同样确认弹窗仍能再次打开**（原稿的验证只测了 ①，恰好测不到遗漏的那一半）。验证后移除。

**更好的方案：让守卫「无法被取出」**`【第十八轮复核新增】`

上面的 `SingleFlightGuard::new(...) -> Option<Self>` 写法虽然能修好缺陷，但它**保留了 P0-1 的同一类隐患**：守卫是一个可以被自由处置的值，写 `let _ = SingleFlightGuard::new(&ANIMATING);` 就会**立刻 Drop → 保护静默失效**。（原稿用的是 `AnimatingGuard::acquire()`，第二十四轮已按「不新建守卫类型」的处方改为复用 `SingleFlightGuard`；隐患性质相同。）而**属性救不了它**——已实测（`rustc 1.96.0`）：

| 写法 | 结果 |
|---|---|
| `G::acquire();`（裸语句，`G` 带 `#[must_use]`，返回 `Option<G>`） | **不告警**——`Option` 自身非 `#[must_use]`，外层表达式整体不 must_use |
| `#[must_use] fn f() -> Option<u32>`，然后 `f();` | ✅ 告警 `unused return value of 'f' that must be used` |
| 同一个 `#[must_use]` 函数，写成 `let _ = f();` | **不告警**（`unused_must_use` 被通配绑定抑制） |
| 同一个 `#[must_use]` 函数，写成 `let _g = f();` | **不告警**（下划线命名同样抑制） |

即：**「必须持有」无法用 `#[must_use]` / 命名约定 / lint 表达**——这与 P0-1 的结论完全一致（第十六轮方案 A-3）。

**推荐改法：把守卫从「返回值」变成「唯一出口的必需参数」**——调用方既拿不到它，也不会忘传：

```rust
// 守卫复用 SingleFlightGuard（见上，P3-13 已把它上移到 state.rs）
/// 唯一出口：守卫是**必需参数**——漏传即 `error[E0061]`，无法绕过；
/// 闭包内显式持有 → 生命周期 = 线程；panic 展开时同样被 Drop，标志照样复位。
fn spawn_animation<F: FnOnce() + Send + 'static>(guard: SingleFlightGuard<'static>, f: F) {
    std::thread::spawn(move || {
        let _guard = guard;
        f();
    });
}

// 调用点（close 与 show 两处同形；原 store(true)/store(false) 四处一并删除）
//   —— 守卫在**函数顶部**取得，早退发生在任何窗口操作之前
let Some(guard) = SingleFlightGuard::new(&ANIMATING) else { return };
// …setup（close 的 place_below_taskbar；show 的 resume_webview / set_size / set_position / show 等）…
spawn_animation(guard, move || animate_close(&win, cx, cy, start_y));
```

**为什么更好**：「忘记移入闭包」「绑到 `_`」「提前 Drop」这三种误用**在结构上不可能发生**——`spawn_animation` 的签名要求**必须**传入守卫（漏传是**类型错误**，不是 lint 提醒），而守卫在函数内部取得、调用方无从处置。若 `spawn` 失败并 panic，`guard` 会随闭包在展开时被 Drop，标志同样被复位（`【第二十五轮复核修正】`**此句仅在 unwind 构建下成立**——本仓 release 是 `panic = "abort"`，见下表注）。

**实测**（`rustc 1.96.0`，真实线程；`-D warnings` 零告警）`【第二十五轮复核修正】`**——第 3、4 行与构建 profile 强相关，必须分列**：

| 场景 | unwind 构建（默认 / `cargo test` / dev） | release 构建（`Cargo.toml:84` 的 `panic = "abort"`） |
|---|---|---|
| 正常路径 | 动画执行期间 `ANIMATING=true`，结束后 `false` ✅ | 同 ✅（与 profile 无关） |
| 漏传守卫（`spawn_animation(move \|\| …)`） | **`error[E0061]`** ✅（类型级拦截，编译期） | 同 ✅（与 profile 无关） |
| **动画内 panic**（`animate_open` / `animate_close`） | **`ANIMATING=false`** ✅（Drop 随展开执行） | ⚠️ **不适用**——实测 panic 后**进程直接终止**（第 3 场景后进程退出、退出码 **127**），标志是否复位**无从观测** |
| panic 后再次启动 | 成功 ✅ | ⚠️ 不适用（进程已终止，不存在「再次启动」） |

> `【第二十五轮复核修正】`**上表第 3、4 行只能在正确的前提下引用，否则会高估本条的收益。** 回源 + 实测确认：
> - **跳过 `store(false)` 的唯一途径是 panic**（或发散）。`popup.rs:157` / `:206` 的 `store(false)` 位于闭包内 `animate_close(...)` / `animate_open(...)` **之后**，而 `animate_*` 内部与 `show` / `close` 中间**没有 `?`、没有早退**——所以**被吞掉的 `Err` 只会让执行继续走到 `store(false)`，不会留下 `true`**。
> - 因此**在 release（`panic = "abort"`）下，P1-8 的「永久卡死弹窗」症状不可达**——panic 直接终止进程。报告 P1-8 的「潜在影响」已自述这一点（「实际后果是应用崩溃重启而非静默卡死」）。
> - **本条在 release 下的真实收益**因此**不是**「panic 后标志复位」，而是：**① 用一次 CAS 取代 `store(true)` / `store(false)` 的不对称手工置位**（消除「2 个置位点 + 2 个复位点必须成对」的维护陷阱）；**② 消除 `toggle` 的 check-then-act 竞态（P3-6）**；**③ 顺带覆盖 `std::thread::spawn` 自身 panic 的路径**（此时闭包连同守卫在展开中被 Drop；现状写法下 `store(true)` 已执行而 `store(false)` 永不执行）。
> - **「panic 后复位」这条收益只在 unwind 构建下可见**——它是**开发期**收益（不再需要重启应用），**不要当作生产环境的收益来陈述**。


> `【第二十四轮复核修正】`⚠️ **不要把「取得守卫」推迟到 spawn 那一行——这会静默削弱本条的修复效果。** 第十八轮原稿给的是一个 `fn run_animation<F>(f: F) -> bool`（守卫在**函数内**取得），调用点写成 `if !run_animation(move || animate_close(...)) { return; }`。问题在于：闭包要捕获 `win` / `cx` / `cy`，这些值必须**先算出来**，所以 `run_animation(...)` 只能写在 **setup 之后**——于是原子占用点被从**函数顶部**挪到了 **spawn 处**。对照 `popup.rs:168-190` 的真实结构，`show()` 在置位之前已经做了 `resume_webview` / `set_memory_usage_target` / `set_size`：
>
> | 设计 | 占用点 | 已有动画在跑时，第二次调用会做什么 |
> |---|---|---|
> | **本方案**（守卫在顶部 + 必需参数） | **函数顶部** | 立刻 `return`，**不碰窗口** ✅ |
> | 原 `run_animation` 写法 | **spawn 处** | 先跑完 `resume_webview` / `set_size` / `set_position` / `show()` / `place_below_taskbar`，**再**被拒 |
>
> 而 §5.3 的「附带收益」写的是「`toggle` 中『读 → 计算 → 写』的 check-then-act 竞态（**P3-6**）一并解决」——**占用点后移恰好使这句打折扣**：窗口操作仍可能在占用判定之前发生。**「守卫作必需参数」同时满足「不可忘记」（第十六轮 A-3 的类型级护栏）与「尽早占用」两条约束，是它们的唯一交点。**

> **取舍**：本改法比原稿多一个 5 行的 `spawn_animation` 助手，但把 P0-1 与 P1-8 的**共同根因（守卫可被自由处置）**一次性消除，且**不引入任何新类型**（复用 P3-13 上移的 `SingleFlightGuard`）。**建议采纳。**

> **还可以更好：给「标志残留」加一条与 profile 无关的兜底（建议）**`【第二十五轮复核修正】`
>
> 上面的守卫方案把「标志复位」绑定在**作用域退出**上。于是在 `panic = "abort"` 的 release 下，唯一的残留途径（panic）会直接终止进程——**症状与复位同时消失**，等于该收益在 release 下为空（见上表注）。若希望**无论何种原因**（含今后新增的路径、`std::thread::spawn` 失败、乃至某个未来分支忘记走守卫）标志都不会长期残留，建议再加一道**超时自愈**——它不依赖 unwind，也不依赖任何一处代码写得对：
>
> ```rust
> // state.rs：记录动画开始时刻（与 ANIMATING 同处，便于一并观察）
> pub static ANIMATION_STARTED: AtomicU64 = AtomicU64::new(0);   // 单调时钟毫秒，0 = 空闲
>
> // popup.rs：三个入口的早退判据由「已占用」改为「已占用且未超时」
> const ANIMATION_TIMEOUT_MS: u64 = 2_000;   // 动画实测最长约 200ms，留 10 倍余量
> fn animating() -> bool {
>     let t = ANIMATION_STARTED.load(Ordering::Relaxed);
>     t != 0 && now_ms().saturating_sub(t) < ANIMATION_TIMEOUT_MS
> }
> ```
>
> **为什么这条值得加**：P1-8 的症状是「**一次异常 → 永久失效，只能重启应用**」。守卫方案缩小了「异常」的触发面，但**没有改变「永久」这个性质**——它仍依赖「每一个退出路径都恰好经过守卫的 Drop」。超时自愈把「永久」改成「最多卡 2 秒」，代价是 **1 个 `AtomicU64` + 3 处判据改写**，且**与 profile 无关**。两条一起做才构成「既缩小触发面、又兜住漏网」的完整闭环；若只做守卫，建议至少按上表注把收益表述收窄。

**回归风险**：低。

### 5.4 P1-11　`update_config` 全量覆盖导致丢失更新

**位置**：`src-tauri/src/commands.rs:84-103`、`src-tauri/dist/scripts/settings.js:26-32`

**问题**：典型 lost update——弹窗重命名设备的同时设置页切换开关并 `saveConfig()`，若设置页的 `config` 快照早于重命名，则**重命名被覆盖丢失**。且丢失是静默的。

**改法（三条路线，按成本递增，建议先做 3 再做 1）**

1. **低成本**：`update_config` 改为「补丁式」——前端只发送被修改的字段（如 `{ newConfig: { theme_mode: "dark" } }`），后端做字段级合并。需为 `Config` 增加可选字段包装（`Option<T>` + 只覆盖 `Some`）。
2. **中成本**：后端维护 `config_revision: u64`，前端回传其持有的 revision；不匹配则拒绝并回传最新配置让前端重试（乐观锁）。
3. **零成本（兜底，先做）**：在 `update_config` 前后各取一次 revision，若在写入窗口内被其他来源修改过则**打日志告警**，便于观测实际发生频率，再决定是否投入 1/2。

**验证**`【第十九轮复核修正】`：`cargo check` + `cargo test`；**外加一个可证伪的并发测试**（原稿只写「按路线 3 先上线观测」，不足以验证任何一条路线的修复，见下）。

> ⚠️ **原稿的验证无法证伪本条**：`cargo check` 是类型检查；`cargo test` 现有用例里**没有任何并发写配置的场景**；而「上线观测」是**事后依赖生产日志**，既不可重复，也无法在 CI 里回归。本条是 **lost update（时序类）**，必须主动制造那个交错。
>
> **可证伪的验证（建议写成 `#[cfg(test)]` 用例）**：把各路线要引入的判定逻辑**抽成纯函数**再测——
> - 路线 1：抽出 `fn merge_config(base: &Config, patch: &ConfigPatch) -> Config`，测试「只带 `theme_mode` 的补丁**不会**清掉 `device_names`」；
> - 路线 2/3：抽出 `fn check_revision(current: u64, incoming: u64) -> RevisionVerdict`，测试「`incoming < current` 时判为冲突（路线 2 拒绝 / 路线 3 告警）」。
>
> 这两条都是**纯逻辑、可单测、可在 CI 回归**，成本远低于「上线观测」，且能在未修复版本上**明确失败**。
>
> **手测补充**（覆盖真实 IPC 路径）：开两个窗口，一个在设置页连点开关，另一个在弹窗重命名设备；重复 ~20 次，确认 `device_names` 不丢。

**回归风险**：路线 1 会改动前后端 IPC 契约，**需前后端同步改**；路线 2/3 风险低。

### 6.2 验证设计原则：可证伪

**本小节是第十九轮复核的核心产出。** 该轮换了一个此前从未用过的角度：**不问「改法对不对」，而问「方案里写的验证步骤，能不能真的把缺陷证伪」。**

**判据只有一条**：

> 一个验证步骤是**有效**的，当且仅当——**在未修复的代码上它会失败（或给出不同结果），在修复后的代码上它会通过**；并且它检查的必须是**本次改动真正改变的那个机制**。

按此判据逐个检查本方案的全部「验证」列，**发现 7 条不成立**（其中 **2 条必改**：P3-12、P1-11，已按此重写；**5 条建议**：P3-11、P3-1、P2-5、P2-4、P3-5，已补充替代验证）：

**① 最严重的一处：P3-12 的验证是同义反复（已实测）**

原稿写：

```bash
grep -c "PostMessageW(Some(self.hwnd), WM_SYNC_CALLBACKS" src-tauri/src/audio_notify.rs
```

实测结果：**未修复的代码上返回 `4`，修复后仍然是 `4`。** 原因很简单——该修复改的是**接收端**（`let _ = PostMessageW(...)` → `if PostMessageW(...).is_err()`），**被 grep 匹配的表达式本身一个字都没变**。这条命令**永远返回 4**，与修没修毫无关系。它更**完全没有检查本次新增的「回滚」**。

已改写为两条**能区分修复前后**的检查：

```bash
# ① 回滚必须与 4 处投递一一对应：匹配到投递行后，紧随的 3 行内必须有回滚
grep -A3 "PostMessageW(Some(self.hwnd), WM_SYNC_CALLBACKS" src-tauri/src/audio_notify.rs \
  | grep -c "SYNC_CALLBACKS_PENDING.store(false"      # 修复后期望 4；未修复为 0

# ② 丢弃式接收必须清零
grep -c "let _ = PostMessageW(Some(self.hwnd), WM_SYNC_CALLBACKS" src-tauri/src/audio_notify.rs
                                                    # 修复后期望 0；未修复为 4
```

> **教训**：**「结构核对命令」不是验证。** `grep -c` 数的是文本出现的次数，它无法回答「这个文本所在的那个分支，行为是否变了」。**凡是「数一数改了几处」的命令，都要再问一句：删掉修复本身，它会不会照样通过？**

**② 第二处：P1-11 的验证不可证伪（原稿三件事都做不到）**

原稿写：`cargo check` + `cargo test` + 「按路线 3 先上线观测」。

- `cargo check` **只证明能编译**；
- `cargo test` —— **本仓当前没有任何并发写测试**，跑通它证明不了丢更新不存在；
- 「上线观测」—— 触发条件是**两个窗口同时改配置**的纳秒级交错，靠用户自然操作几乎不可能复现；且它**不在 CI 里**，不可重复。

**三件事都无法把「丢更新」证伪。** 已补充可证伪设计：把「合并 / 版本号判定」抽成纯函数（`merge_config` / `check_revision`）做单测——因为**丢更新的根因就藏在这个判定里**，把它从并发环境里拎出来单独测，才能稳定复现「后写覆盖先写」；并发环境只留一条 20 次迭代的双窗口手测做兜底。

**③ 其余四条：验证检查的不是本次改动的机制**

**④ P3-11 的注入式复现法（时序类缺陷的通用手法）**

时序类缺陷无法靠「多试几次」验证，正确做法是**人为把窗口撑大**：

```rust
// 【仅在临时分支上做，验证完即删】
loop {
    // 未修复版：读在装载之前 —— 在「读取」与「等待」之间插入 50ms
    let current = crate::windows::system_dark_mode();
    std::thread::sleep(std::time::Duration::from_millis(50));  // ← 撑开窗口
    RegNotifyChangeKeyValue(hkey, 0, REG_NOTIFY_CHANGE_LAST_SET, event, 1);
    if current != last { /* … */ }
    WaitForSingleObject(event, INFINITE);
}
```

**判定**：把窗口撑到 50ms 后，在这 50ms 内切换主题——
- **未修复版**：这次变更**落在窗口里被丢掉**，托盘图标保持旧配色，直到**下一次无关的注册表变更**才自愈（可稳定复现，100% 命中）；
- **修复版**（装载 → 读取 → 等待）：变更落在**已装载的通知**覆盖范围内，**当次即被捕获**。

> 这是**确定性**的：撑开的窗口让「丢/不丢」从概率事件变成必现事件。**已把这条方法列入避坑清单第 20 条。**

**⑤ 一条必须承认的边界：不是所有条目都能被证伪**

本方案里有相当一部分条目的改动本身是**文档、注释、规范文字**（如 P2-5 的契约文档、P3-7 的分类表、P3-8/P3-10 的注释、§八 的收尾项），它们的「验证」只能是**评审**——**这不是缺陷，但必须标注为「评审类」，不能伪装成「已通过机械验证」**。**建议在实施时给每条验证标注三选一：`命令`（可自动判真伪）/ `注入`（需临时改代码）/ `评审`（只能人工看）。**

### 6.4 「回归风险」里写明的确认动作，必须落进「验证」——否则落地时会被静默丢弃

**为什么需要这一节**：本方案每条的固定结构是「改法 → **验证** → **回归风险**」。§6.3 已经规定「**每批完成的判据 = 回归段 + 验收段**」，但它只约束了「**验证**」这一段。**问题在于：本方案有相当一批条目，把「必须做的确认动作」写在了『回归风险』里，而不是『验证』里**。而 §6.3 的执行口径是「**未列出的条目，一律按其所在小节的『验证』执行**」——**『回归风险』不在执行口径内**。于是这些确认动作**在落地时被静默丢弃**，且**没有任何检查会发现它们丢了**。

**落地要求（本节的核心，也是 §6.3 执行口径的补充）**：

> **凡「回归风险」里出现「需确认 / 需扫一遍 / 必须核对 / 需逐处确认 / 需前后端同步改」这类**动作词**的，该动作**必须**二者其一：**
> 1. **提升为「验证」块里的一条**（写明怎么测、期望看到什么）；或
> 2. **显式声明「接受该风险，不验证」并给出理由**（例如「延迟在 1 帧内，无观测手段，接受」）。
>
> **不允许**让这类动作只停留在「回归风险」的文字里——**因为「回归风险」不在任何执行口径内，写在那里等于没写。**

**为什么这条值得单列**：它和第 21~26 轮发现的所有坑**同源**——「**描述了事实，但没有把描述变成会失败/会执行的检查**」。前几轮抓到的是「验证本身不可证伪」（§6.2）、「把回归项当验收项」（§6.3）、「注入点插在原地」（避坑 #24）、「实测脱离 profile」（避坑 #26）；**本轮抓到的是这个家族的最后一块拼图：连『验证』都没进去的动作**。区别在于——前几类是**验证写错了**，这一类是**验证根本没写**。

> ⚠️ **一处必须同时点明的诚实性限定**：本节的「12 条含确认动作 / 7 条未覆盖」是**人读分类**的结果，不是脚本可判定的——因为「什么算确认动作」本身有边界模糊（例如 §4.4 的「见 §八.1 第 3 行」算不算确认动作，取决于是否把「指向」视作「安排」）。**本节的判据（见下 §8.3 第 14 条）因此也只能是评审，不要给它编造命令**——这正是 §6.3 末尾那条边界声明的应用。
