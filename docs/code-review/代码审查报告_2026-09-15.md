## 二、P0 严重问题

### P0-1　单飞守卫（SingleFlightGuard）未随工作线程释放，单飞保护完全失效

**位置**
- `src-tauri/src/wireless_24g/mod.rs:198-214`（`snapshot`）
- `src-tauri/src/bluetooth.rs:653-670`（`enqueue_bt_refresh`）

**现状**

两处写法同构：

```rust
let Some(_guard) = SingleFlightGuard::new(&REFRESHING) else { /* 已有刷新在跑 */ };
// guard 移入闭包，panic 时 Drop 自动复位标志      ← 注释
std::thread::spawn(move || {
    refresh_worker(stale);
    // guard 在此 drop，自动复位 REFRESHING        ← 注释
});
```

变量名为 `_guard` 且**在闭包体内从未被引用**，因此 `move` 闭包不会捕获它。Rust 闭包只捕获「被使用的变量」，未被使用的 `_guard` 会在 `snapshot()` / `enqueue_bt_refresh()` **函数返回时立即 Drop**，而不是在工作线程结束时。

**已实测验证**（用 `rustc 1.96.0` 构造同构最小复现）：

```
[场景A] 与 wireless_24g::snapshot / bluetooth::enqueue_bt_refresh 同构写法：
  抢到标志, 即将 spawn 工作线程
  spawn 返回, 函数即将结束
  >> Guard::drop 执行（标志复位）          ← 在 spawn 返回后立刻复位
  [工作线程] 工作结束, 此时标志 = false    ← 工作期间标志已是 false
```

**潜在影响**

- `REFRESHING` / `BT_BATTERY_REFRESHING` 在每次 spawn 后立刻复位，**单飞语义退化为无保护**。
- `wireless_24g` 侧：多轮设备列表刷新会并发创建多个后台刷新线程，**并发访问同一 HID 设备**——这正是注释里明确要避免的场景（"避免并发访问同一 HID 设备"），可能导致 HID 读取交错、返回错值或句柄异常。
- `bluetooth` 侧：并发发起 GATT / SetupDi 查询，对休眠设备反复敲门，加剧蓝牙栈压力。
- 注释与代码语义相反，后续维护者会依据注释做出错误判断。

**改进建议**

`【第四轮复核修正】`⚠️ **原稿的方案 A 逐字照抄无法编译**：原稿写 `let _guard = guard;`，但源码中的外层绑定名是 `_guard`（无 `guard` 变量），`rustc 1.96.0` 报 `error[E0425]: cannot find value 'guard' in this scope`，并提示「the leading underscore in `_guard` marks it as unused, consider renaming it to `guard`」。**原因是「问题描述」与「修复代码」用了两套命名**。下面给出两种**已实测可编译且能恢复单飞**的写法（任选其一）：

```rust
// 方案 A-1：把外层绑定改名（语义最清晰，推荐）
let Some(guard) = SingleFlightGuard::new(&REFRESHING) else { /* 已有刷新在跑 */ return result; };
std::thread::spawn(move || {
    let _guard = guard;          // 显式引用 → 触发捕获，随线程结束 Drop
    refresh_worker(stale);
});
```
```rust
// 方案 A-2：不改名，靠闭包内自引用触发捕获
let Some(_guard) = SingleFlightGuard::new(&REFRESHING) else { /* 已有刷新在跑 */ return result; };
std::thread::spawn(move || {
    let _guard = _guard;         // RHS 指外层绑定 → 触发捕获（可行但易读性差）
    refresh_worker(stale);
});
```
```rust
// 方案 B：去掉守卫，在闭包内显式建守卫
REFRESHING.store(true, Ordering::SeqCst);
std::thread::spawn(move || {
    let _reset = ResetOnDrop(&REFRESHING);   // 或 defer 风格
    refresh_worker(stale);
});
```

**实测证据**（`rustc 1.96.0`，同构最小复现，三个场景）：

```
[场景 A] 原样写法（闭包体不引用 _guard）
  spawn 返回, 函数即将结束
  >> Guard::drop 执行 → REFRESHING 复位为 false
  [工作线程] A 开始, 此刻 REFRESHING = false      ← 工作期间标志已是 false，单飞失效
[场景 B] 修复写法（外层改名 guard）
  [工作线程] B 开始, 此刻 REFRESHING = true       ← 修复生效
  [工作线程] B 结束, 此刻 REFRESHING = true
  >> Guard::drop 执行 → REFRESHING 复位为 false
[场景 C] 修复写法（外层仍叫 _guard，闭包内 let _guard = _guard;）
  [工作线程] C 开始, 此刻 REFRESHING = true       ← 修复同样生效
  >> Guard::drop 执行 → REFRESHING 复位为 false
```

**另经核实**：该修复**不会引入重入或自锁**——后台线程体 `refresh_worker`（`wireless_24g/mod.rs:371-393`）只调用 `query_and_cache` / `notify_battery_changed` / `persist::flush`，**不触碰 `REFRESHING`**，故修复后标志被正常持有至线程结束不会造成自我阻塞。

建议同时把「未被捕获的守卫」纳入评审清单——这类缺陷编译器不会告警，只能靠人眼或测试发现。

`【第六轮复核修正】`⚠️ **上句「编译器不会告警」经实测需要加一个重要限定**——**编译器本可以捕获它，是 `_` 前缀把告警关掉了**：

```
# 同一段代码，只改绑定名：
[写法 1] let Some(_guard) = Guard::new() else { return };   → 编译无任何告警
[写法 2] let Some(guard)  = Guard::new() else { return };   → warning: unused variable: `guard`
                                                              help: if this is intentional, prefix it with an underscore
```

（`rustc 1.96.0` 实测；`unused_variables` 属 `#[warn(unused)]`，**默认开启**。）

**这意味着**：本项目 `AGENTS.md` 要求 `cargo check` **零告警**（pre-commit 钩子强制拦截），且 `main.rs:2` 已启用 `#![warn(unused_imports, dead_code)]`——**若作者当初把该绑定命名为 `guard`（不带下划线），`cargo check` 会立即告警、钩子会拦下这次提交，P0-1 根本不会进入仓库**。是「用下划线消掉告警」这个习惯，恰好绕过了项目自己的安全网。

由此得到两条可执行结论：

1. **修复时优先采用方案 A-1（把外层绑定改名为 `guard`）**——它不仅修好缺陷，还**恢复了编译器的回归保护**：日后若有人再删掉闭包内对守卫的引用，`unused_variables` 会立刻报警。方案 A-2（保留 `_guard`）虽同样能修好，但仍把这道保护关着。
2. **RAII 守卫不应带下划线前缀**（详见 **P3-14**）。下划线的语义是「我确定这个值不会被使用」，而 RAII 守卫的价值恰恰在于「它必须被持有到作用域结束」——两者语义相反，用 `_` 是把告警静音而非消除问题。

### P0-2　蓝牙电量单飞标志在早退路径泄漏，导致蓝牙电量永久降级

**位置**：`src-tauri/src/bluetooth.rs:466-514`（`find_paired_bluetooth_devices`）

**现状**

```rust
let force = fresh
    && BT_BATTERY_REFRESHING
        .compare_exchange(false, true, Ordering::SeqCst, Ordering::SeqCst)
        .is_ok();
// 注意：此处不使用 RAII guard，因为函数结束时需要复位标志     ← 注释
...
let btc_selector = BluetoothDevice::GetDeviceSelectorFromPairingState(true)?;   // ← 早退，标志未复位
let btc_devices_info = DeviceInformation::FindAllAsyncAqsFilter(&btc_selector)?.join()?;  // ← 早退
let ble_selector = BluetoothLEDevice::GetDeviceSelectorFromPairingState(true)?;  // ← 早退
let ble_devices_info = DeviceInformation::FindAllAsyncAqsFilter(&ble_selector)?.join()?;  // ← 早退
...
if force {
    BT_BATTERY_REFRESHING.store(false, Ordering::SeqCst);   // ← 只有正常走到这里才复位
}
```

该函数**有 4 个 `?` 早退点**（`【第十一轮复核】`口径注明：指 **4 条会早退的语句**——`:475`、`:476`、`:490`、`:491`；其中 `:476` 与 `:491` 是 `FindAllAsyncAqsFilter(...)?.join()?`，**每行含 2 个 `?`**，故 `?` 运算符共 **6 个**。原稿「4 个」按语句计，与上方代码块标注的 4 行一致），且注释自述「不使用 RAII guard」——但后续 `enqueue_bt_refresh` 的 `SingleFlightGuard` 恰好因为 P0-1 也失效，两者叠加后问题更隐蔽。

**潜在影响**

- `【第十一轮复核修正】`**在 `fresh=true` 的调用中**，任一次 WinRT 枚举失败（蓝牙适配器被关闭、驱动异常、`join()` 超时、服务被禁用）都会让 `BT_BATTERY_REFRESHING` **永久停在 `true`**。原稿此处未带该限定语，读起来像「任何一次失败都会泄漏」——**需按 `let force = fresh && CAS` 的门控收窄**：只有 `fresh=true` 的调用才会把标志置位，`fresh=false` 的调用根本不触碰它（失败也只是返回 `Err`，标志仍是 `false`）。
  - 逐调用点核实（`fresh` 实参）：`fresh=true` 仅 **1 处**——`commands.rs:45`（`query_devices(true)`，即用户手动刷新）；`fresh=false` 有 4 处——`commands.rs:37`、`tray.rs:37`、`tray.rs:116`、`bluetooth.rs:686`。故泄漏的实际触发面是「用户点一次刷新 + 该次 WinRT 枚举失败」，比原稿读感要窄，但仍是**必然**的（无任何补偿路径）。
- 后果是**永久性功能退化**，且无任何日志提示：
  - `force` 恒为 `false` → 手动刷新永远只读缓存，不再现查电量；
  - `enqueue_bt_refresh` 的 `SingleFlightGuard::new` CAS 永远失败 → **后台电量补查彻底停摆**，蓝牙电量从此不再更新（直到重启进程）。
- `【第十二轮复核修正】`与蓝牙开关**相关，但并非「关一次蓝牙即触发」**——原稿写作「用户关一次蓝牙即可能触发」，与上方第十一轮修正后的机制**相互矛盾**，已更正。逐链路核实：
  - 用户关蓝牙 → `handle_radio_state()`（`bluetooth.rs:873`）只 `emit("devices-changed")`；
  - 前端监听（`popup-devices.js:447`）走 `scheduleSilentRefresh`（`:435-442`）→ **`loadDevices(false)`** → `get_devices` → `query_devices(false)` → **`fresh=false`**；
  - 而 `fresh=false` **根本不触碰标志**（见上）→ **关蓝牙本身不会泄漏标志**。
  - `fresh=true` 的唯一入口是 `popup.js:16` 的**刷新按钮**（`loadDevices(true)`，带「正在刷新…」提示）。因此准确表述是：**「关掉蓝牙（使 WinRT 枚举必然失败）+ 用户点一次刷新按钮」两件事同时发生才会泄漏**，缺一不可。
  - 这也解释了为何该缺陷难被用户自行归因：用户认为是「关蓝牙导致的」，实际是自己那次刷新把它锁死了。

**改进建议**

`【第四轮复核修正】`原稿方案**可编译且语义正确**（已用 `rustc 1.96.0` 实测：正常返回与 `?` 早退两条路径均正确复位，`fresh=false` 时不触碰标志，已被后台占用时 `force=false` 降级读缓存）。但它**新引入了第三种守卫类型 `ForceGuard`**，而**同文件已有语义完全相同的 `SingleFlightGuard`（`bluetooth.rs:519-541`）**。建议直接复用，避免同类 RAII 类型分裂：

```rust
// 复用既有 SingleFlightGuard（无需新类型）；已实测 4 个场景均正确
let force_guard = fresh
    .then(|| SingleFlightGuard::new(&BT_BATTERY_REFRESHING))
    .flatten();
let force = force_guard.is_some();
// 后续任意 ? 早退都会经 Drop 复位；正常返回亦然
```

### P0-3　手写 COM 回调对象引用计数错误（`add_ref` 不计数、`release` 无条件释放）

**位置**：`src-tauri/src/webview.rs:95-158`（`mod try_suspend_cb`）

**现状**

```rust
unsafe extern "system" fn add_ref(_this: *mut Obj) -> u32 { 1 }      // 恒返回 1，不递增
unsafe extern "system" fn release(this: *mut Obj) -> u32 {
    unsafe { drop(Box::from_raw(this)) };                            // 无条件释放
    0
}
```

配合 `ICoreWebView2TrySuspendCompletedHandler::from_raw_borrowed(&cb_ptr)` 以「借用」方式传入，成功路径不接管引用计数（注释：*成功时回调由 runtime 使用，失败时手动 destroy*）。

`【复核修正】`复核补充一处**同源的 COM 契约违反**：`webview.rs:116-123` 的 `qi` 对**一切** IID 都返回 `E_NOINTERFACE`（`-2147467262`），**包括 `IID_IUnknown`**。COM 规范要求 `QueryInterface(IID_IUnknown)` 必须成功——任何跨公寓封送（standard marshaler）都会先做这次 QI，失败即断链。当前 `with_webview` 闭包在 UI 线程（同公寓）内直接调用 vtable，故尚未暴露；但这条与引用计数一样属于「靠调用环境侥幸成立」的隐式假设，修复时宜一并处理。

**潜在影响**　`【复核修正】`

> **定级建议**：复核后建议由 **P0 调整为 P1**。原文「必然泄漏」的机制描述不成立——`add_ref` 是硬编码返回 1 而不递增，因此**不存在第二份引用**，正常路径既无泄漏也无双重释放。保留编号 P0-3 以便与原稿对照。若按「热点路径上的潜在 UB 一律视为 P0」的口径，也可维持 P0，但下方机制描述必须更正。

- 该对象的引用计数是伪造的：`add_ref` 恒返回 1 而不递增，`release` 无条件 `Box::from_raw`。**只有 Release 恰好被调用一次时才是正确的**——这依赖 WebView2 运行时对完成回调「AddRef 一次 / Release 一次」的配对方式，属隐式依赖。
- 已核实绑定层不产生任何引用计数操作：`windows-core-0.61.2/src/interface.rs:77` 的 `from_raw_borrowed(raw: &*mut c_void) -> Option<&Self>` 返回**借用引用**（不接管、不 AddRef）；`webview2-com-sys-0.38.2/src/bindings.rs:42627` 的 `TrySuspend<P0>(&self, handler: P0) where P0: Param<...>` 经 `handler.param().abi()` 传递，而 `windows-core-0.61.2/src/param.rs:39-56` 中 `impl<T, U> Param<T, InterfaceType> for &U` 在同型情况下返回 `ParamValue::Borrowed`（`transmute_copy`，不 AddRef）。故正常路径下唯一一次 `Box::into_raw` 的分配被唯一一次 runtime `Release` 释放。
- 真正的风险是**双重释放（heap corruption / use-after-free）**，有两条可设想路径：
  1. runtime 内部对回调的 AddRef/Release 配对超过 1:1（如回调被包进带自身引用计数的 wrapper 后又被复制），第二次 `Release` 会重复释放同一指针；
  2. **错误路径叠加**：`webview.rs:195-198` 在 `TrySuspend` 返回 `Err` 时调用 `try_suspend_cb::destroy(cb_ptr)`。若 WebView2 已先构造 wrapper（AddRef）、再因前置条件不满足（例如 `webview.rs:169` 的 `SetIsVisible(false)` 失败，导致 `TrySuspend` 报错）而析构 wrapper（Release → 释放对象），随后 `destroy` 即二次释放。
- 该路径在**每次 popup 关闭时都会执行**（`popup.rs:349-357` 的 `animate_close` 在 `popup.rs:356` 调用 `webview::suspend_webview`，其定义在 `webview.rs:163`），属于高频路径。`【第七轮复核修正】`原稿此处写作「`webview.rs:356`」——**该引用不可能存在**：`webview.rs` 全文仅 283 行。实际是把**调用点行号（`popup.rs:356`）**误配到了**定义文件（`webview.rs`）**上；定义行号为 `webview.rs:163`。一旦 WebView2 运行时调整回调生命周期配对方式，即可能在 COM 回调线程崩溃，排查成本极高。
- 这是全仓 149 处 `unsafe` 中风险最集中的一处：手写 vtable + 手写引用计数。

**改进建议**

`【第十六轮复核修正】`⚠️ **本节的「首选」经实测不可行，已改判**——原稿写「`implement!` 宏…（`webview2-com-sys` 与 `windows-core-061` 同基座，**可直接复用**）」，这个「直接复用」在本仓做不到。用与仓内完全一致的依赖（`windows-core = "0.62"` + `windows-core-061` + `webview2-com-sys = "0.38"`）做离线构建复现，得到：

```
error[E0277]: the trait bound `ICoreWebView2TrySuspendCompletedHandler:
              windows_core::Interface` is not satisfied
note: there are multiple different versions of crate `windows_core` in the dependency graph
  --> windows-core-0.62.2/src/interface.rs:14:1  this is the expected trait
  --> windows-core-0.61.2/src/interface.rs:14:1  this is the found trait
```

根因是 `implement!` 宏**硬编码 `::windows_core::` 路径**且**不支持指定 crate**：`windows-implement-0.60.2/src/lib.rs:150` 生成 `<#ident as ::windows_core::Interface>::Vtable`，全文共 15 个硬编码路径（`ComObject` / `ComObjectInterface` / `AsImpl` / `IUnknownImpl` / `IInspectable_Vtbl` / `GUID` / `HRESULT` / `imp` 等）；其 `ImplementAttributes` 只解析接口名、`TrustLevel(..)`、`Agile(..)` 三类 token，**没有 crate 路径覆盖**。而本仓把 0.62 命名为 `windows_core`（`Cargo.toml:24`）、0.61 改名为 `windows_core_061`（`Cargo.toml:27`），于是宏生成的 `::windows_core::` 一律指向 **0.62**，与 `webview2-com-sys-0.38.2/src/bindings.rs:37212` 所要求的 `windows_core::IUnknownImpl`（0.61）**不是同一个 trait**。**从哪个 windows-core 导入宏都一样失败**——0.61.2 与 0.62.2 依赖的是**同一份** `windows-implement 0.60.2`（`windows-core-0.61.2/Cargo.toml:45`、`windows-core-0.62.2/Cargo.toml:44`），宏体逐字相同；本仓 `Cargo.lock:5341-5342` 亦只有一条 `windows-implement 0.60.2`，而 `windows-core` 有 0.61.2 与 0.62.2 两条。反证：把依赖改成 `windows_core = { package = "windows-core", version = "0.61" }`（让 `windows_core` 就是 0.61）后**编译通过**——但该前提与 `audio_notify.rs:12`（服务 `windows 0.62` 的接口）**互斥**，`Cargo.toml:24-26` 已注明「rename 共存，勿合并」，故不能靠改名解决。**结论：`implement!` 路线需把该回调挪进独立的 0.61 子 crate 才可行，性价比低于下面的方案。**

项目内已有正确范例——`audio_notify.rs` 使用 `windows_core::implement` 宏声明 `IAudioEndpointVolumeCallback` / `IAudioSessionEvents` / `IMMNotificationClient`，由宏生成正确的引用计数实现（它成立的前提正是那些接口与 `windows_core` **同为 0.62**）。建议：

1. **推荐**：保留手写对象，补成契约合规的 COM 对象——真实引用计数 **+ 修 `qi` 对 `IID_IUnknown` 的契约违反**（见本节开头「同源的 COM 契约违反」）+ 同步更新 `create()` 初始化。三者必须一起做；
2. **备选**：加入 `webview2-com = "0.38"`（与现有 `webview2-com-sys = "0.38"` 同版本、已在本地 registry 缓存中），删除手写模块，改用上游 `TrySuspendCompletedHandler::create(...)`（`webview2-com-0.38.2/src/callback.rs:482`）。代价：多引入一份 `windows 0.61` 依赖，且闭包签名用的是 windows-core 0.61 的 `Result`（与仓内主用的 0.62 不同型）。

**「推荐」的具体代码**（`refs` 计数 + `qi` 契约 + `create` 初始化）：

```rust
#[repr(C)]
pub struct Obj { vtable: *const Vtable, refs: AtomicU32 }

unsafe extern "system" fn add_ref(this: *mut Obj) -> u32 {
    unsafe { (*this).refs.fetch_add(1, Ordering::Relaxed) + 1 }
}
unsafe extern "system" fn release(this: *mut Obj) -> u32 {
    let n = unsafe { (*this).refs.fetch_sub(1, Ordering::Release) } - 1;
    if n == 0 { unsafe { drop(Box::from_raw(this)) }; }
    n
}

// qi：IID_IUnknown 必须成功并 AddRef，否则不是合规 COM 对象
unsafe extern "system" fn qi(
    this: *mut Obj,
    iid: *const windows_sys::core::GUID,
    out: *mut *mut core::ffi::c_void,
) -> i32 {
    const IID_IUNKNOWN: windows_sys::core::GUID =
        windows_sys::core::GUID::from_u128(0x0000_0000_0000_0000_C000_0000_0000_0046);
    unsafe {
        if !iid.is_null() && *iid == IID_IUNKNOWN {
            add_ref(this);
            *out = this as *mut core::ffi::c_void;
            0                                   // S_OK
        } else {
            *out = core::ptr::null_mut();
            -2147467262                         // E_NOINTERFACE
        }
    }
}

// create 必须初始化 refs（原稿未给出，照抄会漏）
pub fn create() -> *mut core::ffi::c_void {
    let obj = Box::new(Obj { vtable: &VTABLE, refs: AtomicU32::new(1) });
    Box::into_raw(obj) as *mut core::ffi::c_void
}
```

已用 `rustc 1.96.0` 实测：编译零告警，`create → add_ref(→2) → release(→1) → release(→0)` 运行通过。

并补一条注释说明初始引用计数归属（谁创建、谁释放），避免后续再次误改。**另需一并想清楚 `destroy`（`webview.rs:195-198`）与 runtime `release` 的归属**——引入真实计数后二者可能双重释放，需二选一（保留 `destroy` 则初始计数归调用方；或把 `destroy` 改为 `release`）。

## 三、P1 高优先级问题

### P1-1　事件监听回调在事件线程上执行阻塞 COM 枚举与菜单重建

**位置**：`src-tauri/src/tray.rs:442-461`

**现状**

```rust
app.listen("config-changed", move |_| {
    let new_auto = config::with_config(|c| c.auto_start);
    AUTO_START.store(new_auto, Ordering::Relaxed);
    update_auto_text();
    update_tray_icon();
    update_audio_devices_menu();        // ← 含 audio::enumerate_output_devices()（COM）+ build_full_menu（重建整棵菜单）
    std::thread::spawn(|| { refresh_devices_cache(); update_tooltip(); });  // ← 这一句反而 spawn 了
});

app.listen("audio-devices-changed", |_| {
    update_audio_devices_menu();        // ← 同样未 spawn
});
```

`update_audio_devices_menu()` 内部会：`lock_unpoisoned(TRAY_ICON)` → `audio::enumerate_output_devices()`（创建 IMMDeviceEnumerator、遍历端点、逐台 Activate 读音量）→ `build_full_menu()` → `tray.set_menu()`。

`【复核修正】`菜单项计数原稿写「创建 11 个 MenuItem + 3 个分隔符 + 2 个子菜单」，经逐行核对应为：**整个调用树共创建 12 + N 个 MenuItem**（`build_full_menu` 自身 6 个：show/volume/settings/about/auto_start/exit；`build_windows_sound_settings_menu` 6 个；`build_audio_devices_menu` N 个，N = 可见输出设备数，无设备时为 1 个占位项）+ **3 个分隔符**（`tray.rs:242-244`）+ **2 个子菜单**（音频设备、声音设置）。分隔符与子菜单数无误。

同一文件 `tray.rs:290-294` 与 `main.rs:271-286` 都明确写下约定：

> *"菜单事件在事件线程上分发：重操作（窗口/材质/DWM）一律 spawn 移出"*

`【复核修正】`复核新增：**托盘菜单的「开机自启」分支把 P1-1 与 P1-3 叠加在了同一次点击上**（`tray.rs:311-326`，位于 `on_menu_event` 内，即事件线程）：

```rust
"auto_start" => {
    AUTO_START.store(new_val, Ordering::Relaxed);
    config::with_config_mut(|c| c.auto_start = new_val);  // ← 持全局配置锁做 fsync 落盘（P1-3）
    let _ = if new_val { autostart.enable() } else { autostart.disable() };  // ← 注册表写
    update_auto_text();
    let _ = app.emit("config-changed", config_snapshot);  // ← 同步触发上面的监听 → COM 枚举 + 菜单重建（P1-1）
}
```

即**用户单击一次「开机自启」**，事件线程上会依次发生：配置锁内 fsync 落盘 → 注册表写 → `update_tray_icon()` + `update_audio_devices_menu()`（COM 端点枚举 + 整棵菜单重建）。`app.emit` 对同进程监听器是同步分发，因此这些全部串行发生在事件线程上。

**潜在影响**

- 违反项目自身已文档化的架构约定，属**回归型问题**（约定写了但这两条路径没跟上）。
- `【复核修正】`**最短触发路径是托盘菜单本身**：单击「开机自启」→ 事件线程上完成「配置 fsync + 注册表写 + COM 枚举 + 菜单重建」全部串行工作（见上方 `tray.rs:311-326`）。这条路径与设置页无关，用户无须打开任何窗口即可触发。
- `config-changed` 在每次配置保存时都会触发（设置页任意开关），而 `audio-devices-changed` 在每次音频设备增删、默认设备切换时触发。事件线程被 COM 枚举阻塞期间，**窗口消息无法处理**，表现为弹窗点击无响应、托盘无反应。
- 这正是 `spawn_watchdog` 中「连续 2 次探活超时（最坏 ~40s）判定事件循环僵死 → 重启自身进程」要兜底的场景。用「重启进程」来兜底「自己制造的阻塞」代价过高（用户看到应用重启、正在进行的操作丢失）。此外 `update_audio_devices_menu` 在持有 `TRAY_ICON` 锁期间做 COM 调用，也会与 `update_tray_icon` 形成锁竞争。

> `【2026-09-18 勘误 · 本条「潜在影响」的措辞需限定】`
> 上面这段把「弹窗点击无响应、托盘无反应」归因于**事件线程被 COM 枚举阻塞**——实施期实测表明，
> **实际观测到的那次冻结（`AppHangTransient` / `0xcfffffff`）不是这个机制**，而是 **P0-4 的锁序死锁**
> （子线程持配置锁调菜单 API 同步等主线程 ⇄ 主线程等配置锁，**永久互等**，见本节开头的勘误块）。
> 两者的**可观测症状相同**（窗口点不动、日志停在某一行），但**成因与修法完全不同**：
> COM 阻塞是**有时长上限**的（数十毫秒~数百毫秒，最终会自行恢复）；
> **锁序死锁没有时长上限**（永不恢复，看门狗也救不回，因为探活本身要主线程）。
> **因此：本条的 COM 阻塞是真实且应修的（P1-1），但它不能用来解释「永久冻结」**——
> 遇到「窗口完全无响应」时，请先按 P0-4 的判据查**锁序**，不要停在 COM 上。
> 另：本报告 P2-7 一节（`show_toast` 在**持设备缓存锁**时做跨进程通知调用）是**同一类锁纪律问题**，
> 属「持锁做慢操作」，实施期已一并修掉（`da38238`）。

**改进建议**

比照同文件既有模式，把两条监听里的重操作全部 spawn 到子线程：

```rust
app.listen("config-changed", move |_| {
    let new_auto = config::with_config(|c| c.auto_start);
    AUTO_START.store(new_auto, Ordering::Relaxed);
    update_auto_text();                       // 轻量，可留在事件线程
    std::thread::spawn(|| {
        update_tray_icon();
        update_audio_devices_menu();
        refresh_devices_cache();
        update_tooltip();
    });
});
```

另建议在 `update_audio_devices_menu` 中先构造新子菜单、再短暂持锁替换，缩短 `TRAY_ICON` 锁的持有时长。同时建议把「事件线程只做轻量分发」补进 `AGENTS.md` 的强制约束清单，并为 `app.listen` 回调增加评审检查项。

### P1-3　`with_config_mut` 在持有全局配置锁期间执行同步磁盘 I/O（含 fsync）

**位置**：`src-tauri/src/config.rs:329-366`

**现状**

```rust
pub fn with_config_mut<F, R>(f: F) -> R {
    let mut guard = lock_unpoisoned(CONFIG.get().expect("Config not initialized"));
    let result = f(&mut guard);
    if let Ok(content) = toml::to_string_pretty(&*guard) {
        ...
        let write_result = std::fs::File::create(&tmp_path)
            .and_then(|mut f| { f.write_all(content.as_bytes())?; f.sync_all()?; Ok(()) })
            .and_then(|_| std::fs::rename(&tmp_path, &cfg_path));   // ← 锁内完成
```

原子写入（临时文件 + `sync_all` + `rename`）本身是**正确且值得肯定**的设计，问题在于它发生在**全局配置锁的临界区内**，且由**同步 Tauri 命令**调用（`update_config`、`toggle_device_hidden`、`rename_device`、`change_device_group`、`toggle_group_hidden`、`toggle_device_tray`、`set_hotkey_config`…）。

`【复核修正】`全仓 `with_config_mut` 调用点共 13 处（`commands.rs` 10 处、`config.rs:308`、`tray.rs:315`、`window_material.rs:263`）。需特别指出：**`tray.rs:315` 并非 Tauri 命令，而是托盘菜单「开机自启」分支的事件回调**——即配置锁内 fsync 也会发生在**事件线程**上（详见 P1-1 的新增段落）。

**潜在影响**

- `sync_all()` 强制落盘，机械盘/受控磁盘/杀软实时扫描场景下可达数十毫秒。期间：
  - 所有 `with_config` 读取者（托盘 tooltip 构建、设备查询、电量通知、快捷键分发、看门狗探活…）全部阻塞在配置锁上；
  - 同步命令的执行线程被占用，若该线程参与 IPC 处理，表现为 UI 卡顿。
- 高频操作（隐藏/显示设备、批量重命名）会连续触发多次「锁内 fsync」。
- 与 P1-1 叠加：`config-changed` 事件监听里还会同步做 COM 枚举，配置保存路径整体偏重。

**改进建议**

保留原子写入，但把 I/O 移出锁：

```rust
pub fn with_config_mut<F, R>(f: F) -> R {
    let (result, snapshot) = {
        let mut guard = lock_unpoisoned(CONFIG.get().expect("Config not initialized"));
        let result = f(&mut guard);
        sync_log_cache(&guard);                       // 缓存同步留在锁内（纯内存，微秒级）
        (result, toml::to_string_pretty(&*guard).ok())
    };                                                // ← 锁在此释放
    if let Some(content) = snapshot { persist_if_changed(content); }   // 脏检查 + 落盘在锁外
    result
}
```

注意：把落盘移出锁后需重新审视「脏检查缓存 `LAST_CONFIG_CONTENT`」的并发语义（当前是在锁内读写的），建议改为 `Mutex<String>` 独立保护并在锁外串行化落盘，避免两次并发写入交错覆盖。

`【第七轮复核修正】`示例中的 `persist_if_changed(content)` 是**方案新引入的辅助函数，当前并不存在**（`config.rs` 无任何 `persist*` / `write_config*` / `save_config*` 函数，现有落盘逻辑内联在 `with_config_mut` 中）。这不影响建议成立，但**照抄无法编译**，需一并实现该函数（含脏检查）。建议今后所有修复块统一标注「新增符号」，避免读者误以为可直接粘贴。

### P1-4　`open_with_system` 用 `cmd /c start` 打开任意字符串，且与既有 `ShellExecuteW` 实现并存

**位置**：`src-tauri/src/process.rs:304-311`，暴露面 `commands.rs:151-153`（`open_url`）、`commands.rs:220-230`、`commands.rs:383-387`

**现状**

```rust
pub fn open_with_system(path: &str) -> Result<(), String> {
    let mut cmd = new_hidden_cmd("cmd");
    cmd.args(["/c", "start", "", path]).spawn()...
}

#[tauri::command]
pub fn open_url(url: String) -> Result<(), String> {
    process::open_with_system(&url)          // ← 无 scheme 白名单，任意字符串直通 cmd
}
```

同一文件里另有基于 `ShellExecuteW` 的 `shell_open()`（`process.rs:341-357`），但它是私有的、只服务于 `open_sound_panel` / `open_settings_page`，**并未用于 `open_url`**。

**潜在影响**

- `cmd.exe` 会二次解析命令行。Rust 1.77+ 已针对 `cmd`/`bat` 引入特殊转义（BatBadBut / CVE-2024-24576 的修复），本项目工具链为 1.96，**当前大概率已被 std 兜住**；但这是一层隐式依赖——工具链降级、或未来有人把 `cmd` 换成 `powershell`/`bash` 就会立刻退化。不应把安全性建立在「标准库恰好做了转义」上。
- `open_url` 无 scheme 白名单，可被用于打开 `file:`、`ms-*`、自定义协议等任意 URI。结合 P1-10（CSP 为 `null`、`withGlobalTauri: true`），一旦 webview 内出现脚本注入点，`open_url` 就是最直接的落地利用原语。`【复核修正】`原稿此处误引为「P2-1」，实为 P1-10。
- 同一功能两套实现，属可维护性负担。

`【第五轮复核修正】`**位置信息已逐条核实**：`process.rs:304-311` 确为 `new_hidden_cmd("cmd")` + `.args(["/c", "start", "", path])` ✓；`shell_open`（`process.rs:341-357`）确为**私有** `fn`（无 `pub`），且确只被 `open_sound_panel`（`:361`）与 `open_settings_page`（`:369`）调用 ✓；`open_url`（`commands.rs:151-153`）确无 scheme 白名单 ✓。**补充**：`open_with_system` 全仓实际有 **5 个调用点**（`commands.rs:147`（`ms-settings:bluetooth`）、`:152`（`open_url`）、`:229`、`:386`、`tray.rs:341`（`sndvol.exe`）），原稿列出的 3 处为「安全暴露面」；另 2 处是硬编码字面量、无注入面，故原稿的取舍成立，但清单非穷举——若将来有人把用户输入接到那两处，需一并纳入白名单约束。

**改进建议**

1. `open_url` 改用 `ShellExecuteW`（无需 shell 解析，天然免疫注入），并把 `shell_open` 提升为 `pub`：

```rust
pub fn open_url(url: &str) -> Result<(), String> {
    // 白名单 scheme
    const ALLOWED: &[&str] = &["https://", "http://", "ms-windows-store://", "ms-settings:"];
    if !ALLOWED.iter().any(|p| url.starts_with(p)) {
        return Err(format!("不允许的链接协议: {}", url));
    }
    shell_open(url, None);
    Ok(())
}
```

2. 把 `open_with_system` 也统一切到 `ShellExecuteW`（打开文件/目录同样适用），消除 `cmd /c start` 这条路径，让「打开外部目标」只有一种实现。

`【第七轮复核修正】`⚠️ **上面第 1 条的示例代码不能逐字照抄，有两处未标注的变更**（沿用第六轮 P1-7 的「三失效模式」检查法发现）：

| 问题 | 原代码 | 示例代码 | 后果 |
|---|---|---|---|
| **丢失 `#[tauri::command]` 属性** | 有 | **无** | 命令不会注册进 invoke 处理器，前端 `invoke("open_url")` 在**运行时**失败；且不会有任何编译告警 |
| **签名由 `String` 改为 `&str`** | `url: String` | `url: &str` | 经查 `tauri-macros-2.6.3/src/command/wrapper.rs:176-240`，**引用参数的限制只针对 `async` 命令**，`open_url` 是同步命令，故该改动**大概率可编译**；但它是对公开 IPC 契约的静默变更，应显式说明而非夹带 |

正确的替换写法（保留属性与签名）：

```rust
#[tauri::command]
pub fn open_url(url: String) -> Result<(), String> {
```

**附：本条依赖的符号已逐条查证为真实存在** ✅——`shell_open` 定义在 `process.rs:341`，签名为 `fn shell_open(file: &str, params: Option<&str>)`，与示例的 `shell_open(url, None)` **匹配**；原稿对它的**文件归属（`process.rs`，非 `windows.rs`）与私有性判断均正确**。

### P1-5　`set_hotkey_config` 先注销旧快捷键再校验新键，失败即静默失效

**位置**：`src-tauri/src/commands.rs:408-450`

**现状**

```rust
let prev_key = config::with_config(|c| ...);          // 1. 读旧键
if let Some(ref pk) = prev_key {
    if let Ok(sc) = parse_shortcut(pk) {
        let _ = app.global_shortcut().unregister(sc);  // 2. 先注销旧键（不可逆）
    }
}
if let Some(ref new_key_str) = key {
    let sc = parse_shortcut(new_key_str)?;             // 3. 新键解析失败 → 直接 Err 返回
    if app.global_shortcut().is_registered(sc.clone()) {
        set_config_key(&action, None);                 // 4. 被占用 → config 置 None 后返回 Err
        return Err("快捷键已被占用".to_string());
    }
    ...
}
set_config_key(&action, key);                          // 5. 只有全部成功才写 config
```

**潜在影响**

- **分支 3（新键无法解析）**：旧键已注销、`config` 仍保留旧键 → **配置与实际注册状态不一致**。前端显示「已设置 XX 快捷键」，但按键无任何反应；且因为 `config` 没变，`config-changed` 也不会广播，用户无从察觉。需重启应用才恢复。
- **分支 4（新键被占用）**：旧键被注销且 `config` 被清空 → 用户原可用快捷键丢失，需重新设置。语义上「清空」尚可接受，但未提示用户「你的旧快捷键已被清除」。
- 注册失败的错误被 `let _ =` 吞掉，用户无法得知注册实际未生效。`【第五轮复核修正】`⚠️ **原稿把此处引为「`commands.rs:437-444` 中 `on_shortcut` 的返回值」，引用错位**——`commands.rs:437-444` 实际是 `.map_err(|e| e.to_string())?`，**错误是向上传播的**。真正被 `let _ =` 吞掉的是 **`shortcut.rs:81-88`** 与 **`shortcut.rs:104-111`**（设备快捷键的注册路径），见 **P2-12**。
- `【第五轮复核修正】`另注：`commands.rs:434-436` 在**注册尝试之前**就打印了 `"[hotkey] registered {} {}"`，若随后 `on_shortcut` 失败（`:444` 返回 `Err`），日志已留下「注册成功」的错误记录，排查时会误导。

**改进建议**

改为「先校验、后变更」的原子顺序：

```rust
#[tauri::command]
pub fn set_hotkey_config(app: tauri::AppHandle, action: String, key: Option<String>) -> Result<(), String> {
    // ① 只做校验，不做任何副作用
    let new_sc = match &key {
        Some(k) => {
            let sc = parse_shortcut(k)?;                        // 解析失败：状态零变化
            if app.global_shortcut().is_registered(sc.clone()) {
                return Err("快捷键已被占用".to_string());         // 被占用：状态零变化
            }
            Some(sc)
        }
        None => None,
    };

    // ② 校验全部通过后，才执行「注销旧 → 注册新 → 落配置」
    let prev = config::with_config(|c| /* 取旧键 */);
    if let Some(pk) = prev { if let Ok(sc) = parse_shortcut(&pk) { let _ = app.global_shortcut().unregister(sc); } }
    if let Some(sc) = new_sc {
        app.global_shortcut().on_shortcut(sc, move |...| { ... }).map_err(|e| e.to_string())?;
    }
    set_config_key(&action, key);
    ...
}
```

同时把 `on_shortcut` 的错误从 `let _ =` 改为向上传播，让前端能提示「注册失败」。`【第五轮复核修正】`需改的是 **`shortcut.rs:81-88` / `:104-111`** 两处（`commands.rs:437-444` 本已传播），详见 P2-12。

### P1-7　配置解析失败时整份配置静默重置为默认值

**位置**：`src-tauri/src/config.rs:267-287`（`init_config`）

**现状**

```rust
Ok(content) => match toml::from_str(&content) {
    Ok(config) => config,
    Err(e) => {
        eprintln!("[config] parse error: {}", e);
        Config::default()          // ← 解析失败 = 全部配置回默认
    }
},
```

而 `Config` 中 **10 个字段没有 `#[serde(default)]`**：`auto_start`、`hidden_devices`、`hidden_groups`、`device_names`、`device_groups`、`filter_enabled`、`filter_regex`、`dedup_devices`、`show_unnamed_bt`、`use_system_bt`。任一个缺失都会使整份 TOML 解析失败。

> `【第五轮复核修正】`**该清单经脚本逐字段核对完全属实**：`Config` 共 **42 个字段**，其中 **31 个**已带 `#[serde(default)]`，**10 个**缺失（即上述清单，逐字吻合）。另有第 11 个未带该属性的字段 `legacy_log_enabled`（旧版日志开关迁移用），其类型为 **`Option<bool>`**——serde 对 `Option` 隐式按 `None` 处理缺失字段，**故不构成风险，未计入 10 个之内是正确的**。

**潜在影响**

- 触发条件：用户手工编辑 `config.toml` 误删字段、从新版本回退到旧版本（旧代码不认识新字段通常无碍，但反向缺字段会失败）、文件被外部工具截断。
- 后果严重：**用户全部个性化配置（重命名、分组、隐藏列表、快捷键、电量阈值、托盘设备…）一次性丢失**，且仅在日志/`stderr` 中留一行，UI 无任何提示。用户感知为「设置全没了」。
- 更隐蔽的是：解析失败后下一次任意配置写入会用默认值**覆盖磁盘上的原文件**，原始配置无法找回。

**改进建议**

1. 给全部字段补 `#[serde(default)]` / `#[serde(default = "...")]`，让单字段缺失只影响该字段。

`【第六轮复核修正】`⚠️ **原稿这条建议的示例代码有缺陷**：它给出了 `filter_enabled` / `filter_regex` 的正确属性，随后用 `// ...其余同理` 一笔带过——但**「同理」在这里会出错**。逐字段比对 `Config::default()`（`config.rs:167-176`）后，10 个字段中有 **2 个**的默认值**不等于** `Default::default()`：

| 字段 | `Config::default()` 实际值 | 裸 `#[serde(default)]` 会得到 | 后果 |
|---|---|---|---|
| **`hidden_groups`** | `vec!["Battery", "Monitor"]` | `vec![]`（`Vec::default()`） | **默认隐藏分组丢失**——用户升级后 Battery / Monitor 两组会突然出现在列表里 |
| **`dedup_devices`** | `true` | `false`（`bool::default()`） | **设备去重被静默关闭** |

其余 8 个字段（`auto_start: false`、`hidden_devices: vec![]`、`device_names`/`device_groups: HashMap::new()`、`filter_enabled: true`、`filter_regex: Self::default_filter_regex()`、`show_unnamed_bt: false`、`use_system_bt: false`）与各自类型的 `Default` 一致，裸 `#[serde(default)]` 或原稿给出的属性均正确。

**修正后的写法**（注意后两行需要 helper，其中 `default_hidden_groups` **尚不存在、需新增**）：

```rust
#[serde(default)]                              pub auto_start: bool,
#[serde(default)]                              pub hidden_devices: Vec<String>,
#[serde(default = "default_hidden_groups")]    pub hidden_groups: Vec<String>,   // ← 新增 helper，返回 ["Battery","Monitor"]
#[serde(default)]                              pub device_names: HashMap<String, String>,
#[serde(default)]                              pub device_groups: HashMap<String, String>,
#[serde(default = "default_true")]             pub filter_enabled: bool,
#[serde(default = "Config::default_filter_regex")] pub filter_regex: String,
#[serde(default = "default_true")]             pub dedup_devices: bool,          // ← 默认 true，不能用裸 default
#[serde(default)]                              pub show_unnamed_bt: bool,
#[serde(default)]                              pub use_system_bt: bool,
```

> 已核实原稿用到的两个 helper **确实存在**：`fn default_true()`（`config.rs:142`）与 `impl Config { fn default_filter_regex() }`（`config.rs:215`）——这两处引用无误，问题只在被 `// ...其余同理` 掩盖的那两个字段。
>
> **这类「修复代码本身有缺陷」的问题编译不会报错、测试也未必覆盖**，属最容易漏过评审的一类（与 P0-1 的方案 A 同族，但更隐蔽：P0-1 是编译失败，本条是**编译通过但行为静默改变**）。

2. 解析失败时**不要立即用默认值覆盖**，而是把原文件重命名为 `config.toml.bak.<时间戳>` 保留现场，并向前端广播一次「配置已重置」提示。
3. 建议补一个「配置往返测试」（`Config::default()` → `to_string_pretty` → `from_str` 应等价），防止未来新增字段时漏加 default 属性。

### P1-8　`ANIMATING` 全局标志无 RAII 保护，动画线程异常即永久卡死弹窗

**位置**：`src-tauri/src/popup.rs:102-208`

**现状**

```rust
fn close(window: &tauri::WebviewWindow, ...) {
    ANIMATING.store(true, Ordering::Relaxed);
    ...
    std::thread::spawn(move || {
        animate_close(&win, cx, cy, start_y);
        ANIMATING.store(false, Ordering::Relaxed);     // ← 只有正常返回才复位
    });
}
```

`toggle` / `open_popup` / `close_popup` 三个入口都在首行做 `if ANIMATING.load(...) { return; }`。

**潜在影响**

- `animate_close` / `animate_open` 内部调用 `window.set_position`、`window.hide`、`webview::suspend_webview`（COM）。若其中任一环节 panic（例如 P0-3 的 COM 对象问题触发、或 win32 调用异常），**`ANIMATING` 永久停在 `true`**。
- 后果：弹窗**再也无法通过托盘点击打开或关闭**（所有入口直接 return），只能重启应用。这是典型的「一次异常 → 永久失效」故障模式。
- 叠加 `panic = "abort"`：panic 会直接 abort 进程（不 unwind），实际后果是应用崩溃重启而非静默卡死——但若异常以 `Err` 形式被吞（如 `let _ = window.hide()`）而不 panic，则会落到「静默卡死」分支。两种后果都不可接受。`【第二十五轮复核修正】`**上面末句与代码结构不符，已更正。** 回源确认：`store(false)`（`popup.rs:157` / `:206`）位于闭包内 `animate_close(...)` / `animate_open(...)` **之后**，而 `animate_*` 内部与 `show` / `close` 中间**没有 `?`、没有早退**——因此**被吞掉的 `Err` 只会让执行继续走到 `store(false)`，不会留下 `true`**。**跳过 `store(false)` 的唯一途径是 panic（或发散）**，而 panic 在 `panic = "abort"` 下**直接终止进程**。**结论收窄为：本条的「永久卡死弹窗」症状只在 unwind 构建（dev / `cargo test`）下可达；release 下的实际后果是进程崩溃重启。** 该结论与修复方案 §5.3 的实测表注一致（release 下 panic 实测直接终止进程、退出码 127）。
- 另有 check-then-act 竞态：`toggle` 中「读 `ANIMATING` → 计算位置 → 写 `ANIMATING`」非原子，快速双击理论上可双开动画（P3-6）。

**改进建议**

用 RAII 守卫替代手工置位：

```rust
struct AnimatingGuard;
impl AnimatingGuard {
    fn acquire() -> Option<Self> {
        ANIMATING.compare_exchange(false, true, Ordering::SeqCst, Ordering::SeqCst)
            .ok().map(|_| AnimatingGuard)
    }
}
impl Drop for AnimatingGuard { fn drop(&mut self) { ANIMATING.store(false, Ordering::SeqCst); } }

fn close(window: &tauri::WebviewWindow, ...) {
    let Some(guard) = AnimatingGuard::acquire() else { return };   // 原子占用
    std::thread::spawn(move || {
        let _guard = guard;                                        // 随线程结束释放（注意 P0-1 的教训）
        animate_close(&win, cx, cy, start_y);
    });
}
```

**注意**：此处必须显式 `let _guard = guard;` 把守卫移入闭包——否则会重演 P0-1 的缺陷。

> `【第十七轮复核修正】`⚠️ **上面的修复块只覆盖了一半**——它只改了 `close`，而 `ANIMATING.store(true, …)` 在本文件里有**两个**置位点，失败模式完全相同：
>
> | 置位点 | 复位点 | 动画体 |
> |---|---|---|
> | `popup.rs:145`（`close`） | `:157` | `animate_close` |
> | **`popup.rs:190`（`show`）** | **`:206`** | **`animate_open`** |
>
> 本条自己的「潜在影响」段写的是「**`animate_close` / `animate_open`** 内部调用 `window.set_position`…若其中任一环节 panic」——即**已经知道有两条路径，但「改进建议」只给了一条**（与 P0-3 遗漏 `qi` 属同一类跨节丢失）。照原样实施后，`animate_open` 的 panic 仍会**永久卡死弹窗**（本条要消除的正是这个症状）。
>
> **`show` 需同样处理**：
>
> ```rust
> fn show(window: &tauri::WebviewWindow, /* …原参数… */) {
>     let Some(guard) = AnimatingGuard::acquire() else { return };
>     // …resume_webview / set_memory_usage_target / set_size / set_position / show 保持不变…
>     let win = window.clone();
>     std::thread::spawn(move || {
>         let _guard = guard;
>         animate_open(&win, target_x, start_y, target_y);
>     });
> }
> ```
>
> **落地后核对**：`grep -c "ANIMATING.store" src-tauri/src/popup.rs` 应为 **0**（2 个置位 + 2 个复位共 4 处全部被守卫取代）。**验证也必须两条路径各测一次**——只在 `animate_close` 里插 `panic!()` 恰好测不到漏掉的那一半。

> `【第十八轮复核修正】`⚠️ **上面这个 `acquire() -> Option<Self>` 写法能用，但它保留了 P0-1 的同一类隐患**：守卫是一个**可以被自由处置的值**，写 `let _ = AnimatingGuard::acquire();` 就会**立刻 Drop → 保护静默失效**，且**没有任何编译器机制能拦住它**——已实测（`rustc 1.96.0`）：
>
> | 写法 | 结果 |
> |---|---|
> | `G::acquire();`（`G` 带 `#[must_use]`，返回 `Option<G>`） | **不告警**——`Option` 自身非 `#[must_use]`，外层表达式整体不 must_use |
> | `#[must_use] fn f() -> Option<u32>` 后写 `f();` | ✅ 告警 `unused return value of 'f' that must be used` |
> | 同一个 `#[must_use]` 函数写成 `let _ = f();` | **不告警**（`unused_must_use` 被通配绑定抑制） |
> | 同一个 `#[must_use]` 函数写成 `let _g = f();` | **不告警**（下划线命名同样抑制） |
>
> 即：**「必须持有」无法用 `#[must_use]` / 命名约定 / lint 表达**——与 P0-1 的结论完全一致。
>
> **更好的方案：让守卫不作为「返回值」离开函数**（调用方根本拿不到它）：
>
> ```rust
> /// 唯一入口：占用标志并在新线程上执行动画。返回 false = 已有动画在跑。
> /// 守卫在函数内取得、随闭包移入线程 —— 调用方既拿不到它，也无法把它绑到 `_` 上。
> fn run_animation<F: FnOnce() + Send + 'static>(f: F) -> bool {
>     let Some(guard) = AnimatingGuard::acquire() else { return false };
>     std::thread::spawn(move || {
>         let _guard = guard;   // 显式引用 → 闭包捕获 → 生命周期 = 线程
>         f();
>     });
>     true
> }
>
> // 调用点（close 与 show 两处同形；原 store(true)/store(false) 四处一并删除）
> if !run_animation(move || animate_close(&win, cx, cy, start_y)) { return; }
> ```
>
> 把 `acquire` 降为**私有**后，「忘记移入闭包」「绑到 `_`」「提前 Drop」三种误用**在结构上不可能发生**（而不是靠约定提醒）。**已实测**（真实线程，零告警）：正常路径期间 `ANIMATING=true`、结束后 `false`；**`let _ = run_animation(..)` 下动画照常执行且守卫全程持有**；**动画内 panic 后 `ANIMATING=false`**（本条要消除的症状被消除）；panic 后再次启动成功。若 `spawn` 失败并 panic，`guard` 随闭包展开时被 Drop，标志同样复位。

### P1-9　会话/电量枚举存在重复的全量 COM 扫描

**位置**
- `src-tauri/src/audio.rs:270-383`（`enumerate_audio_sessions`）
- `src-tauri/src/audio.rs:457-486`（`resolve_session_device_names`）
- `src-tauri/src/bluetooth.rs:700-746`（`read_btc_battery_from_device_id`）

**现状**

1. `resolve_session_device_names(pids)`：先完整枚举一次输出设备、再完整枚举一次输入设备（建立 id→name 映射）；随后**对每个 pid** 调用 `get_session_device(pid, "output")` 与 `get_session_device(pid, "input")`。后者走 `IPolicyConfig::GetPersistedDefaultAudioEndpoint`（`audio_policy.rs:264-286`），成本是**每次调用重新激活一次 `Windows.Media.Internal.AudioPolicyConfig`**（`audio_policy.rs:125-142`：`RoGetActivationFactory` + HSTRING 构造 + 释放）。即 **2 次端点枚举 + 2N 次 WinRT 激活调用**（N = pid 数）。
   `【复核修正】`原稿此处表述为「`get_session_device` 内部会各自重新枚举端点、Activate `IAudioSessionManager2`、遍历会话，即 2 + 2N 次全量 COM 枚举」——经核实不成立：该函数不做端点枚举，而是按 pid 的持久化默认端点查询。
2. `enumerate_audio_sessions`：外层遍历所有输出设备 × 内层遍历该设备所有会话，对每个会话调用 `get_app_icon_by_pid`（首次需 OpenProcess + 版本信息 + 图标提取 + PNG 编码 + base64）与 `get_process_name_by_pid`。虽有两级 LRU(256) 缓存，但**冷启动首次展开音量页**时是 N 次同步磁盘/进程操作。
3. `read_btc_battery_from_device_id`：**每台蓝牙设备**都重新 `SetupDiGetClassDevsW` 打开一次设备信息集，并 `for index in 0..u32::MAX` 遍历系统全部设备直到命中。M 台蓝牙设备 → M 次全量系统设备枚举。

**潜在影响**

- 弹窗打开音量页 / 设备列表刷新时，主线程外的阻塞线程被 COM 往返占用，表现为「音量页出现慢」「应用音量列表延迟」。
- 蓝牙电量后台补查耗时随设备数线性放大；`snapshot_fresh`（手动刷新）在鼠标休眠场景下注释已承认「耗时可达数秒」，重复枚举进一步叠加。
- 属可优化但当前不致命的性能债务，随设备数增长而恶化。

**改进建议**

1. `resolve_session_device_names`　`【复核修正】`：**持久化默认端点无法从端点枚举中推导**（必须走 `IPolicyConfig` 查询），因此「改为一次遍历所有会话、把 2+2N 降为 2 次枚举」的路径不成立。可行优化是**复用同一个 factory 实例**——把 `create_policy_config_factory()` 从 `get_session_device` 内部提到 `resolve_session_device_names` 调用方，一次调用只激活一次，把 2N 次激活降为 1 次。
2. `read_btc_battery_from_device_id`：把 `SetupDiGetClassDevsW` / `SetupDiDestroyDeviceInfoList` 提到批量循环之外（如新增 `read_btc_batteries(ids: &[String]) -> HashMap<String, u8>`），一次枚举内匹配多个 MAC。
3. 会话卡片渲染的图标解析考虑改异步（先渲染占位、图标到达后回填），避免首屏同步等待。

### P1-11　`update_config` 全量覆盖配置，多窗口并发修改存在丢失更新

**位置**：`src-tauri/src/commands.rs:84-103`、`src-tauri/dist/scripts/settings.js:26-32`

**现状**

```js

async function saveConfig() { await invoke("update_config", { newConfig: config }); }
```
```rust

config::with_config_mut(|c| { *c = new_config; });
```

前端 `config` 由 `get_config` 初始化，并在 `config-changed` 事件中整体替换（`settings.js:736-745`）。弹窗页（`popup-*`）与设置页都会修改配置并触发 `config-changed`。

**潜在影响**

- 典型 lost update：用户 A 在弹窗重命名设备（后端改 `device_names`）的同时，设置页刚切换一个开关并 `saveConfig()`——若设置页的 `config` 快照早于重命名，则**重命名被覆盖丢失**。
- 窗口越小概率越低，但 `config-changed` 的往返延迟 + 用户操作时序使其并非理论问题。且丢失是静默的（下一次 `config-changed` 会把被覆盖后的值同步回两页，用户看到的是「刚改的没了」）。
- 当前依赖「每次变更都广播完整快照」来收敛，属**最终一致的启发式**，而非并发安全。

**改进建议**

1. **低成本**：`update_config` 改为「补丁式」——前端只发送被修改的字段（如 `{ newConfig: { theme_mode: "dark" } }`），后端做字段级合并。需为 `Config` 增加可选字段包装（`Option<T>` + 只覆盖 `Some`）。
2. **中成本**：后端维护 `config_revision: u64`，前端回传其持有的 revision；不匹配则拒绝并回传最新配置让前端重试（乐观锁）。
3. **零成本（兜底）**：在 `update_config` 前后各取一次 revision，若在写入窗口内被其他来源修改过则打日志告警，便于观测实际发生频率，再决定是否投入 1/2。

### P2-1　【已撤回】主题监听线程「手动重置事件导致忙循环」—— 实测推翻

**位置**：`src-tauri/src/tray.rs:163-209`

> **本条目结论作废，请勿据此修改代码。** 原稿标注「疑似」是对的；第二轮复核时曾一度将其上调为「机制确定」，该上调**同样是错的**，现已通过直接实测推翻。保留编号以便与原稿对照。

**原论断**：`CreateEventW(null, 1, ...)` 创建手动重置事件且循环体内无 `ResetEvent`，故首次通知后 `WaitForSingleObject` 每次立即返回 → 忙循环空转。

**实测过程**（`rustc 1.96.0` 编译的独立最小程序，直接调用 `CreateEventW` / `RegNotifyChangeKeyValue` / `RegSetValueExW` / `WaitForSingleObject`，监听自建测试键 `HKCU\Software\PeriTrayRegTest`，复刻应用的 `arm → wait → read` 循环结构）：

```
========== 手动重置事件 (bManualReset=1) ==========
  第1次等待: 结果=0 耗时=311ms                                  ← 正常收到通知
  第2次等待: 结果=258 耗时=1010ms ← 正常超时（事件已被复位，无忙循环）
  第3次等待: 结果=258 耗时=1005ms ← 正常超时（事件已被复位，无忙循环）
  第4次等待: 结果=258 耗时=1003ms ← 正常超时（事件已被复位，无忙循环）
  第5次等待(主动触发): 结果=0 耗时=303ms ← 通知链路仍然有效

========== 自动重置事件 (bManualReset=0) ==========
  （行为与手动重置完全一致）
```

（`结果=0` 为 `WAIT_OBJECT_0`，`258` 为 `WAIT_TIMEOUT`）

**结论**：`RegNotifyChangeKeyValue` 在（重新）装载通知时会**自行复位事件**，因此手动重置事件 + 无 `ResetEvent` **不会**导致忙循环。第 5 轮的「主动触发后 303ms 收到通知」证明重新装载后通知链路完好，故第 2~4 轮的 1005ms 超时是真实的「无变更」超时，而非通知机制失效。这也解释了为何 MSDN 官方示例可以放心使用 `CreateEvent(NULL, TRUE, FALSE, NULL)`。

**连带结论**：原「改进建议」（改自动重置 / 补 `ResetEvent`）虽无害，但**没有必要**，不应作为修复项排期。

**该条目唯一的残留观察**（降级为 P3-11）：循环中「读注册表 → 下次装载」之间存在一个未受保护的微秒级窗口，见 P3-11。

### P2-2　`audio_notify.rs` 使用 `.lock().unwrap()`，违反项目 `lock_unpoisoned` 约定

**位置**：`src-tauri/src/audio_notify.rs:28`

**现状**

```rust

    let mut map = lock.lock().unwrap();        // ← 全仓唯一一处裸 unwrap 加锁
```

`state.rs:44-48` 明确以注释确立了统一语义：

- 一致性破坏（约定被单点违反，后续维护者可能照抄）。

```rust
let mut map = crate::state::lock_unpoisoned(lock);
```

> `【第四轮复核修正】`「全仓 `.lock().unwrap()` 仅此一处」**经全仓检索确认属实**（唯一命中即 `audio_notify.rs:28`）。但第四轮发现该约定被绕过的**方式不止一种**——另有约 16 处采用与 `lock_unpoisoned` 语义不同或重复其实现体的写法，其中「静默跳过」风格会**直接放弃操作**，与 `state.rs:44-48` 声明的语义相反。详见 **P2-11**。

### P2-4　`watchdog` 自愈重启副作用：静默 `process::exit(0)` 且跳过清理

**位置**：`src-tauri/src/main.rs:95-114、210-267`

**现状**

```rust
fn watchdog_self_restart() {
    process::append_log("[watchdog] EVENT LOOP STUCK — self-restarting");
    ...
    std::process::Command::new(&exe).args(["--autostart", &arg]).spawn()...
    std::thread::sleep(std::time::Duration::from_millis(300));
    std::process::exit(0);              // ← 立即退出，无清理
}
```

`audio_notify.rs:559-562` 的注释已诚实承认：

> *"best-effort：仅覆盖正常退出路径（app.exit）；watchdog/panic 的 process::exit 不触发。"*

**潜在影响**

- 判定门槛为「连续 2 次探活超时」，最坏 ~40s 触发。若事件循环只是**短暂**繁忙（例如 P1-1 的 COM 枚举叠加 + 磁盘 fsync 抖动），可能误判并重启，用户看到应用无预警重启。
- `process::exit(0)` 不执行 `AudioMonitor::Drop`（`IMMNotificationClient` / 各设备与会话回调未反注册）、不刷新配置、不 flush 24G 电量缓存。反注册缺失可能让系统音频栈短暂持有失效回调。

**改进建议**

1. 提高判定门槛或增加二次确认（如连续 3 次、或探活超时放宽到 8~10s），降低误判率。
2. 重启前尝试一次优雅收尾：调用 `audio_notify::request_shutdown()` 并 `sleep(200ms)` 给消息循环机会，再 `exit`。
3. 退出码改为非 0（如 `exit(70)`），并在日志中记录触发起因（是探活超时还是时间跳变），便于用户反馈时定位。
4. **根本解法**：先消除 P1-1 / P1-3 这类自造阻塞，再评估看门狗阈值是否可放宽——看门狗是兜底，不应成为常态。

### P2-5　`ensure_com_initialized` 反复 `CoInitializeEx` 而无配对 `CoUninitialize`

**位置**：`src-tauri/src/audio.rs:58-66`

**现状**

```rust
pub(crate) unsafe fn ensure_com_initialized() {
    if let Err(e) = CoInitializeEx(None, COINIT_APARTMENTTHREADED).ok() { ... }
}
```

`with_enumerator` 每次调用都会执行它，而全仓**没有任何 `CoUninitialize` 调用**。每次成功的 `CoInitializeEx` 都会递增线程的 COM 初始化计数。

**潜在影响**

- 计数只增不减，线程的 COM 公寓永不释放。对长期存活的线程（tokio blocking pool 复用线程）而言影响有限（本就是进程生命周期），但：
  - 计数无界增长属资源语义错误，未来若引入线程池回收会暴露问题；
  - 若某线程已以 MTA 模式初始化（`RPC_E_CHANGED_MODE`），当前只记 verbose 日志后继续执行——后续 COM 调用可能以非预期公寓运行。虽 `main.rs:346-354` 已预先 `CoInitializeEx(APARTMENTTHREADED)`，但 `run_blocking` 使用 tokio blocking 线程，**这些线程的公寓模式由首次调用者决定**，存在隐性依赖。

**改进建议**

- 明确各执行路径的 COM 公寓契约并写入注释/文档：哪些线程是 STA、哪些是 MTA、`run_blocking` 上的 COM 调用依赖什么。
- `RPC_E_CHANGED_MODE`（`0x80010106`）应单独识别并记录为**告警级**日志，而非混在通用错误里——它是「公寓模式不符」的明确信号。
- 若要彻底正确，可在 `ensure_com_initialized` 用线程局部标志记录「本线程是否由我们初始化」，并在 `run_blocking` 任务收尾时配对 `CoUninitialize`；但考虑到 tokio 线程复用，更实际的做法是**保持现状并在文档中明确「进程内统一 STA，不做反初始化」**，把隐性假设变成显式契约。

- `std::thread::sleep` 会**阻塞 tokio 运行时的一个 worker 线程** 200ms。Tauri 默认运行时 worker 数有限，若同时有其他异步任务（更新检查、窗口创建）排队，会加剧调度延迟。
- 属局部性能与一致性问题，非功能缺陷。

**改进建议**

```rust
tokio::time::sleep(std::time::Duration::from_millis(200)).await;
```

并建议在代码规范中补一条：**异步上下文中禁止 `std::thread::sleep`**（`tools/check.mjs` 可增加一条针对 `async` 函数体内 `std::thread::sleep` 的静态检查）。

> `【第十八轮复核修正】`⚠️ **括号里那条「`check.mjs` 可增加静态检查」不成立，已改判。** 三点核实：

### P2-11　Mutex 中毒处理约定被系统性绕过：「静默跳过」风格与声明语义相反
`【第四轮复核新增】`

**位置**：`state.rs:44-48`（约定声明）对比全仓 **6 种**实际写法（`【第七轮复核修正】`原为「4 种」）

**现状**

`state.rs:44-48` 以注释确立了唯一语义：

> *"容忍 Mutex 中毒的加锁：锁中毒时直接接管内部数据继续使用（本项目各静态量在 panic 后仅需"可用"而非"严格一致"，统一在此表达该语义）"*

但全仓实际存在 **6 种**中毒处理风格（`【第七轮复核修正】`原稿称「4 种」，经逐点落地后更正——见下方说明）：

| # | 风格 | 语义 | 出现处 | 是否符合约定 |
|---|---|---|---|---|
| 1 | `lock_unpoisoned(m)` | 接管数据继续 | **41 处**（主流） | ✅ 符合 |
| 2 | `m.lock().unwrap()` | **panic**（`panic = "abort"` → 终止进程） | `audio_notify.rs:28` | ❌ 违反（即 P2-2） |
| 3 | `m.lock().unwrap_or_else(\|e\| e.into_inner())` | 接管数据继续，但**内联复刻**了 helper 实现体 | `process.rs:101`、`battery_notify.rs:65` | ⚠️ 语义等价，绕过统一入口 |
| 4 | `if let Ok(guard) = m.lock() { … }` | **静默跳过整个操作** | `tray.rs:22 / :80 / :132 / :238 / :411 / :473`、`config.rs:296 / :338 / :359`、`audio_spatial.rs:94 / :115`、`device_data.rs:143`、`update.rs:53`（**13 处，已逐点核实**） | ❌ **与声明语义相反** |
| 5 | `m.lock().map_err(\|e\| e.to_string())?` | **把中毒错误向上传播为 `Result::Err`** | `bt_ble.rs:47 / :138 / :154` | ❌ 与声明语义相反（但**比风格 4 更可取**，见下） |
| 6 | `m.lock().ok()` | 静默退化为 `None` | `update.rs:59` | ❌ 与声明语义相反（风格 4 同族） |

`【第七轮复核修正】`**关于「4 种 → 6 种」的说明**：原稿的分类表是**用正则计数**得出的，未逐点落地。本轮把全仓 21 处裸 `.lock()` 调用与 41 处 `lock_unpoisoned` 调用**逐条分类**，结论如下：

- **风格 4 的 13 处枚举逐点核实，完全正确** ✅——这一项经受住了最严格的检查；
- **风格 1 的「约 40 处」实为 41 处**（`lock_unpoisoned` 调用点；`toast.rs:42` 是注释，不计入）；
- **新增风格 5（3 处）**：`bt_ble.rs` 的三处 `ble_conn().lock().map_err(|e| e.to_string())?`。这是**第 3 种互相矛盾的语义**——既不 panic（风格 2）、不接管（风格 1/3）、也不静默跳过（风格 4），而是**把中毒作为错误返回给 Tauri 命令调用方**。讽刺的是，对返回 `Result` 的函数而言这**恰恰是最合理的做法**（用户能看到失败原因），却是全仓唯一未在 `state.rs` 注释中承认的语义；
- **新增风格 6（1 处）**：`update.rs:59` 的 `LAST_STATUS.lock().ok().and_then(|g| g.clone())`。与风格 4 同属「静默降级」，但语法形态独立，原表未收录。

**净效应**：这**加强了**本条结论而非削弱——项目实际存在 **6 种风格、3 类互相矛盾的语义**（接管 / 跳过 / 传播），比原稿描述的更分散。原稿「4 种」的说法应视为**低估**。

风格 4 的问题不在于「不一致」，而在于**语义相反**：约定说「接管数据继续使用」，风格 4 却是「拿不到锁就什么都不做」。前者保证功能可用性优先，后者直接放弃功能。

**潜在影响**

具体后果链（可静态推导，非理论风险）：

- `tray.rs:238-240`：`if let Ok(mut guard) = AUTO_MENU_ITEM.get().unwrap().lock() { *guard = Some(auto_i.clone()); }`——若该 Mutex 中毒，`AUTO_MENU_ITEM` **永不赋值**（保持 `None`）；
- `tray.rs:473`：`update_auto_text()` 同样是 `if let Ok(guard) = item.lock()`——中毒则静默返回；
- 合起来：一旦 `AUTO_MENU_ITEM` 中毒，**托盘「开机自启」菜单项的文案从此永不更新**（`AUTO_START` 状态与界面显示脱节），且无任何日志。

同类后果还见于 `tray.rs:132`（中毒则**低电量通知整轮跳过**）、`tray.rs:22`（中毒则**设备缓存永不写回**，tooltip 冻结在旧值）、`update.rs:53`（中毒则更新状态机失效）。

**触发概率**：需「持锁期间 panic」才会中毒，而本项目 `panic = "abort"` 会在 panic 时**直接终止进程**——因此风格 4 的分支在 release 构建下**实际上不可达**。这一点削弱了实际危害，故仍定 P2（与 P2-2 同级），但它揭示了**约定本身的自相矛盾**：

> 若 `panic = "abort"`，则「中毒」状态在进程内根本不可能出现，`lock_unpoisoned` 与 `if let Ok(...)` 的差别在 release 下无意义；
> 而在 `panic = "unwind"` 的构建（如测试、或未来改动）下，两者行为才真正分化，且风格 4 会静默丢功能。

**改进建议**

1. **统一到风格 1**：把风格 2、3、4、6 全部改为 `crate::state::lock_unpoisoned(...)`；**风格 5 需单独判断**（见下）。风格 4 的改造需把 `if let Ok(guard) = … { 体 }` 改写为直接取 guard（helper 永不失败）：
   ```rust
   let mut guard = crate::state::lock_unpoisoned(AUTO_MENU_ITEM.get().unwrap());
   *guard = Some(auto_i.clone());
   ```
   `【第七轮复核修正】`**风格 5（`bt_ble.rs:47 / :138 / :154`）不建议盲目并入风格 1**：它把中毒转成 `Result::Err` 返回给调用方，是本仓**唯一让用户能看到失败原因**的做法，而这三个函数（`ble_connect` / `ble_disconnect`）本来就返回 `Result`。更合适的处理是**承认它是一种有意风格**，在 `state.rs` 注释中单列，而不是改成「接管可疑的 BLE 连接表继续用」——后者对持有 WinRT 句柄的映射表反而更危险。这一条是本轮修正暴露出的**方案级取舍**，原稿的「全部统一」建议在此处不成立。
2. **或在 `state.rs` 注释中显式承认差异**：若「静默跳过」是有意选择（对只读缓存而言，跳过比接管可疑数据更安全），应在 `lock_unpoisoned` 旁注明「何时可用 `if let Ok` 风格、何时必须用 helper」，把隐性分歧变成显式规范；同时说明该分支在 `panic = "abort"` 下不可达。
3. 建议把「静态量的加锁方式」纳入 `tools/check.mjs` 的可检测项（正则匹配 `\.lock\(\)` 的裸用与 `if let Ok` 形态），与既有的 BOM / 版本一致性等检查同级。`【第七轮复核修正】`正则需覆盖**6 种**形态，尤其 `.lock().ok()`（风格 6，容易被 `.ok()` 后缀绕过 `if let Ok` 的匹配）。

### P2-12　`shortcut.rs` 注册失败仍被标记为「已注册」，设备快捷键静默永久失效
`【第五轮复核新增】`（排查 P1-5 的引用错位时发现）

**位置**：`src-tauri/src/shortcut.rs:80-89`（`sync_device_shortcuts` 的注册分支）

> `【第十一轮复核修正】`**原稿把该分支归属到 `register_shortcuts`，这是错的。** 行号 `:80-89` 本身正确，但**所属函数**错误：`register_shortcuts` 的定义是 `shortcut.rs:11-41`，其函数体内**没有任何 `registered.insert`**——它只做两件事：对 5 个全局快捷键各调一次 `register_single`（`:25-38`），然后 `sync_device_shortcuts(&app)`（`:40`）。含 `registered` 集合、`retain`、`contains` 跳过逻辑、`insert` 的那个函数是 **`sync_device_shortcuts`（定义于 `:46`）**。
>
> 之所以九轮复核都没发现：第七轮的行号机械校验只验「行号是否存在」、第十轮的反向定位只验「片段是否出现在声称的文件里」——**两轮都在「行/片段」层面工作，从未校验「该行号落在哪个函数里」**。行号正确 + 文件正确 + 片段逐字吻合，三者同时成立，仍然可能**函数归属错误**。这属新发现的失效模式，已记入复核记录。

**现状**

```rust
let action = format!("device_shortcut_key:{}", key);
let key_str = key.clone();
standard_log!("[shortcut] registered {} -> {}", key, action);   // ← 先打印「已注册」
let _ = app
    .global_shortcut()
    .on_shortcut(sc, move |_app, _shortcut, event| { ... });    // ← 失败被 let _ = 吞掉
registered.insert(key.clone());                                // ← 无条件标记为已注册
```

三个问题叠加：

1. **失败被吞**：`on_shortcut` 的 `Err` 被 `let _ =` 丢弃，无日志、无上报（同一文件的 `register_single`（`:104-111`）同样如此）。
2. **状态与实际不符**：`registered.insert(key.clone())` **无条件执行**——即使注册失败，该键也被记入 `DEVICE_REGISTERED_KEYS`。
3. **永久跳过**：循环开头（`:67-70`）是 `if registered.contains(key) { continue; }`，因此失败过的键**后续每次 `sync_device_shortcuts` 都被跳过**，永不重试。

> `【第十一轮复核修正】`**重试频率比原稿描述的更高**：原稿称该函数「由 `main.rs:459` 在启动时调用」，易被读成「只在启动时才会重试」。实际 `sync_device_shortcuts` 有 **4 个调用点**：`shortcut.rs:40`（经 `register_shortcuts`，即启动）、`commands.rs:90`（`update_config` 关闭共享开关时）、`commands.rs:504`（`set_device_shortcut`，每次设置/修改设备快捷键）、`commands.rs:533`（`remove_device_shortcut`）。**用户每次在设置页改动设备快捷键，都会重新走一遍这个循环**——但失败键因 `:68-70` 的 `contains` 判断被跳过，所以「重试」在形式上发生了、效果上等于零。

**潜在影响**

- 触发条件常见：目标快捷键已被其他应用占用时 `on_shortcut` 即失败。
- 后果：**该设备的快捷键从此完全不工作**，直到重启进程；而用户界面不会给出任何提示（`main.rs:459` 调用 `register_shortcuts`，其内部再转发给 `sync_device_shortcuts`；两者均返回 `()`，失败**没有任何上报通道**）。用户感知为「设了快捷键但按了没反应」。
- `【第十一轮复核修正】`**关于「重设也不恢复」的准确边界**：原稿写作「且重设也不恢复（因为 `registered` 已记住）」——结论对，但只对**同一键**成立，且原因需按第十一轮更正后的调用链表述。逐路径核实如下：
  - **重设为同一个键** → `set_device_shortcut`（`commands.rs:504`）会重跑 `sync_device_shortcuts`，但 `desired` 仍含该键，`:64` 的 `registered.retain(|k| desired.contains(k))` 保留它，`:68-70` 随即 `continue` → **不恢复** ✅（原稿结论成立）；
  - **改设为另一个键** → 旧键离开 `desired`，被 `retain` 清除；新键不在 `registered` 中 → **会重新尝试注册，可恢复**（若新键未被占用）；
  - **先移除再重设**（`remove_device_shortcut` → 再加回）→ `desired` 一度为空，`registered` 被清空 → **会重新尝试，可恢复**。
  即：用户**改一个键**即可绕过，而原稿的「重设也不恢复」若被读成「任何重设都无效」则偏严。这是本轮**两处需收窄的后果边界之一**（另一处见 P0-2 的「任一次」）。
- 与 P0-2 / P3-12 属**同一缺陷家族**：*「失败路径上仍写入成功状态，且无回滚」*。本项目已为该家族建立了 RAII 约定（`SingleFlightGuard` / 句柄包装），但这两处 `let _ =` + 无条件 `insert` 未覆盖。
  - `【第十二轮复核修正】`**本家族成员是 3 条（P0-2 / P3-12 / P2-12），不含 P0-1**。P3-14 原先把本家族写成「P0-1 / P0-2 / P3-12 / P2-12 四条同族」是**另一类缺陷被并了进来**——P0-1 属「守卫被下划线静音」，而本家族三条**根本没有守卫绑定**（`let force` / 两处 `let _ =` 丢弃 `Result`），两者需要**不同的检测手段**。详见 P3-14 的第十二轮修正。
- 日志误导：`:80` 在**尝试之前**就打印 `"registered …"`，失败时日志与事实相反（与 `commands.rs:434-436` 同病）。

**改进建议**

```rust
// 1) 传播失败，并只在成功后才记入 registered
let result = app.global_shortcut().on_shortcut(sc, move |_app, _shortcut, event| { ... });
match result {
    Ok(()) => {
        standard_log!("[shortcut] registered {} -> {}", key, action);   // 成功后打印
        registered.insert(key.clone());
    }
    Err(e) => {
        standard_log!("[shortcut] 注册失败 {} -> {}: {}", key, action, e);
        // 不 insert：保留重试机会，或向用户提示该键不可用
    }
}
```

`register_single`（`:104-111`）同样处理。另建议：把 `sync_device_shortcuts` 的失败计数汇总后经一次 `app.emit` 通知前端，让用户知道「有 N 个快捷键未能注册」。

## 五、P3 低优先级问题与改进建议

### P3-1　`update.rs` 的 WinHTTP 响应体无大小上限
`winhttp_get` 中 `body` 随 `WinHttpReadData` 循环无界增长（`update.rs:246-273`）。GitHub Releases API 响应通常 <100KB，但若响应异常或被中间人放大，可造成内存放大。建议加 `if body.len() > 4 * 1024 * 1024 { return Err("响应体过大") }`。

### P3-2　`compare_versions` 对 `1.2` 与 `1.2.0` 判定为不同版本
`cur_nums < lat_nums` 直接比较 `Vec<u32>`（`update.rs:316-318`），`[1,2] < [1,2,0]` 为真，故 `1.2` 会被判为「低于」`1.2.0`。若 tag 命名不一致（如 `v1.3` 与 `v1.3.0`）可能误报有新版本。建议比较前补齐到等长（不足补 0）。

### P3-3　`battery_notify::NOTIFIED` 不随电量恢复清理
`(设备名, 阈值)` 一旦通知过就永不再通知（`battery_notify.rs:10`，注释已声明「重启后清空重新检测」）。设备充电至 100% 后再次掉到阈值时不会提醒，可能不符用户预期。建议在 `level > 阈值 + 回差`（如 +5%）时移除对应条目。

### P3-4　`popup.html` / `settings.html` 使用内联事件处理器
两页均在第 10 行使用 `<body oncontextmenu="return false">`（`popup.html:10`、`settings.html:10`）。`【复核修正】`原稿仅提到 `popup.html`，经核实 `settings.html` 同样存在。当前 `csp: null` 下无影响，但若要按 P1-10 收紧 CSP 则两页都须先改为 `document.addEventListener("contextmenu", e => e.preventDefault())`。建议提前改掉，为收紧 CSP 铺路。

### P3-5　`app_icon` 中 64KB 栈缓冲
`query_exe_path_by_openprocess` 使用 `[0u16; 32768]`（32768 × 2 = 64KB）栈数组（`app_icon.rs:48`），传给 `QueryFullProcessImageNameW`。默认 1MB 线程栈下安全，但该函数可能运行在 tokio blocking 线程上，属不必要的栈压力。

`【复核修正】`原稿建议「缩小到 8192（覆盖 32K 路径长度上限的两倍已足够）」——该括注**算错了**：8192 个 `u16` 只能容纳 8191 字符，而 Windows 路径上限为 32767 字符，8192 是上限的**四分之一**而非两倍。缩到 8192 会使超长路径（含 `\\?\` 前缀的深目录）触发 `ERROR_INSUFFICIENT_BUFFER` 而失败（`QueryFullProcessImageNameW` 不会静默截断，会返回错误）。

**改进建议**：**首选改为 `Vec<u16>`**（堆分配，既不压栈也不牺牲超长路径支持）；若坚持固定缓冲，8192 可覆盖绝大多数实际路径但需接受超长路径失败的退化，且应把这条权衡写进注释。

### P3-6　弹窗动画的 check-then-act 竞态
`popup.rs` 的 `toggle` / `open_popup` / `close_popup` 均为「读 `ANIMATING` → 计算 → 写 `ANIMATING`」，非原子。快速双击理论上可双开动画线程。若采纳 P1-8 的 `AnimatingGuard::acquire()`（CAS），此问题一并解决。

### P3-11　`start_theme_watcher` 的「读取 → 重新装载」之间存在未受保护窗口
`【第二轮复核新增】`（由原 P2-1 撤回后降级而来）

**位置**：`src-tauri/src/tray.rs:193-206`

循环结构为 `arm → wait → read`：

```rust
loop {
    RegNotifyChangeKeyValue(hkey, 0, REG_NOTIFY_CHANGE_LAST_SET, event, 1);  // ① 装载
    WaitForSingleObject(event, INFINITE);                                    // ② 等待

```

**现状**：③ 读取发生在 ① 装载之后，因此「③ 读取完成 → 下一轮 ① 装载」之间有一个**未受通知保护**的窗口。若主题恰在此窗口内变更，③ 读到的是旧值，而该次变更没有已装载的通知来触发唤醒 → 托盘图标会停留在旧配色，直到下一次主题变更才纠正。

**潜在影响**：窗口宽度为「一次注册表读取 + 循环跳转」的时间量级（微秒级），实际命中概率极低；后果也仅为图标配色短暂滞后，非功能性故障。故定为 P3。

**改进建议**：把读取移到装载之后、等待之前，使「读取点」之后发生的任何变更都能被已装载的通知捕获：

```rust
loop {
    RegNotifyChangeKeyValue(hkey, 0, REG_NOTIFY_CHANGE_LAST_SET, event, 1);  // ① 先装载
    let current = crate::windows::system_dark_mode();                        // ② 再读取
    if current != last { last = current; std::thread::spawn(move || update_tray_icon()); }
    WaitForSingleObject(event, INFINITE);                                    // ③ 后等待
}
```

> 注：本条与已撤回的「忙循环」结论无关。经实测（见 P2-1），手动重置事件不会导致忙循环，`ResetEvent` 亦无必要。

### P3-12　`audio_notify` 的合并标志在 `PostMessageW` 失败时永久泄漏
`【第三轮复核新增】`（第三轮全仓扫描 `compare_exchange` 时发现，前两轮均遗漏）

**位置**：`src-tauri/src/audio_notify.rs:168-173、185-190、202-207、226-231`（4 个 COM 回调）+ 复位点 `:589`

**现状**

```rust
// 4 个 IMMNotificationClient 回调（OnDeviceStateChanged / OnDeviceAdded /
// OnDeviceRemoved / OnDefaultDeviceChanged）中的同一段：
if SYNC_CALLBACKS_PENDING
    .compare_exchange(false, true, Ordering::SeqCst, Ordering::SeqCst)
    .is_ok()
{
    let _ = PostMessageW(Some(self.hwnd), WM_SYNC_CALLBACKS, WPARAM(0), LPARAM(0));  // ← 失败被吞
}
```

```rust
// 复位点：只有消息处理器会复位
WM_SYNC_CALLBACKS => {
    SYNC_CALLBACKS_PENDING.store(false, Ordering::SeqCst);   // ← 唯一复位处（:589）
    ...
}
```

`SYNC_CALLBACKS_PENDING` 是「合并标志」：置位后投递一条消息，由消息处理器复位，从而把密集的设备变更回调合并为一次同步。问题在于 **`PostMessageW` 的失败被 `let _ =` 吞掉**：若投递失败，标志已置为 `true` 但没有消息进入队列 → 处理器永不运行 → 标志**永久停在 `true`** → 此后所有设备变更回调都在 CAS 处失败并静默跳过 → **音频设备变更通知彻底失效**（直到进程重启）。

**触发条件（苛刻，故定 P3）**：已核实 `hwnd` 在回调注册（`:508`）之前就已由 `CreateWindowExW`（`:486`）创建，且合并机制保证同一时刻至多一条消息在队列中（不会因消息堆积而投递失败），因此正常运行期 `PostMessageW` 基本不会失败。现实可触发窗口仅剩**关闭竞态**——`WM_CLOSE → DestroyWindow`（`:607`）使 hwnd 失效，而 `WM_DESTROY`（`:628`）才回收 `AudioMonitor` 并反注册回调，两者之间的极短窗口内若恰有回调触发即会失败；但此时进程正在退出，实际影响有限。

**为何仍值得修**：与 P0-2 属**同一缺陷类别**（标志在失败路径上泄漏且无恢复），而本项目对该类别已有明确的 RAII 约定（`SingleFlightGuard` / 四个句柄包装）。修复成本仅一行，且一旦真被触发，后果是「静默的永久功能失效」——正是最难排查的一类。

**改进建议**

```rust
if SYNC_CALLBACKS_PENDING
    .compare_exchange(false, true, Ordering::SeqCst, Ordering::SeqCst)
    .is_ok()
{
    // 投递失败必须回滚标志，否则后续回调会被永久合并掉
    if PostMessageW(Some(self.hwnd), WM_SYNC_CALLBACKS, WPARAM(0), LPARAM(0)).is_err() {
        SYNC_CALLBACKS_PENDING.store(false, Ordering::SeqCst);
        verbose_log!("[audio_notify] PostMessageW(WM_SYNC_CALLBACKS) 失败，已回滚合并标志");
    }
}
```

4 处需同样处理；建议抽成一个 `fn request_sync_callbacks(hwnd: HWND)` 统一收口，避免下次再漏改。

### P3-14　RAII 守卫带下划线前缀，使 `unused_variables` 保护失效
`【第六轮复核新增】`（实证 P0-1 的编译器行为时发现，属全仓习惯性问题）

**位置**：`wireless_24g/mod.rs:199`、`bluetooth.rs:653`（P0-1 的两处）；同类习惯散布于 `bluetooth.rs:365/374`、`tray.rs:285` 等

**现状**：本仓 RAII 守卫普遍以 `_` 前缀命名（`_guard` / `_tray` / `_radio_find_guard`）。对**确实不会使用**的值，下划线是正确习惯；但对 **RAII 守卫**，其语义恰恰相反——守卫的**全部价值**就在于「必须被持有到作用域结束」，即它**必须被使用**（以 Drop 的形式）。

**已实测的后果**（`rustc 1.96.0`，同构最小复现）：

```
[写法 1] let Some(_guard) = Guard::new() else { return };   → 编译无任何告警
[写法 2] let Some(guard)  = Guard::new() else { return };   → warning: unused variable: `guard`
                                                              help: if this is intentional, prefix it with an underscore
```

即：**下划线前缀把本可捕获「守卫未被持有」这一缺陷的告警静音了**。本项目 `AGENTS.md` 要求 `cargo check` 零告警且 pre-commit 强制拦截——若这些绑定不带下划线，P0-1 会在提交时被自动拦下（详见 P0-1 的第六轮修正）。目前 `cargo check` 确实是零告警，但这份「干净」里**包含了两处被下划线掩盖的真实缺陷**。

**潜在影响**：这是一个**系统性**的隐患放大器——它不制造缺陷，但会**关闭缺陷的自动发现通道**。任何「守卫未被持有 / 被过早 Drop」的缺陷，只要绑定名带下划线，就无法被 CI 拦住。

> `【第十二轮复核修正】`⚠️ **原稿接着写「而这类缺陷（P0-1 / P0-2 / P3-12 / P2-12 四条同族）」，这个四条清单不成立**——它把**两类不同的缺陷**并成了一个「家族」，且其中 3 条**根本没有绑定名可供改名**，本条的护栏对它们完全无效。逐条核实：

| 条目 | 实际代码形态 | 是否有「下划线前缀的绑定」 | 本条（改名护栏）能否拦住 |
|---|---|---|---|
| **P0-1** | `let Some(_guard) = SingleFlightGuard::new(...)`（`wireless_24g/mod.rs:199`、`bluetooth.rs:653`） | ✅ **有**（`_guard`） | ✅ **能**——改名即触发 `unused_variables` |
| **P0-2** | `let force = fresh && BT_BATTERY_REFRESHING.compare_exchange(...).is_ok();` | ❌ 无（`force` 是 `bool` 且**被使用**） | ❌ **不能**——没有守卫绑定，也无可改之名 |
| **P3-12** | `if SYNC_CALLBACKS_PENDING.compare_exchange(...).is_ok() { let _ = PostMessageW(...); }` | ❌ 无（`let _ =` **丢弃 `Result`**，没有绑定名） | ❌ **不能** |
| **P2-12** | `let _ = app.global_shortcut().on_shortcut(...);` | ❌ 无（同上，`let _ =` 丢弃 `Result`） | ❌ **不能** |

> 关键区别：`let _ = <expr>` 与 `let _guard = <expr>` 是**两回事**——前者是**通配模式**，`unused_variables` 对它**任何情况下都不告警**（与命名无关，改名也无从谈起）；只有后者是「有名字但带下划线」，才存在「改名即可恢复告警」的空间。上表共出现三种写法（`_guard` 绑定 / `let force` 具名 bool / `let _ =` 通配丢弃），原稿把它们**混为一谈**，因而高估了本条的覆盖面。
>
> 因此准确的分类是**两类**，而非一个四条家族：
> - **类 ①「守卫被下划线静音」= { P0-1 }**（全仓仅此 2 处属此缺陷；本条护栏只对它有效）
> - **类 ②「失败路径上状态未回滚」= { P0-2, P3-12, P2-12 }**（见 P2-12 的「同一缺陷家族」表述——**报告本身在别处也只列这 3 条**，与本处 4 条清单**自相矛盾**）。这类缺陷**没有守卫绑定**，需另设检测手段（如「置位成功后必须记录状态」的工具化，或 `tools/check.mjs` 对「CAS 成功后无回滚」形态的提示），**改名护栏对它们无效**。
>
> 即：本条的**结论与建议本身是对的**（下划线确实静音了 P0-1 的告警，也确实该改），但**受益面被高估了 3 倍**。

## 六、值得肯定的设计

审查中以下做法质量较高，建议在后续演进中保持：

1. **并发模型的自洽性**：`mpsc + recv_timeout` 探活（`main.rs:243-264`）把「事件循环是否僵死」转化为可判定的超时，比单纯心跳更有效；`TrySuspend`/`Resume` 与 `MemoryUsageTargetLevel` 互补，注释清楚说明了各自职责边界。
2. **RAII 资源管理**：`bluetooth.rs` 中 `RadioFindHandle` / `DeviceFindHandle` / `RadioHandle` / `DeviceInfoSetHandle` 四个 Win32 句柄包装，杜绝了句柄泄漏——**唯独单飞守卫没有沿用这个范式**（P0-1），反差明显。
3. **SWR 缓存语义统一**：`wireless_24g` 与 `bluetooth` 采用一致的「成功值常驻 + 失败不抹除 + 负缓存窗口」，并有对应单测（`apply_result_*`、`apply_battery_*`）覆盖合并规则，这是全仓测试密度最高的部分。
4. **COM 类型安全基座**：`webview.rs` 头部注释解释了 `webview2-com-sys 0.38` + `windows-core-061` 的版本共存原因，`Cargo.toml` 中也标注了「勿合并」——这类"为什么不能改"的注释价值极高。**唯一的例外是 `try_suspend_cb` 手写 vtable**（P0-3），与文件头部「零 transmute、零手写 vtable」的自述相矛盾。
5. **日志分级 + 惰性求值宏**：`standard_log!` / `verbose_log!` 先判开关再 `format!`，日志关闭时零堆分配，设计正确且注释点明了意图。
6. **原子配置写入**：临时文件 + `sync_all` + `rename` 是正确的做法（问题只在锁范围，见 P1-3）。
7. **闸门体系**：`check.mjs` 的「跨文件同名全局函数检测」直接来自真实事故（`updateDeviceCard` 被遮蔽），这类"从事故中提炼检查项"的做法应当继续。
8. **托盘图标生命周期正确**（`【第四轮复核】`排除的一处疑似缺陷）：`tray.rs:285` 写作 `let _tray = TrayIconBuilder::…build()?;`，表面看「局部绑定在 `setup()` 结束时 Drop，托盘图标应随之消失」。经查 `tauri-2.11.5/src/tray/mod.rs:447`，`build_inner` 内部执行 `app_handle.resources_table().add(self.clone())` 并把 `(id, rid)` 记入 `manager.tray.icons`——**应用资源表持有了一份克隆**，故局部绑定 Drop 不影响图标存活。此处不是缺陷，且是「`_` 前缀绑定不等于立即丢弃」的正确用法。
