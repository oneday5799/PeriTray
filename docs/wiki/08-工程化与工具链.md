# 08 · 工程化与工具链

## 1. 提交闸门总览（三道防线）

```
本地 pre-commit 钩子          远端 CI (.github/workflows/ci.yml)
├─ node tools/check.mjs      ├─ node tools/check.mjs
├─ (Rust 有暂存改动时增量)     ├─ cargo fmt --check
│   ├─ cargo fmt --check     ├─ cargo check  (RUSTFLAGS=-D warnings)
│   └─ cargo check 零警告     └─ cargo test
```

热增量成本约 3-4s（Rust 未动时仅 check.mjs <1s）。`git commit --no-verify` 可跳过，仅限明知未完成的 WIP 中间提交。

钩子不随仓库走，重新克隆后安装：

```bash
cp tools/pre-commit .git/hooks/pre-commit && chmod +x .git/hooks/pre-commit
```

## 2. check.mjs 五类校验详解（tools/check.mjs，271 行）

入口即全量运行，任何一类失败整体 exit(1) 并逐条列出错误。

### 第 1 类：HTML 引用与磁盘文件双向一致
- 解析两页 HTML 的 `<link href="*.css">` 与 `<script src="*.js">`：引用的文件必须存在（check.mjs:165-180）
- 反向孤立检测：`scripts/`、`styles/` 目录下每个文件必须被至少一页引用，否则报"孤立文件"（check.mjs:203-212）——防止删了引用留下死文件

### 第 2 类：跨文件调用审计（标识符审计）
核心思路：同一页面的所有 JS 共享全局作用域（经典脚本无模块边界），因此可以静态验证"调用的标识符必有声明"：

- `stripLiterals`：先剥除注释与字符串字面量（含转义处理），避免误报（check.mjs:42-85）
- `declaredNames` 收集声明池：函数声明 / `window.x =` 挂载 / let/const/var / **解构声明**（`const { invoke } = ...`——否则 settings 页裸用 invoke 只能靠 common 内部局部变量意外通过）/ 函数形参（含解构重命名与默认值）/ 箭头函数绑定 / 对象方法简写（check.mjs:87-142）
- `calledNames` 收集调用点：`标识符(` 且非属性访问/字符串内（负向断言排除 `.x(` 与引号前缀）（check.mjs:144-150）
- 白名单豁免三类：JS 关键字 KEYWORDS、浏览器/BOM 全局 BROWSER_GLOBALS、Promise 回调 LOCAL_CALLBACKS
- 命中未声明 → 报错。此机制依赖前端"头注释四要素写清 提供/依赖"的约定成立

### 第 3 类：JS 语法机检
对每个脚本跑 `node --check`（execFileSync），捕获首行 stderr 报告语法错误（check.mjs:224-235）。

### 第 4 类：BOM 扫描
CSS/JS/HTML 全部 dist 文件检查 `EF BB BF` 前缀（check.mjs:152-155, 214-222）。起因见 [07 §10](07-踩坑复盘-高频回归.md)：BOM 曾把首个选择器变成非法节点。

### 第 5 类：版本号一致性
五处必须同版（check.mjs:237-264）：`tauri.conf.json` / `Cargo.toml [package]` / `Cargo.lock`（PeriphMonitor 条目）/ `package.json` / `settings.html` 关于页占位文案。防发版间隙漂移。

**维护注意**（AGENTS.md 原文）：新增页面/目录需同步更新 PAGES 数组；标识符审计出现误报时优先扩展声明提取规则，而非绕过钩子。

## 3. Rust 侧闸门约定

- main.rs 顶部 `#![warn(unused_imports, dead_code)]` + CI `-D warnings` ⇒ 任何 warning 都会挡住合入
- rustfmt 全量格式化已固化（4f39219），格式不符直接拦截
- 日志规范：统一走 `process::append_log` 带 `[模块]` 前缀；新增模块先定标签再写日志（现有标签清单见 AGENTS.md：[popup] [tray] [audio] [bt] [update] [material] [event] [heartbeat] [watchdog] [window] 等）

## 4. CI 工作流

### ci.yml（push main / PR）
windows-latest 单 job 四步：checkout → Rust stable+rustfmt / Node 24 → Cargo 缓存（registry/git/target，key 绑 Cargo.lock）→ 前端完整性 + fmt + check -D warnings + test。

### release.yml（tag v* 触发）
- x64 / arm64 双矩阵构建 NSIS 安装包
- tag 格式校验（`^v\d+\.\d+\.\d+(-.+)?$`），从 tag 提取版本回填配置文件
- softprops/action-gh-release@v3 + generate_release_notes：对已存在的手工 Release 是更新追加而非报错——所以流程允许手工先建 Release 写 notes，CI 构建后自动追加产物

## 5. 发版流程清单（AGENTS.md 固化）

1. **版本号同步五处**（tauri.conf.json / Cargo.toml / package.json / Cargo.lock 经 `cargo check` 自动刷新 / settings.html 占位文案）→ 单独 `chore(release): vX.Y.Z` 提交并 push
2. Release Notes 写临时文件经 `--notes-file` 传入（避免 shell 转义问题）
3. 创建发布：
   ```bash
   gh release create v<ver> --target <完整SHA> --title "PeriphMonitor v<ver>" \
     --notes-file <notes文件> --latest
   ```
   **--target 必须传完整 SHA**（短 SHA 会 422）；tag 含 `-` 时 CI 自动标记预发布

### Release Notes 写作规范（面向普通用户）
- 分节按实际内容取用：✨ 新功能 / 🐛 问题修复 / 🧹 内部优化（一切用户无感知的变化归此节）
- 一条一句话动词开头直给结果；**禁止实现术语**（API 名/函数名/commit 号/"架构/接口层"类词汇）；必要产品名词保留（空间音效、2.4G、快捷键等）
- 关键限定必须保留在条目内：实验性、默认关闭、需重启生效等
- 节内按用户影响程度排序；末尾以「**完整变更列表**：<compare 链接>」收尾
- 信息源取自本版全部 commits 的 body——**这就是 commit body 要求宁详勿略的原因**
