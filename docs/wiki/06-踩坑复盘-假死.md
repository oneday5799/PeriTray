# 06 · 踩坑复盘 · 假死问题 ⭐

> 这是本项目历史上投入最大的单题攻坚（2026-08-23 至 08-24 连续数日、v1.2.11-beta.1~beta.5 五轮发版）。
> **任何涉及窗口生命周期、事件回调、WebView2 的改动，动手前先读完本章。**

## 0. TL;DR

| | A 类：销毁链假死 | B 类：唤醒僵死 |
|--|--|--|
| 症状 | 关闭设置页后托盘/弹窗全部无响应 | 显示器唤醒/系统睡眠后事件循环冻结 |
| 根因 | `CloseRequested` 触发的 wry drop 链中，`controller.Close()`（WebView2 COM 同步调用）在事件循环线程上执行，偶发永久阻塞——其完成依赖浏览器进程回应与宿主消息泵，互等即死 | WebView2 渲染进程在系统睡眠期间持有/阻塞事件循环线程；唤醒后 COM 调用永不返回 |
| 定罪证据 | 三次假死日志均为"心跳存活但 CloseRequested(settings) 后零事件分发" | `[watchdog] time jump: 20s` + heartbeat 期间零事件分发 + 看门狗 streak 自重启成功 |

| 兜底 | 事件循环僵死 → 探活超时 ×2 → 自重启新实例，假死从永久降为最坏 ~40s 自愈 | 同左 |

## 1. 背景：为什么 Tauri 应用会"全局假死"

Tauri 在 Windows 上是**单进程单事件循环**架构：

- 所有窗口消息、菜单事件、`on_menu_event` / `on_tray_icon_event` / `on_window_event` 回调都在**同一个事件线程**上分发
- 该线程上任何一个同步调用挂起（Win32 API 死等、COM 跨进程调用阻塞、Mutex 死锁），**整个应用所有功能一起冻结**——但进程还活着，表现为"托盘在、点了没反应"
- WebView2 是多进程浏览器架构，Rust 侧 controller 与渲染/浏览器进程之间是 **COM 跨进程同步调用**——这类调用的完成依赖对方进程健康，是最危险的阻塞源
- Windows 强制 STA 属主线程销毁 COM 对象，所以"销毁 webview"这件事天然落在事件线程上，**根治不存在，只能工程兜底**

这个认知是整个攻坚期换来的第一条教训。此前代码里大量回调直接在事件线程做重活（显示器枚举、配置读取、DWM 材质调用、show/focus），每一处都是潜在的假死点。

## 3. 排查方法论（比结论更值得复用的部分）

假死的最大困难是**现场无证据**：进程活着但不响应，panic hook 不触发，普通日志看不出哪一步卡住。攻坚期沉淀出一套"埋点—定罪—修复"流程：

### 3.1 心跳定位死点时刻
独立线程周期性写 `[heartbeat]` 日志（aa24b3f）。事件循环死亡时心跳也停 → 日志最后一条心跳的下一刻即死点；配合事件入口打桩（`[tray] click / [tray] menu: xxx`）可判断"事件分发是否还活着"。**铁证特征：心跳存活但零事件分发 = 事件循环线程卡死而非进程死亡**。

### 3.2 panic hook 补证据链
583772a 之前 panic 不留任何文件证据。加 hook 先落盘再弹窗（main.rs:30），排除"其实是崩溃被误认为假死"这一整类干扰。

### 3.3 定罪埋点要"低频低开销、直指假设"
9864910 为验证"B 类与显示器唤醒相关"，只加了三个探针：电源状态快照、15s 周期的时间跳变检测（>20s 说明经历过睡眠）、窗口几何事件（ScaleFactorChanged/Moved/Resized——唤醒时必收到）。预期定罪路径写进 commit："下次僵死时若 time jump 紧邻 ScaleFactorChanged 且时间吻合 → 定罪 WebView2 渲染恢复阻塞"。**结果一次实测命中**。

### 3.4 修复后清理诊断残留
f08b5af 在根治落地的同时删掉了全部临时埋点（保留心跳与看门狗），避免诊断代码长期污染日志与性能。诊断代码要有退出机制。

## 4. 两类假死的完整复盘

### 4.1 A 类：设置页关闭销毁链阻塞（882a45b）

**现象**：用户关闭设置窗口后，托盘点击/菜单全部失灵。

**定罪过程**：三次假死日志呈现同一模式——`CloseRequested(settings)` 事件之后心跳继续、零事件分发。结合 wry 源码审查确认死因：窗口 drop 链中 `InnerWebView::drop` 会同步调用 `ICoreWebView2Controller.Close()`，这是 COM 跨进程调用，浏览器进程繁忙时可能永久不返回；而 Windows 强制该销毁发生在事件线程（STA 属主）。

**修复设计**（三层递进）：

1. **hide 先行**（main.rs:366-367）：`api.prevent_close()` + 立即 `window.hide()`——点击瞬间视觉响应，用户侧零感知差异
2. **延迟销毁**（main.rs:368-377）：子线程 sleep 3s 后复查 `is_visible()`（延迟期内被重开则放弃本次销毁，保留内存回收语义）再 `destroy()`。destroy 仍会走那条危险链路，但从"用户点击的关键路径"挪到了"无人等待的后台时刻"；`dispatched/destroyed` 成对日志用于终审定罪
3. **看门狗兜底**：即便如此仍有极小概率卡死 → 见 §5 自愈机制

### 4.2 B 类：显示器唤醒事件循环僵死（f08b5af 根治）

**现象**（beta.2 用户实测）：外接显示器唤醒瞬间，托盘假死；且此时没有设置页销毁参与——证明存在独立于 A 类的第二类成因。

**定罪过程**：9864910 埋点一次命中。日志链条：`time jump 20s`（期望 15s → 系统睡过）→ heartbeat 存活 → 零事件分发 → 看门狗 streak=2 自动重启成功（重启后恢复正常，进一步排除硬件因素）。结论：**系统睡眠时 WebView2 渲染进程处于活跃状态，唤醒瞬间其对宿主 COM 调用的处理与事件循环互等**。

**根治设计**：让渲染进程在不需要时彻底休眠——

- popup 关闭动画结束 → `suspend_webview`：`put_IsVisible(FALSE)` + `TrySuspend`（windows.rs:380-421），渲染进程完全挂起。此后系统睡眠时 COM 不活跃，无从阻塞
- popup 打开前 / 看门狗检测到 time jump → `resume_webview`：`Resume` + `put_IsVisible(TRUE)`
- 页面状态跨 suspend 完整保留，用户无感

### 4.3 附生波折：COM 接口获取的两连错（bc83957 → 5c491f1）

TrySuspend 方案在 beta.4 一度回退为 put_IsVisible 过渡版，原因是 QI 失败的两段乌龙：

1. **第一错**：使用了错误的 GUID（0x8ee661b0...），真实对象不识别 → E_NOINTERFACE
2. **第二错**（根）：webview2-com-sys 的 `define_interface!` 宏生成的是**合成 IID（Rust 类型名哈希）**，并非微软官方 COM IID——用它 QI 运行时真实 WebView2 对象必然失败。这是 Rust COM 绑定生态的经典陷阱：编译通过 ≠ IID 正确

**修正**：改用官方绑定中的正确 IID `{A0D6DF20-3B92-416D-AA0C-437A9C727857}`（ICoreWebView2_3），TrySuspend/Resume 恢复完整可用；put_IsVisible 降级为其前置条件（TrySuspend 要求 IsVisible=FALSE）。

**教训**：手调 COM 时 IID 必须取自官方 IDL/webview2-com-sys 官方绑定常量，绝不可用宏合成值；vtable 偏移同理需以官方绑定布局为准（现注释块 windows.rs:255-270 记录了完整推导链，勿删）。

## 5. 看门狗自愈机制详解（main.rs:289-344, 92-108）

无论根因为何，只要事件循环僵死就需要兜底。设计要点：

### 5.1 探针原理
```text
每 15s：
  写 [heartbeat]
  时间跳变检测：elapsed > 20s ⇒ 经历过睡眠/唤醒 → resume_webview 兜底
  探活：spawn worker 线程 → popup.is_visible()（经 proxy 往返，事件循环僵死则永挂）
        worker 结果经 channel 回传，主循环 recv_timeout(5s)
  超时 ⇒ stuck_streak += 1；连续 2 次（最坏 ~40s）⇒ watchdog_self_restart()
```

- 为什么用 is_visible 做 probe：它是一次轻量的 proxy 往返，事件循环健康时毫秒级返回，僵死时恰好永远排队——天然的"事件循环活性"试金石
- 为什么连续 2 次才判死：容忍单次系统级抖动（如游戏加载导致的瞬时卡顿），降低误杀率

### 5.2 自重启协议
`watchdog_self_restart`（main.rs:92）：spawn 自身 `--autostart --watchdog-restart=<旧pid>` → sleep 300ms → exit(0)。新实例 main() 开头内核级等待旧 pid 死亡（最多 3s）才开始初始化。

## 6. 攻坚期的两个衍生修复（同样重要）

### 6.1 "转发自杀"竞态（31996b6）

beta.1 用户实测暴露：看门狗正确触发自重启，但**新实例启动竞态窗口内被 single-instance 插件误判为第二实例**——旧实例互斥量/事件的内核对象清理晚于进程退出可见性，新实例 `CreateMutexW` 撞上 `ERROR_ALREADY_EXISTS` 后走转发路径 `exit(0)`，自愈失败且看起来像"又死了"。

**结构性免疫**：`--watchdog-restart` 实例不再注册 single_instance 插件（main.rs:163-166）。理由：旧进程数百毫秒内必退、新实例必然独占，此场景下单实例保护无用且有致命副作用。wait_process_exit 保留以尽量缩短重叠窗口。

**教训**：插件提供的"保护机制"在非典型启动路径上可能变成凶器；自愈路径必须端到端演练（当时跑了 7 轮双实例压测）。

### 6.2 事件线程硬化（583772a + e193d99）

定罪之前先消除已知风险面，两步把事件线程上的重操作清空：

- 583772a：托盘点击回调改为纯分发（坐标记录 + spawn toggle）；6 处裸 `lock().unwrap()` 改毒化容忍；single-instance 回调体 spawn 化并补 popup 缺失分支
- e193d99：托盘菜单 show/volume/settings/about 四分支、Focused 失焦关闭、设置页已有窗口重开路径（DWM 材质+show+focus）全部 spawn 化

**由此确立本项目最重要的一条编码铁律**（现已写入 tray.rs:246 注释与各回调现场）：

> 事件线程回调只做"记录参数 + clone AppHandle + spawn"；一切可能慢的操作（WMI、COM/DWM、窗口 show/focus/move、配置 IO）一律移出。
