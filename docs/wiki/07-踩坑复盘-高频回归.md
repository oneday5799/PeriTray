## 1. 窗口材质（Mica/Acrylic）—— 五连修后的架构级根治 ⭐

**症状时间线**（v1.2.x 早期）：切换材质失效（ad7886c）→ 深色主题 flyout 背景错（32465c3）→ 卡片展开背景透明异常（011f6eb）→ 主窗口与设置页不同步（080af17）→ **打包后材质整体失效**（dd4d022）。中间还有一轮失败重构存档于 `backup/failed-material-round` 分支。

**根因**（dd4d022 定罪）：Tauri 窗口的透明能力在**创建瞬间固化进 HWND**——创建时未带 `transparent(true)` 的窗口，其合成表面不支持像素级 alpha，事后 `SetDefaultBackgroundColor` 即使返回成功也无法与 DWM 混合。debug 构建的时序侥幸掩盖了问题，release 暴露：
- 主窗口以默认（不透明）材质出生并永久复用 → 永远不透明
- 设置页运行时切换依赖"出生状态" → 必须重开窗口才生效

**最终方案：恒透明架构**
- 两窗口无条件 `transparent(true)` 出生（popup.rs:167-169、windows.rs:64-66）；「默认」材质的不透明观感由 CSS `--page-bg` 实色承担（视觉零差异）
- COM 层退化为创建时一次性设定（`ensure_webview_bg_transparent` 带重试），运行时只切两层：DWM 背景板 + 前端 `data-material` CSS
- 切换协议（windows.rs:725-768）：**先**广播 `material-changed` 让前端铺 CSS，**再**延迟 120ms 摘默认材质背景板；延迟任务执行前复核配置防快速往返竞态
- DWM 应用三层降级：DWMWA_SYSTEMBACKDROP_TYPE(38) → DWMWA_MICA_EFFECT(1029) → AccentPolicy BlurBehind（未公开 API 动态解析）

**防回归守则**：
1. 任何新窗口必须恒透明出生，禁止按配置决定 transparency
2. 运行时禁止触碰 webview 背景 COM 层
3. 材质相关时序改动必须在 release 构建下验证（debug 时序侥幸是本项目最贵的一课）
4. AGENTS.md 备忘：材质系统收敛（删除 settings-general 手动三件套）暂缓中——下次动材质代码顺手做并实测闪烁

## 2. 托盘坐标换算 —— 双臂匹配铁律

**症状**：弹窗从 (0,0) 弹出半截（ce8853e）；缩放屏上弹窗只弹出上半、底边裁出屏幕约 270px（fbb6c01，日志实证 sf=1.25 时 y 携带物理值 1380 而下游按逻辑坐标消费）。

**根因**：Tauri 的 tray rect 位置可能是 Physical 也可能是 Logical 两套坐标；两轮独立事故分别是①重构回调时误删 Logical 分支②Physical 分支只除了 x 没除 y。

**最终方案**（tray.rs:339-342）：双臂 match 完整保留，物理分支 x/y 统一转逻辑：
```rust
let (px, py) = match rect.position {
    tauri::Position::Physical(p) => (p.x as f64 / sf, p.y as f64 / sf),
    tauri::Position::Logical(p) => (p.x, p.y),
};
```

**防回归守则**：动托盘回调时双臂一个都不能少；物理↔逻辑转换必须成对检查 x 和 y。排查此类问题用 toggle 心跳全量快照（tray 坐标/sf/屏高/target）一次定位。

## 3. 弹窗 Z 序 —— 一条不变式终结三连修

**症状**：动画期间弹窗被前台窗口遮挡、结束时"凭空出现"（eeb6460）；上浮时盖住任务栏（bfdeb94）；托盘重开后切标签动画偶发丢失（c66ff3f）。

**根因**：show/close 流程中置顶状态被反复切换——先降置顶再显示导致动画期不 topmost；纯 always_on_top 又会把窗口抬到 topmost 波段顶而盖住任务栏；焦点激活还会再次抬升 Z 序。

**最终方案**：确立并全程维持一条不变式（popup.rs show/create/animate_open 四处接线）：

> **弹窗自创建起恒为 topmost（builder 保证）；可见期间恒位于「普通窗口之上、任务栏之下」——由 `place_below_taskbar()` 在 show 后、animate_open 末尾（set_focus 之后）、close 开始前三个时机强制沉降实现。**

`place_below_taskbar`（windows.rs:142-161）：FindWindowW("Shell_TrayWnd") + SetWindowPos 插队至任务栏正下方；找不到任务栏（Explorer 重启间隙）保持原序。

**防回归守则**：改 popup 显隐流程只能调整"何时调用沉降"，不能删除任何一处沉降调用点；set_focus 会抬升 Z 序这一点决定了它之后必须补一次沉降。

## 4. 空间音效 —— 未公开接口的防御性写入

**背景**：走 `CPolicyConfigClient` 未公开扩展接口（槽位经 PDB 符号 + 运行时双重验证，audio_spatial.rs）。

**症状系列**：菜单在未装提供应用时仍显示全部格式（2038774 已改为动态过滤）；激活格式被卸载后设备端点停留非标准过渡态 → 设备级读取失败导致整个右键菜单退化、且无法切换其他格式（4a2bc8b）；布局自检硬闸门误杀合法写入（8e3982e）。

**最终方案**（三层防御，均已落地）：
1. 读失败降级：返回无勾选的可用格式列表而非报错；写入走降级路径（fmt=null 直写 + 尽力读回）
2. 布局自检从硬闸门降级为日志记录（真正防线是写后读回校验）
3. 读回校验带 200ms 延迟重试，容忍音频引擎异步归一化

**防回归守则**：未公开接口的任何"校验"都只能是软约束；一切写入必须有读回验证兜底；仅接口缺失才提示用户跳系统设置。

## 6. 应用级音频设备切换 —— 接口路径打包陷阱

**症状**：功能上线后切换形同虚设（052d113）。

**根因**：`SetPersistedDefaultAudioEndpoint` 要求 deviceId 打包为完整设备接口路径 `\?\SWD#MMDEVAPI#<MMDevice id>#<接口后缀>`；此前传裸 id，API 返回 0x80070057 被静默吞掉，持久化覆盖从未创建。Get 侧同理需解包，且 Get 的 0x80070057/0x80070490 语义为"无覆盖"而非错误。

**防回归守则**：未公开 API 的 HRESULT 语义要逐个查证并显式分类，禁止统一当 Err 吞掉；涉及 SWD/MMDEVAPI 的 id 必须经打包/解包函数往返，禁止裸传。

## 7. 静音语义与音量钳制 —— 三态模型的确立

静音相关曾连续五修（6d79ab5 引入锁定 → c5530c6 图标/tooltip → 29b2c4a 精细调节 → 2c3f361 音量式设备兼容 → b98a7c2 锁定范围收窄）。最终确立的三态语义：

| 用户操作 | 语义 | 表现 |
|----------|------|------|
| 点击静音图标 | 按钮（永久）静音 | 红色图标；静音锁开启时进入锁定，拖滑块不解锁 |
| 滑块拖到 0 | 临时静音（仅下发音量 0） | 不变红 |
| 强制静音 | 对需多次点击才能真静音的设备一次直达 | set_device_mute 显式路径 |

配套的后端行为：`set_device_volume` 在静音锁开启时执行"只许降"钳制（target=min(target,current)）。**注意该钳制与"解除静音后补发目标音量"存在并发竞态**——这正是下一节保序锚点修复的对象。

**防回归守则**：改动静音/音量链路时先画清三态归属；按钮静音的持久性靠 buttonMutedDevices 集合跨刷新保持，勿移除。

## 8. 「拖零不静音/音量回弹」—— 与硬件固件的对抗及其失败 ⭐（78ca25b 调查归档）

这是项目里唯一一次"确认不可修复并正式归档"的调查，结论对后续所有音频交互设计有约束力。

### 问题一：有线耳机拖到 0 仍有微弱声音 —— 设备物理特性
- **定性**：DUNU DTC100pro（USB DAC 耳放一体机）上探针复测软件链路完全正常——SetMasterVolumeLevelScalar(0) 成功且持久、混合器同步显示 0、app 行为与 Windows 原生滑块一致
- **根因**：WASAPI 标量是归一化值，该设备 GetVolumeRange 报告 dB 范围 [-63.5, 0]，scalar=0 映射到 -63.5dB 衰减**而非静音**，约剩满幅 0.07% 声压，高灵敏度耳机可闻
- **已排除**：静音锁门禁、独占模式流、外部代理回写、invoke 失败、dataset 失配
- **决策**：尊重设备物理特性维持原生行为，**不实现拖零自动静音**

### 问题二：智能音箱拖到 0 回弹至 ~6.3% —— 固件 HID 代理
- **现象规律**：实测回弹值恰为 8/127≈0.0630、6/127、4/127——设备固件按 HID 0-127 步进同步硬件档位，规则是强制「muted 与否等价于标量是否恰在下限」：mute@任意非下限值会在 200ms~1s 内被回写为 {vol=下限, 取消静音}；低于下限的标量也被钳回
- **三轮对抗方案全部失败**：
  - v1 拖零自动静音+意图标记：标记被自己的静音成功推送提前清除，重试永不触发
  - v2 防抖确认后重试：机制可用，但手势节流尾沿会再发一次标量 0 再次触发代理回写
  - v3 拖零仅走静音通道：下行经过亚下限区间的节流拍点、上拖补发等时机仍被代理介入，日志出现数十次静音乒乓 retry 循环
- **结论**：**软件层无法稳定赢过硬件固件的状态同步**

### 最终决策
拖到 0 仅下发标量由设备自行钳制，不做拦截；需要真静音时引导使用「强制静音」（其设计动机正是为此类"最低音量才真正静音"的设备）。全部探针与实验代码已移除。

### 附带的真 bug 修复：静音上拖保序锚点
设备卡从静音态向上拖动时，此前"解除静音"与"音量写入"是两个并发 IPC：若音量写入先落地，后端"只许降"钳制读到 current=0（上次拖零所致）把目标钳成 0——表现为滑块显示新值而设备实际无声。修复（popup-audio.js）：解除静音落地**后再**补发目标音量（保序锚点）。

**防回归守则**：
1. 不再尝试任何"拖零自动静音/对抗回写"方案（调查结论见 78ca25b，勿重开）
2. 新增音量类交互时默认假设设备侧可能异步回写，UI 以事件推送为准而非本地乐观值
3. 解除静音与音量写入必须保序

## 9. 设备名与去重 —— core_name 语义边界

早期系列修复（74980fe、2e4185e）：PnP/BT/Battery 三路查询对同一物理设备产生名称漂移（原始名/精简名/带协议后缀），直接字符串比较导致去重失效、连接态误判。

**确立的约定**：
- 存储与比较一律用 `core_name`（dedup.rs：括号内核心名剥蓝牙协议后缀）
- BT UPDATE 路径不再更新 name 字段；Battery 设备存精简名
- **dedup::core_name 与 tray::simplify_device_name 语义不同**（后者仅 UI 显示取括号内容、不剥后缀），两者勿互换——dedup.rs 头注释有显式警告
